# Инструменты — Staff

### Современные фреймворки для тестирования (Cypress, Playwright), а также интеграция с инструментами для E2E-тестирования

Cypress и Playwright решают одну задачу разными средствами, и выбор между ними определяется требованиями проекта.

| | Cypress | Playwright |
|---|---|---|
| Модель выполнения | тесты выполняются внутри браузера, рядом с приложением | внешний драйвер через CDP/протоколы браузеров |
| Браузеры | Chromium, Firefox, WebKit (с ограничениями) | Chromium, Firefox, WebKit полноценно |
| Параллелизм | через платный Cloud или ручное шардирование | из коробки, воркеры и шардинг |
| Несколько вкладок/доменов | ограниченно | нативно, включая несколько контекстов |
| Отладка | интерактивный раннер, time-travel | trace viewer, видео, пошаговый разбор |
| Скорость на больших наборах | ниже | выше |

Практический выбор: Playwright — для больших E2E-наборов, кросс-браузерных проверок и CI с параллелизмом; Cypress — когда важен интерактивный цикл разработки тестов и команда уже в нём работает.

```ts
// playwright.config.ts — конфигурация, пригодная для CI с самого начала
export default defineConfig({
  testDir: './e2e',
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,          // ретраи только в CI, локально ошибка должна быть видна
  reporter: [['html'], ['junit', { outputFile: 'results.xml' }]],
  use: {
    baseURL: process.env.BASE_URL ?? 'http://localhost:5173',
    trace: 'on-first-retry',                // трейс только для упавших — иначе артефакты раздуваются
    video: 'retain-on-failure',
  },
  projects: [
    { name: 'setup', testMatch: /auth\.setup\.ts/ },
    { name: 'chromium', use: { ...devices['Desktop Chrome'], storageState: '.auth/user.json' }, dependencies: ['setup'] },
    { name: 'mobile', use: { ...devices['iPhone 14'], storageState: '.auth/user.json' }, dependencies: ['setup'] },
  ],
  webServer: { command: 'npm run preview', port: 5173, reuseExistingServer: !process.env.CI },
});
```

```ts
// Стабильный тест: селекторы по роли и данным, ожидание состояния вместо таймаутов
test('оформление заказа', async ({ page }) => {
  await page.goto('/cart');
  await page.getByRole('button', { name: 'Оформить' }).click();
  await expect(page.getByTestId('order-status')).toHaveText('Оплачен'); // авто-ожидание
});
```

Интеграция в процесс: E2E запускаются на pull request только для затронутых сценариев (smoke-набор) и полностью — по расписанию и перед релизом; артефакты (трейсы, видео, скриншоты) публикуются в CI; тест, который «моргает», карантинится и чинится, а не перезапускается бесконечными ретраями. Компонентное тестирование (Playwright CT, Cypress Component Testing) закрывает середину пирамиды — быстрее E2E и ближе к реальному рендеру, чем unit.

### Особенности использования инструментов контрактного тестирования (Pact, Dredd)

Контрактное тестирование проверяет совместимость потребителя и поставщика API без поднятия всей системы целиком.

**Pact** реализует consumer-driven подход:

1. Фронтенд (consumer) в тестах описывает ожидаемые запросы и ответы — из этого генерируется файл контракта (pact-файл).
2. Контракт публикуется в брокер (Pact Broker).
3. CI бэкенда (provider) прогоняет контракт против реального сервиса — верификация падает, если ответ изменился несовместимо.
4. `can-i-deploy` проверяет перед деплоем, совместимы ли версии, которые окажутся вместе в окружении.

```ts
// Consumer-тест: фиксируем ожидания фронтенда от API
await provider.addInteraction({
  state: 'существует пользователь 42',
  uponReceiving: 'запрос профиля',
  withRequest: { method: 'GET', path: '/api/users/42' },
  willRespondWith: {
    status: 200,
    body: like({ id: 42, name: 'Аня', email: 'a@example.com' }), // matcher по типу, а не по значению
  },
});
```

**Dredd** работает от спецификации: берёт OpenAPI/API Blueprint и проверяет, что реальный сервис отвечает так, как задокументировано. Это provider-driven подход — он ловит расхождение реализации и документации, но не показывает, что именно нужно конкретному потребителю.

Что даёт контрактное тестирование фронтенд-платформе: breaking change обнаруживается в CI бэкенда, а не в проде; отпадает необходимость держать полный интеграционный стенд для каждой проверки; моки в тестах перестают расходиться с реальностью, потому что они и есть контракт. Ограничения: контракт проверяет форму и статусы, а не бизнес-семантику, и требует дисциплины — устаревшие контракты нужно удалять, иначе верификация превращается в шум.

### Принципы работы с инструментами для управления крупномасштабными проектами (Nx, Turborepo, Bazel)

Все три инструмента решают одну задачу — не пересобирать и не перетестировать то, что не менялось, — но с разной глубиной.

| | Turborepo | Nx | Bazel |
|---|---|---|---|
| Модель | граф задач по `package.json` | граф проектов + анализ импортов | герметичная сборка по явным правилам |
| Кеш | локальный и удалённый | локальный, удалённый, computation cache | строгий контентный кеш |
| Порог входа | низкий | средний | высокий |
| Возможности | пайплайны задач, фильтры | генераторы, границы модулей, миграции, плагины под фреймворки | полиязычные монорепозитории, воспроизводимость до байта |
| Когда выбирать | JS-монорепозиторий, нужно быстро | продуктовый JS/TS-монорепозиторий с несколькими командами | огромный полиязычный репозиторий, требование строгой воспроизводимости |

```json
// turbo.json — кеш работает только при явно объявленных входах и выходах задачи
{
  "pipeline": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "test": { "dependsOn": ["build"], "outputs": ["coverage/**"], "inputs": ["src/**", "tests/**"] },
    "lint": { "outputs": [] },
    "dev": { "cache": false, "persistent": true }
  }
}
```

```bash
# Инкрементальность: собираем и тестируем только затронутые изменением проекты
turbo run build test --filter=...[origin/main]
nx affected -t build test lint --base=origin/main
```

Практика эксплуатации монорепозитория, которая важнее выбора инструмента: единая версия общих зависимостей (`pnpm` с workspace-протоколом и `overrides`), автоматические границы между слоями и доменами (`@nx/enforce-module-boundaries` или `eslint-plugin-boundaries`), кодовладение через `CODEOWNERS`, генераторы для типовых пакетов, удалённый кеш в CI и обязательное объявление входов/выходов задач — без этого кеш будет либо промахиваться, либо отдавать устаревший результат.

### Инструменты для сканирования уязвимостей (в том числе в npm-пакетах)

Задача — обнаруживать уязвимости до релиза и не превращать процесс в поток игнорируемых предупреждений.

Слои проверки:

- **SCA (зависимости).** `npm audit`, `pnpm audit`, Snyk, Dependabot/Renovate, OSV-Scanner — сверяют lock-файл с базами CVE/GHSA.
- **SAST (собственный код).** ESLint с security-плагинами, Semgrep, CodeQL — ищут опасные паттерны: `innerHTML` из непроверенного источника, `eval`, небезопасные регулярные выражения.
- **Секреты.** Gitleaks, TruffleHog, GitHub secret scanning — токены, попавшие в репозиторий.
- **Контейнеры и артефакты.** Trivy, Grype — базовые образы, в которых деплоится фронтенд.
- **DAST.** OWASP ZAP по staging-стенду — проверка уже работающего приложения.
- **Цепочка поставки.** `npm ci --ignore-scripts` в CI, проверка провенанса пакетов, lock-файл под ревью, политика на новые зависимости.

```yaml
# CI: сборка падает только на действительно значимом, остальное — в отчёт
- name: dependency audit
  run: pnpm audit --audit-level=high --prod

- name: static analysis
  uses: github/codeql-action/analyze@v3

- name: secrets scan
  run: gitleaks detect --redact --exit-code 1
```

Организационная часть, без которой инструменты не работают: пороги (что блокирует мерж, что попадает в бэклог с SLA на исправление), процесс исключений с обоснованием и сроком, регулярное обновление зависимостей автоматическими PR — большинство уязвимостей закрывается патч-версией, если репозиторий не отстаёт на год, и отдельное внимание транзитивным зависимостям, которых в типичном фронтенд-проекте на порядок больше прямых.

### Настройка и оптимизация работы с монорепозиториями, устранение дублирования и конфликтов зависимостей

Дублирование зависимостей — это одновременно размер бандла, время сборки и источник трудноуловимых багов (две копии одной библиотеки с внутренним состоянием).

```yaml
# pnpm-workspace.yaml — единый каталог версий на весь репозиторий
packages:
  - 'apps/*'
  - 'packages/*'
catalog:
  vue: ^3.4.0
  pinia: ^2.1.0
```

```json
// package.json пакета: версия берётся из каталога, разъехаться невозможно
{
  "dependencies": { "vue": "catalog:" },
  "peerDependencies": { "vue": "^3.4.0" }
}
```

```bash
pnpm dedupe --check            # в CI: падает, если появились дубли
pnpm why vue                   # кто именно притащил вторую версию
npx vite-bundle-visualizer     # подтверждение дублей в собранном бандле
```

Дополняющие меры: `overrides` для форсирования версии транзитивной зависимости, `peerDependencies` во всех внутренних библиотеках вместо прямых, запрет глубоких импортов через поле `exports`, единая политика обновления мажорных версий платформенной командой и размерный бюджет в CI как индикатор — внезапный рост бандла почти всегда означает продублировавшуюся зависимость.

### Интеграция Performance API с RUM для анализа реального пользовательского опыта

Лабораторные замеры показывают потенциал, RUM — реальность: медленные устройства, плохие сети, холодный кеш, реальные сценарии.

```ts
// rum.ts — сбор метрик и отправка одним пакетом, без влияния на производительность страницы
import { onLCP, onINP, onCLS, onTTFB } from 'web-vitals';

const buffer: MetricPayload[] = [];
const push = (m: MetricPayload) => {
  buffer.push(m);
  if (buffer.length >= 10) flush();
};

function flush() {
  if (!buffer.length) return;
  const body = JSON.stringify({
    release: import.meta.env.VITE_RELEASE,
    route: router.currentRoute.value.name,     // метрика без контекста бесполезна
    connection: (navigator as any).connection?.effectiveType,
    deviceMemory: (navigator as any).deviceMemory,
    metrics: buffer.splice(0),
  });
  navigator.sendBeacon('/rum', body);          // переживает уход со страницы
}

[onLCP, onINP, onCLS, onTTFB].forEach((fn) => fn((m) => push({ name: m.name, value: m.value, rating: m.rating })));
addEventListener('visibilitychange', () => { if (document.hidden) flush(); });

// Собственные бизнес-таймеры поверх стандартных метрик
performance.mark('checkout:start');
await submitOrder();
performance.measure('checkout', 'checkout:start');
new PerformanceObserver((list) => list.getEntries().forEach((e) => push({ name: e.name, value: e.duration })))
  .observe({ type: 'measure', buffered: true });
```

Что делает RUM полезным, а не декоративным: метрики считаются по перцентилям (p75/p95, а не среднее), разрезаются по маршруту, релизу, типу устройства и сети, привязаны к версии сборки для поиска регрессий, и на них настроены алерты. Замыкается цикл бюджетами в CI: пороги, нарушенные в лаборатории, блокируют релиз, а деградация в поле создаёт задачу с приоритетом.

### Выявление системных взаимосвязей и определение стандартов инструментальной платформы

Инструменты в зрелой организации — это платформа, а не набор личных предпочтений. Задача уровня Staff — видеть систему целиком и находить первопричины, а не чинить симптомы.

Признаки системной проблемы и типичные первопричины:

| Симптом | Что обычно стоит за ним |
|---|---|
| «Тесты постоянно падают, все ставят retry» | нестабильные селекторы и зависимость тестов от общего состояния, а не «плохой раннер» |
| «CI идёт 40 минут» | отсутствие кеша и инкрементальности, а не медленные раннеры |
| «Бандл вырос вдвое» | дубль зависимости после обновления одного пакета |
| «Каждая команда чинит одно и то же» | нет общего пакета и владельца, копипаста вместо библиотеки |
| «Обновления ломают проекты» | нет единого каталога версий и автоматических миграций |

Порядок внедрения стандарта, который приживается: сначала измерить проблему числом, затем пилот на одном проекте, затем автоматизация (шаблон, генератор, правило линтера, проверка в CI), затем миграция остальных с кодмодами, и только в конце — запрет старого способа. Стандарт без автоматической проверки не соблюдается, а запрет без пути миграции блокирует работу команд.
