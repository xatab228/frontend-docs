# Вёрстка (HTML, CSS) — Staff

### Превышает ожидания по уровню и глубине знаний Senior-уровня

Матрица требований не задаёт для Staff отдельный список тем по вёрстке: предполагается свободное владение всем материалом Junior–Senior плюс работа на уровне системы, а не отдельной страницы. Практически это означает три вещи: видеть первопричины проблем вёрстки в масштабе продукта, задавать стандарты и методологию для всех команд и решать задачи, для которых готовых приёмов нет.

Ниже — как эти три ожидания выглядят применительно к HTML и CSS.

### Выявление системных взаимосвязей, компромиссов и первопричин проблем

Отличие уровня Staff — умение отличить симптом от причины. Одна и та же жалоба почти всегда имеет системный источник, и чинить нужно его.

| Симптом | Обычная первопричина | Системное решение |
|---|---|---|
| «Стили постоянно ломаются в чужих компонентах» | глобальные селекторы и каскад без изоляции | методология изоляции (BEM/CSS Modules/Shadow DOM), запрет глобальных правил вне слоя `base` |
| «Правки требуют `!important`» | неконтролируемая специфичность, конкурирующие источники стилей | `@layer`, единая шкала специфичности, ревью на селекторы |
| «CSS-бандл растёт на каждый спринт» | дублирование значений вместо токенов, мёртвые правила | дизайн-токены, отчёт неиспользуемого CSS в CI |
| «Верстка прыгает при загрузке» (CLS) | отсутствие резервирования места под медиа и шрифты | `aspect-ratio`, размеры у изображений, `font-display`, скелетоны нужной высоты |
| «Анимации дёргаются на слабых устройствах» | анимируются свойства, вызывающие layout | ограничение анимаций `transform`/`opacity`, бюджет на слои |
| «Каждая команда рисует свою кнопку» | нет общей библиотеки и владельца | дизайн-система с реальным контрактом и версионированием |
| «Интерфейс недоступен с клавиатуры» | доступность не заложена в компоненты и не проверяется | a11y-правила в линтере и автотестах, компоненты с корректной семантикой по умолчанию |

Инструмент анализа — не только DevTools, но и данные: доля страниц с плохим CLS в RUM-метриках, размер и покрытие CSS, число уникальных значений цвета и отступов в кодовой базе (разброс — прямой индикатор отсутствия токенов), частота однотипных багов вёрстки в трекере.

Отдельная часть работы — явная фиксация компромиссов. Почти каждое решение в вёрстке — это обмен: Shadow DOM даёт изоляцию, но усложняет глобальную тему; utility-CSS ускоряет разработку, но делает разметку шумной; критический CSS ускоряет первый экран, но усложняет сборку; поддержка старых браузеров стоит размера бандла. Задача Staff — не выбрать «правильное», а сделать компромисс осознанным, записанным и пересматриваемым.

```css
/* Каскадные слои — системный способ убрать войну специфичности:
   порядок слоёв важнее веса селектора внутри них */
@layer reset, base, tokens, components, utilities;

@layer components {
  .card { padding: var(--space-4); background: var(--color-surface); }
}

@layer utilities {
  /* утилита переопределит компонент без !important — просто потому, что слой ниже */
  .p-0 { padding: 0; }
}
```

### Определение стандартов, улучшение процесса и методологии

Стандарт живёт, только если он автоматически проверяем и у него есть владелец. Порядок внедрения, который работает: измерить проблему числом → пилот на одном продукте → автоматизация (токены, линтер, шаблон, проверка в CI) → миграция остальных кодмодами → отключение старого способа.

Что имеет смысл стандартизировать на уровне организации:

- **Дизайн-токены как единый источник истины.** Цвета, типографика, отступы, радиусы, тени, брейкпоинты выгружаются из дизайн-инструмента и генерируются в CSS-переменные — правки дизайна не требуют ручного переписывания стилей.
- **Методология именования и изоляции.** Один выбранный подход на организацию, а не по одному на команду.
- **Слои каскада и правила специфичности.** Явный порядок `@layer` и запрет `!important` вне утилит.
- **Требования к доступности.** Контраст, фокус-стили, семантика, поддержка клавиатуры — как обязательный критерий приёмки, а не пожелание.
- **Бюджеты производительности.** Размер CSS, число слоёв композитинга, пороги CLS и LCP в CI.
- **Поддерживаемая матрица браузеров.** Единый `browserslist` и политика прогрессивного улучшения.

```js
// stylelint.config.js — стандарт, который проверяется автоматически, а не «в ревью»
export default {
  extends: ['stylelint-config-standard-scss'],
  rules: {
    'declaration-property-value-disallowed-list': {
      // цвета и отступы — только из токенов
      '/color|background/': [/^#/, /^rgb/],
      '/^(margin|padding|gap)/': [/^\d+px$/],
    },
    'declaration-no-important': true,
    'max-nesting-depth': 2,
    'selector-max-specificity': '0,3,0',
  },
};
```

```yaml
# CI: доступность и бюджеты — часть определения готовности, а не отдельная активность
- run: npx stylelint "src/**/*.{css,scss,vue}"
- run: npx playwright test --grep @a11y      # axe-проверки в e2e
- run: npx size-limit                        # бюджет размера CSS/JS
```

Улучшение процесса — это и работа с людьми: живая документация с примерами вместо PDF-гайдлайна, общий стенд компонентов (Storybook/Histoire) как источник правды для дизайна и разработки, регулярный аудит расхождений макета и реализации, обучающие разборы вместо повторяющихся замечаний в код-ревью.

### Выход за рамки стандартных решений

Часть задач не закрывается существующими приёмами — тогда решение проектируется с нуля, с пониманием ограничений платформы и цены поддержки.

Типовые классы таких задач и подходы к ним:

- **Кастомные элементы управления со сложным поведением.** Виртуализированные таблицы с закреплёнными колонками, редакторы, конструкторы: слои с `contain`, ручной расчёт позиций, `content-visibility`, синхронизация прокрутки без реакции на каждый кадр.
- **Тонкая работа с рендерингом.** `contain: layout paint size` для изоляции подсистем, `content-visibility: auto` с `contain-intrinsic-size` для длинных страниц, точечное управление слоями композитинга.
- **Графика и эффекты, недоступные в CSS.** Canvas/WebGL/WebGPU для визуализаций, SVG-фильтры, генеративные фоны — с обязательным статическим фолбэком.
- **Новые возможности платформы под флагом прогрессивного улучшения.** Container queries, `:has()`, View Transitions, anchor positioning, scroll-driven animations: базовый сценарий работает везде, улучшение включается через `@supports`.
- **Собственный инструментарий.** Плагины PostCSS под правила проекта, генераторы токенов, кодмоды для массовых миграций стилей, скрипты аудита мёртвого CSS.

```css
/* Прогрессивное улучшение: сначала работающая база, затем современный слой */
.sidebar { display: block; }

@supports (container-type: inline-size) {
  .layout { container-type: inline-size; }
  @container (min-width: 40rem) {
    .sidebar { display: grid; grid-template-columns: 12rem 1fr; }
  }
}

@supports selector(:has(*)) {
  /* стиль родителя по состоянию потомка — без JS-классов */
  .field:has(input:invalid) { border-color: var(--color-danger); }
}
```

```js
// View Transitions с фолбэком: анимация — улучшение, а не условие работы навигации
function navigate(to) {
  if (!document.startViewTransition) return router.push(to);
  document.startViewTransition(() => router.push(to));
}
```

Критерий, отличающий обоснованный выход за рамки от изобретательства: у решения есть измеримая цель (метрика, которую оно улучшает), оценена стоимость поддержки, определён фолбэк для окружений без нужной возможности и записано условие, при котором от решения откажутся в пользу стандартного, когда платформа его догонит.
