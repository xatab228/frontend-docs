# Браузерные JS и API — Staff

### Внутренние механизмы браузера: Layout, Paint, Composite pipeline

Каждый кадр браузер проходит один и тот же конвейер, и цена изменения зависит от того, с какого этапа этот конвейер придётся перезапустить.

1. **JavaScript** — выполнение скриптов, изменение DOM и стилей.
2. **Style** — пересчёт применимых правил CSS для затронутых элементов.
3. **Layout (reflow)** — вычисление геометрии: размеры и позиции. Самый дорогой этап, затрагивает потомков, а часто и соседей.
4. **Paint** — растеризация: заливки, границы, тени, текст в слоях.
5. **Composite** — сборка слоёв в итоговое изображение, выполняется на GPU.

Разные свойства входят в конвейер на разной глубине:

| Что меняем | С какого этапа перезапуск | Цена |
|---|---|---|
| `width`, `height`, `top`, `font-size` | Layout → Paint → Composite | высокая |
| `background-color`, `box-shadow`, `border-radius` | Paint → Composite | средняя |
| `transform`, `opacity` (на своём слое) | только Composite | низкая |

Отсюда правила оптимизации конвейера: анимировать только `transform` и `opacity`, поднимать анимируемый элемент на отдельный слой через `will-change` (точечно — каждый слой стоит памяти GPU), избегать layout thrashing (чередования записи и чтения геометрии в одном цикле), батчить чтения и записи DOM, использовать `content-visibility: auto` для длинных страниц, чтобы браузер пропускал рендер невидимых секций.

```js
// Плохо: чтение после записи в цикле — принудительный синхронный layout на каждой итерации
items.forEach((el) => {
  el.style.width = '100px';
  console.log(el.offsetHeight);   // браузер вынужден пересчитать layout прямо сейчас
});

// Хорошо: сначала все чтения, потом все записи
const heights = items.map((el) => el.offsetHeight);
requestAnimationFrame(() => {
  items.forEach((el, i) => { el.style.transform = `translateY(${heights[i]}px)`; });
});
```

Диагностика ведётся в Chrome DevTools → Performance: фиолетовые полосы Layout/Recalculate Style в трейсе, вкладка Layers для проверки слоёв, счётчик Frames для поиска пропущенных кадров.

### Механизмы регидрации и гидрации в DOM

Гидрация — процесс, при котором клиентский фреймворк «оживляет» уже пришедшую с сервера разметку: строит своё внутреннее дерево, сопоставляет его с существующими узлами и навешивает обработчики, не пересоздавая DOM. Регидрация — повторное выполнение этого процесса для части дерева, например после замены данных или восстановления состояния.

Ключевые свойства и проблемы:

- **Соответствие разметки обязательно.** Любое расхождение серверного и клиентского рендера (случайные значения, `Date.now()`, чтение `localStorage` в рендере, вмешательство расширений браузера) приводит к mismatch и полной перерисовке поддерева — выигрыш SSR теряется.
- **Гидрация блокирует интерактивность.** Пока идёт обход дерева, страница выглядит готовой, но не отвечает — это прямой вклад в INP на первых секундах.
- **Стратегии снижения цены:** ленивая гидрация по появлению в вьюпорте или по первому взаимодействию, частичная гидрация («острова» интерактивности среди статики), потоковая гидрация по мере поступления HTML, серверные компоненты, часть которых вообще никогда не гидрируется.

Проектирование стратегии регидрации сводится к разметке дерева по приоритетам: критичный интерактив (навигация, форма первого экрана) гидрируется сразу, второстепенные виджеты (комментарии, рекомендации, аналитика) — отложенно, статические зоны — не гидрируются вовсе. Состояние, посчитанное на сервере, передаётся в сериализованном виде и экранируется, чтобы не превратиться в XSS-вектор.

### Event-driven архитектуру и её паттерны

Событийная архитектура заменяет прямые вызовы между модулями публикацией и подпиской на события: издатель не знает получателей, получатели не знают друг о друге.

Базовые паттерны:

- **Pub/Sub** — центральная шина, слушатели подписываются по типу события.
- **Event bus на нативных примитивах** — `EventTarget` и `CustomEvent` вместо самописного эмиттера.
- **Медиатор** — один координатор, который знает правила взаимодействия и переводит события в команды.
- **Event sourcing на клиенте** — состояние восстанавливается воспроизведением последовательности событий: даёт undo/redo и полную историю действий в редакторах.
- **Очередь с backpressure** — события копятся в буфере и обрабатываются пачками, если источник быстрее потребителя.

```ts
// Типизированная шина поверх нативного EventTarget: без сторонних зависимостей
type AppEvents = {
  'order:created': { id: string; total: number };
  'cart:cleared': void;
};

class TypedBus extends EventTarget {
  emit<K extends keyof AppEvents>(type: K, detail: AppEvents[K]) {
    this.dispatchEvent(new CustomEvent(type as string, { detail }));
  }
  on<K extends keyof AppEvents>(type: K, cb: (detail: AppEvents[K]) => void) {
    const handler = (e: Event) => cb((e as CustomEvent).detail);
    this.addEventListener(type as string, handler);
    return () => this.removeEventListener(type as string, handler); // отписка — часть контракта
  }
}
```

Границы применимости: событийная модель снижает связность, но усложняет отслеживание причинно-следственных связей. На уровне архитектуры её удерживают в рамках правилами — события именуются как факты в прошедшем времени (`order:created`, а не `createOrder`), полезная нагрузка неизменяема, обработчик не порождает цепочку из десятка следующих событий, а для отладки есть централизованное логирование всех событий в dev-режиме.

### Passive listeners и их влияние на производительность при скроллинге

Обработчик `touchstart`/`touchmove`/`wheel` может вызвать `preventDefault()` и отменить прокрутку. Браузер не знает заранее, вызовет он его или нет, поэтому вынужден дождаться завершения обработчика, прежде чем скроллить — отсюда «залипание» прокрутки на мобильных устройствах.

Флаг `passive: true` — обещание браузеру, что `preventDefault()` вызван не будет: прокрутка идёт немедленно, параллельно с выполнением обработчика.

```js
// Прокрутка не ждёт обработчик
window.addEventListener('scroll', onScroll, { passive: true });
el.addEventListener('touchmove', onTouchMove, { passive: true });

// Если preventDefault действительно нужен (например, кастомный жест) — passive указывать нельзя
el.addEventListener('touchmove', (e) => { if (isDragging) e.preventDefault(); }, { passive: false });
```

Дополнительно к самому флагу: тяжёлую работу из обработчика скролла выносят в `requestAnimationFrame` с флагом «уже запланировано», состояние видимости элементов считают через `IntersectionObserver`, а не по координатам на каждый пиксель прокрутки, и по возможности заменяют скролл-обработчики CSS-механизмами (`position: sticky`, scroll-driven animations).

### Архитектурные паттерны offline-first решений

Offline-first означает, что источником истины для UI является локальное хранилище, а сеть — механизм синхронизации, а не условие работы приложения.

Слои такого приложения:

- **Локальное хранилище** — IndexedDB для структурированных данных, Cache API для ответов и статики, `localStorage` только для мелких флагов.
- **Очередь исходящих операций** — действия пользователя записываются локально и отправляются, когда сеть доступна (Background Sync или собственный планировщик с повторами).
- **Service Worker** — сетевой посредник со стратегиями: cache-first для статики, stale-while-revalidate для полустатичных данных, network-first с фолбэком для критичных запросов.
- **Разрешение конфликтов** — стратегия задаётся заранее: last-write-wins по метке времени, версионирование записей, слияние по полям или CRDT для совместного редактирования.
- **Обратная связь в UI** — состояние записи (локально / отправляется / подтверждено / конфликт) видно пользователю, иначе offline-режим воспринимается как потеря данных.

```js
// Очередь операций: пользователь работает, отправка происходит при появлении сети
async function enqueue(op) {
  await idb.add('outbox', { ...op, id: crypto.randomUUID(), createdAt: Date.now() });
  if (navigator.onLine) void flush();
}

async function flush() {
  for (const op of await idb.getAll('outbox')) {
    try {
      // ключ идемпотентности защищает от дублей при повторной отправке
      await api.send(op, { headers: { 'Idempotency-Key': op.id } });
      await idb.delete('outbox', op.id);
    } catch (e) {
      if (isNetworkError(e)) return;      // ждём следующего окна связи
      await idb.put('failed', { ...op, error: String(e) });
      await idb.delete('outbox', op.id);
    }
  }
}
window.addEventListener('online', flush);
```

### Подходы к миграции данных и обеспечению backward compatibility

Локальные данные живут дольше кода: у пользователя может быть открыт старый таб, закешированный Service Worker и база, созданная полгода назад. Поэтому схема локального хранилища версионируется так же, как схема БД на сервере.

- **Версия схемы и миграции.** В IndexedDB для этого есть событие `upgradeneeded` с номерами версий; миграции пишутся последовательно и накатываются по цепочке.
- **Толерантное чтение.** Код читает данные защищённо: неизвестные поля игнорируются, отсутствующие получают значения по умолчанию.
- **Совместимость в обе стороны.** Новая версия должна пережить данные старой, а старая (в другом табе) — не сломаться о новые записи.
- **Аварийный сброс.** Если миграция невозможна, данные удаляются с явным уведомлением пользователя, а не оставляют приложение в нерабочем состоянии.

```js
const req = indexedDB.open('app', 3);
req.onupgradeneeded = (e) => {
  const db = e.target.result;
  const from = e.oldVersion;              // накатываем последовательно, без пропусков
  if (from < 1) db.createObjectStore('orders', { keyPath: 'id' });
  if (from < 2) db.createObjectStore('outbox', { keyPath: 'id' });
  if (from < 3) {
    const store = e.target.transaction.objectStore('orders');
    store.createIndex('byStatus', 'status');
  }
};
```

Тот же принцип версионирования применяется к кешу Service Worker (имя кеша содержит версию, старые кеши удаляются в `activate`) и к сериализованному состоянию, которое приложение сохраняет между сессиями.

### Полифиллы и fallback-стратегии для поддержки старых браузеров

Полифилл реализует отсутствующий API средствами языка; fallback — альтернативный сценарий, когда полноценная реализация невозможна или слишком дорога.

Стратегии подключения:

- **Feature detection вместо определения браузера.** Проверяется наличие возможности, а не строка `userAgent`.
- **Условная загрузка.** Полифилл догружается динамическим `import()` только там, где он нужен, и не попадает в бандл современных браузеров.
- **Differential serving.** Два бандла: современный через `type="module"`, legacy через `nomodule`.
- **Progressive enhancement.** Базовый сценарий работает без продвинутого API, а тот лишь улучшает опыт: без `IntersectionObserver` изображения просто грузятся сразу, без `View Transitions` переход происходит мгновенно.

```js
// Условная загрузка полифилла + честный фолбэк, если API нет и полифилл не нужен
if (!('IntersectionObserver' in window)) {
  await import('intersection-observer');
}

// Написание собственного полифилла: не переопределяем существующую реализацию
if (!Array.prototype.at) {
  Object.defineProperty(Array.prototype, 'at', {
    value(n) {
      const i = Math.trunc(n) || 0;
      return this[i < 0 ? this.length + i : i];
    },
    writable: true, configurable: true, enumerable: false, // как у нативных методов
  });
}
```

Цена полифиллов измеряется: каждый добавленный `core-js`-модуль увеличивает бандл для всех пользователей, если подключён безусловно. Решение о поддержке конкретного браузера принимается по данным аналитики (доля трафика и выручки), а не по умолчанию.

### Ограничения и особенности различных браузерных API

Часть проблем совместимости не решается полифиллами, потому что упирается в политику браузера, а не в отсутствие функции:

- **Хранилища.** В приватном режиме и при жёстких настройках приватности квота урезана или запись бросает исключение; Safari удаляет данные сайтов, которыми не пользовались 7 дней. Любая запись в хранилище оборачивается в `try/catch` с деградацией в память.
- **Автовоспроизведение и звук.** Воспроизведение со звуком требует пользовательского жеста; `AudioContext` создаётся в состоянии `suspended`.
- **Разрешения.** Геолокация, уведомления, камера доступны только по HTTPS и после явного согласия; запрос без контекста часто получает отказ навсегда.
- **Кросс-доменные ограничения.** Сторонние cookie блокируются, `SharedArrayBuffer` требует заголовков COOP/COEP, доступ к буферу обмена — жеста и фокуса.
- **Фоновые задачи.** Таймеры в скрытых вкладках троттлятся, вкладка может быть выгружена из памяти; надёжнее опираться на `visibilitychange` и `pagehide`, а не на `beforeunload`.
- **Различия движков.** Safari/WebKit отстаёт по части Web API и имеет собственные ограничения на Service Worker и Push; iOS-браузеры используют WebKit независимо от названия.

Диагностика комплексных проблем совместимости строится на воспроизведении в реальном окружении (устройство или облачная ферма), сравнении поведения между движками, изоляции минимального примера и проверке спецификации — иногда «баг» оказывается корректным поведением по стандарту, а неверным было предположение.

### Intersection Observer API для реализации lazy loading

`IntersectionObserver` асинхронно сообщает о пересечении элемента с вьюпортом или заданным контейнером, не заставляя читать геометрию на каждый кадр прокрутки.

```js
// Универсальный ленивый загрузчик: изображения, виджеты, подгрузка следующей страницы
const io = new IntersectionObserver(
  (entries) => {
    for (const entry of entries) {
      if (!entry.isIntersecting) continue;
      const el = entry.target;
      if (el.dataset.src) el.src = el.dataset.src;      // изображение
      el.dispatchEvent(new CustomEvent('lazy:visible')); // виджет/подгрузка
      io.unobserve(el);                                  // одноразовое срабатывание
    }
  },
  {
    root: null,
    rootMargin: '200px 0px',   // начинаем грузить заранее, до появления в кадре
    threshold: 0,
  }
);
document.querySelectorAll('[data-src], [data-lazy]').forEach((el) => io.observe(el));
```

Практические детали: нативный `loading="lazy"` закрывает простой случай с изображениями и не требует JS; `rootMargin` подбирается по скорости прокрутки, чтобы контент успевал загрузиться; для бесконечных списков наблюдают за элементом-сентинелом в конце, а не за каждой строкой; observer обязательно отключается (`disconnect`) при размонтировании, иначе удерживает узлы в памяти.

### File API для работы с файловой системой

Набор API для работы с файлами включает несколько уровней: `input[type=file]` и drag-and-drop для получения `File`, `FileReader`/`Blob` для чтения, File System Access API для полноценной работы с файлами и каталогами, OPFS (Origin Private File System) для быстрого приватного хранилища.

```js
// Выбор каталога и обход дерева — основа файлового менеджера в браузере
const dirHandle = await window.showDirectoryPicker({ mode: 'readwrite' });

async function* walk(handle, path = '') {
  for await (const [name, entry] of handle.entries()) {
    const full = `${path}/${name}`;
    if (entry.kind === 'file') yield { entry, path: full };
    else yield* walk(entry, full);          // рекурсивный обход подкаталогов
  }
}

// Потоковая запись большого файла без загрузки в память целиком
const fileHandle = await dirHandle.getFileHandle('report.csv', { create: true });
const writable = await fileHandle.createWritable();
await rowsStream.pipeTo(writable);
```

Ограничения, которые определяют архитектуру такого приложения: File System Access доступен не во всех браузерах (для Safari/Firefox нужен фолбэк на скачивание и `input`), доступ выдаётся только после жеста пользователя и может быть отозван, разрешения не переживают перезагрузку без явного повторного подтверждения, а большие файлы читаются потоками (`stream()`, `slice()`), иначе вкладка падает по памяти.

### Современные Web API и их интеграцию в сложные системы

Отдельные API редко используются изолированно — ценность появляется на стыке. Типичный пример интеграции: коллаборативный редактор, который работает офлайн.

| Задача | API |
|---|---|
| Хранение документа и очереди операций | IndexedDB, OPFS |
| Работа без сети и фоновая отправка | Service Worker, Background Sync |
| Синхронизация между вкладками | BroadcastChannel, Web Locks |
| Тяжёлые вычисления и слияние изменений | Web Workers, WASM |
| Реалтайм-канал | WebSocket, WebTransport |
| Отзывчивость интерфейса | `requestIdleCallback`, `scheduler.postTask`, IntersectionObserver |
| Наблюдаемость | Performance API, `PerformanceObserver`, `reportError` |

Принципы, которые удерживают такую систему от превращения в клубок: каждый API прячется за собственным адаптером с фолбэком (приложение зависит от интерфейса «хранилище», а не от IndexedDB напрямую), доступность возможности проверяется на старте и фиксируется в матрице фич, у каждого фонового процесса есть владелец и явное завершение, а любые межслойные взаимодействия идут через одну событийную шину, чтобы поток данных оставался отслеживаемым.

### Оптимизация использования ресурсов браузера на системном уровне

Ресурсы, за которые конкурируют части приложения: главный поток, память, сеть, GPU и батарея. Системная оптимизация — это распределение бюджета между ними, а не ускорение отдельной функции.

- **Главный поток.** Задачи длиннее 50 мс разбиваются (`scheduler.yield()`, `postTask` с приоритетами, разбиение циклов), фоновые вычисления уходят в Worker.
- **Память.** Виртуализация длинных списков, освобождение крупных буферов, `WeakRef`/`FinalizationRegistry` для кешей, регулярная проверка снимков кучи на утечки.
- **Сеть.** Приоритеты загрузки (`fetchpriority`, `preload`, `preconnect`), дедупликация запросов, отмена неактуальных через `AbortController`, ограничение параллелизма.
- **GPU.** Контроль числа композитных слоёв, отказ от анимаций свойств, вызывающих layout, ограничение размеров canvas.
- **Энергопотребление.** Остановка таймеров, анимаций и опроса при `document.hidden`, отказ от поллинга в пользу серверных событий.

```js
// Разбиение длинной задачи, чтобы не блокировать ввод пользователя
async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    process(items[i]);
    if (i % 100 === 0) await scheduler.yield?.() ?? new Promise((r) => setTimeout(r, 0));
  }
}

// Остановка фоновой активности в скрытой вкладке
document.addEventListener('visibilitychange', () => {
  document.hidden ? stopPolling() : startPolling();
});
```
