# Сборка и организация кода — Staff

### Принципы работы с плагинами и хуками на уровне исходного кода сборщиков

Сборщик — это конвейер с точками расширения. Понимание порядка хуков позволяет писать плагины, которые не ломают кеш и работают предсказуемо в watch-режиме.

**Rollup / Vite** — плагин это объект с хуками двух фаз:

| Фаза | Хук | Назначение |
|---|---|---|
| Build | `options`, `buildStart` | подготовка, валидация конфигурации |
| Build | `resolveId` | разрешение импорта в путь или виртуальный модуль |
| Build | `load` | выдача содержимого модуля (в том числе синтетического) |
| Build | `transform` | преобразование кода модуля, возврат кода и source map |
| Output | `renderChunk` | правка готового чанка перед записью |
| Output | `generateBundle`, `writeBundle` | добавление файлов, манифесты, отчёты |

Vite добавляет собственные хуки: `config`/`configResolved` (правка конфигурации), `configureServer` (middleware dev-сервера), `transformIndexHtml`, `handleHotUpdate` (контроль HMR), а также поле `enforce: 'pre' | 'post'` и `apply: 'build' | 'serve'` для порядка и области применения.

**Webpack** устроен иначе — через tapable-хуки компилятора и компиляции:

```js
class BuildManifestPlugin {
  apply(compiler) {
    compiler.hooks.thisCompilation.tap('BuildManifest', (compilation) => {
      compilation.hooks.processAssets.tap(
        { name: 'BuildManifest', stage: compilation.PROCESS_ASSETS_STAGE_REPORT },
        (assets) => {
          const manifest = Object.keys(assets).reduce((acc, name) => {
            acc[name] = assets[name].size();
            return acc;
          }, {});
          compilation.emitAsset('build-manifest.json', new compiler.webpack.sources.RawSource(
            JSON.stringify(manifest, null, 2)
          ));
        }
      );
    });
  }
}
```

Правила, отличающие рабочий плагин от источника проблем: не мутировать общее состояние между сборками, возвращать корректные source maps из `transform`, объявлять зависимости (`this.addWatchFile`) для watch-режима, помечать виртуальные модули префиксом `\0`, кешировать дорогие операции по содержимому файла.

### Как создавать собственные плагины и лоадеры для решения уникальных задач проекта

Собственный плагин пишется, когда задача специфична для проекта: свой формат файлов, кодогенерация из схемы, инъекция метаданных сборки, проверки, которые нельзя выразить линтером.

```js
// Vite-плагин: превращает *.api.yaml в типизированный клиент на этапе сборки
export function apiClientPlugin() {
  const VIRTUAL = '\0virtual:api-client';
  return {
    name: 'api-client',
    enforce: 'pre',
    resolveId(id) {
      if (id === 'virtual:api-client') return VIRTUAL;
    },
    async load(id) {
      if (id !== VIRTUAL) return;
      const schema = await readSchema('src/api/openapi.yaml');
      this.addWatchFile('src/api/openapi.yaml');  // пересборка при изменении схемы
      return generateClient(schema);              // возвращаем сгенерированный модуль
    },
  };
}
```

```js
// Webpack-лоадер: цепочка обработки одного файла, снизу вверх
// webpack.config.js → use: ['style-loader', 'css-loader', 'svg-icon-loader']
module.exports = function svgIconLoader(source) {
  const callback = this.async();
  this.cacheable?.(true);                        // результат зависит только от входа
  optimizeSvg(source)
    .then((optimized) => callback(null, `export default ${JSON.stringify(optimized)}`))
    .catch(callback);
};
```

Перед написанием плагина стоит убедиться, что задача не решается конфигурацией или существующим пакетом: собственный плагин становится частью инфраструктуры, которую придётся сопровождать при каждом мажорном обновлении сборщика.

### Как оптимизировать сборку для масштабируемых приложений

В больших репозиториях узкое место — не размер бандла, а время обратной связи: пересборка, тесты, CI.

- **Кеширование на всех уровнях.** Persistent cache Webpack (`cache: { type: 'filesystem' }`), кеш зависимостей Vite, удалённый кеш задач в Nx/Turborepo, кеш слоёв Docker в CI.
- **Инкрементальность.** Пересобирается и тестируется только затронутый граф проектов (`nx affected`, `turbo run build --filter=...[origin/main]`).
- **Параллелизм.** Параллельные задачи по числу ядер, вынос типов и линтинга в отдельные процессы (`vue-tsc`/`tsc --build` вместо проверки типов внутри бандлинга).
- **Дешевле инструмент на горячем пути.** esbuild/SWC для транспиляции в dev, полноценные трансформации только в production-сборке.
- **Контроль графа.** Ограничение глубины barrel-файлов, отказ от импорта пакета целиком, `exports` вместо произвольных путей — всё это уменьшает объём разбираемых модулей.
- **Измерение.** `--profile`, `speed-measure-webpack-plugin`, `vite build --profile`: оптимизировать нужно ту стадию, которая действительно занимает время.

```js
// Webpack: кеш и явные границы графа — самый заметный выигрыш в монорепозитории
module.exports = {
  cache: { type: 'filesystem', buildDependencies: { config: [__filename] } },
  resolve: { symlinks: false },
  module: { rules: [{ test: /\.[jt]sx?$/, exclude: /node_modules/, use: 'swc-loader' }] },
  experiments: { lazyCompilation: true },  // dev: компилируем только открытые маршруты
};
```

### Глубокое понимание внутренней архитектуры Module Federation (например, как работают remote containers и shared dependencies)

Module Federation превращает бандл в контейнер, который умеет отдавать свои модули другим приложениям и потреблять чужие в рантайме.

Механика:

1. **Container.** Хост загружает `remoteEntry.js` ремоута — это точка входа контейнера с двумя методами: `init(sharedScope)` и `get(moduleName)`.
2. **Shared scope.** Хост создаёт общий реестр разделяемых зависимостей: имя пакета → доступные версии и фабрики загрузки.
3. **Инициализация.** Хост вызывает `init` контейнера, передавая общий scope; контейнер регистрирует туда свои версии и видит чужие.
4. **Разрешение версий.** При запросе зависимости выбирается подходящая версия по `requiredVersion` и `singleton`; при несовместимости выводится предупреждение и берётся собственная копия (кроме `strictVersion`, где будет ошибка).
5. **Получение модуля.** `get('./Widget')` возвращает фабрику, вызов которой отдаёт сам модуль — асинхронно, поэтому точка входа хоста оборачивается в bootstrap-файл.

```js
// Хост и ремоут: контракт версий — самая важная часть конфигурации
new ModuleFederationPlugin({
  name: 'host',
  remotes: { checkout: 'checkout@https://cdn.example.com/checkout/remoteEntry.js' },
  shared: {
    vue: { singleton: true, requiredVersion: '^3.4.0', strictVersion: false },
    pinia: { singleton: true, requiredVersion: '^2.1.0' },
    lodash: { singleton: false },   // дубли допустимы, состояние не шарится
  },
});
```

```js
// index.js хоста: асинхронная граница обязательна
import('./bootstrap');
```

`singleton: true` нужен всем библиотекам с внутренним состоянием и контекстом (Vue, роутер, стейт-менеджер): две копии Vue на странице ломают `provide/inject`, devtools и реактивность между приложениями.

### Знание аналогов Webpack Module Federation, преимущества и недостатки каждого инструмента в зависимости от задачи

| Подход | Как устроен | Сильные стороны | Ограничения |
|---|---|---|---|
| Webpack Module Federation | контейнеры и shared scope на уровне сборщика | зрелость, разделение зависимостей, ленивая загрузка модулей | привязка к webpack, сложная отладка версий, общий рантайм |
| Native Federation / `@module-federation/vite` | тот же контракт поверх ESM и import maps | работает с Vite/Rollup, ближе к платформе | экосистема моложе, меньше готовых рецептов |
| Import maps + чистые ESM | браузер сам резолвит спецификаторы | без сборщика в рантайме, прозрачно | ручное управление версиями, слабее поддержка в старых браузерах |
| single-spa | оркестратор жизненного цикла приложений | фреймворк-агностичность, независимые релизы | не решает разделение зависимостей, свой рантайм-контракт |
| Web Components | изоляция через Custom Elements и Shadow DOM | сильная изоляция стилей, независимость от фреймворка | обмен состоянием через события, дублирование рантаймов |
| iframe | полная изоляция контекста | максимальная безопасность и независимость | тяжело, проблемы с UX, навигацией и общим состоянием |
| Сборка на этапе CI (монорепозиторий) | «микрофронтенды» собираются вместе | простота, единые версии, отсутствие рантайм-рисков | нет независимого релиза, общая частота деплоя |

Выбор определяется главным требованием: независимый релиз команд — федерация или single-spa; изоляция и безопасность — Web Components или iframe; простота и предсказуемость — единая сборка из монорепозитория. Микрофронтенды оправданы организационно (много команд, разный цикл релиза), а не технически.

### Принципы работы с несколькими инструментами и подходами для микрофронтендов

На практике ландшафт редко однороден: часть приложений на федерации, часть подключается как веб-компонент, легаси живёт в iframe. Чтобы это оставалось управляемым, фиксируются общие правила платформы:

- **Единый контракт монтирования.** Каждое приложение экспортирует `mount(el, context)` и возвращает функцию размонтирования — независимо от способа доставки кода.
- **Контекст вместо глобалов.** Токен, локаль, тема, телеметрия передаются аргументом, а не читаются из `window`.
- **Изоляция стилей.** Префиксы классов или Shadow DOM, запрет глобальных сбросов стилей в ремоутах.
- **Матрица версий.** Общие библиотеки (фреймворк, дизайн-система) фиксируются на уровне платформы, обновление синхронизируется, а не оставляется на усмотрение команд.
- **Наблюдаемость.** Общая система трейсинга и ошибок с тегом приложения-владельца, иначе инцидент невозможно адресовать.
- **Деградация.** Падение ремоута не роняет хост: загрузка оборачивается в границу ошибок с фолбэком.

### Принципы работы полифиллов и их влияние на производительность бандла

Полифилл — не бесплатная совместимость: он попадает в бандл, выполняется на старте и иногда переопределяет прототипы, влияя на все библиотеки в приложении.

Способы подключения и их цена:

- **`useBuiltIns: 'usage'` в preset-env** — Babel анализирует код и добавляет только используемые модули `core-js`. Дёшево по размеру, но не видит зависимости из `node_modules`.
- **`useBuiltIns: 'entry'`** — разворачивает импорт `core-js` по целевым браузерам: предсказуемо, но тяжелее.
- **Точечный динамический импорт** — полифилл грузится только при отсутствии возможности: лучший вариант для больших API вроде `IntersectionObserver`.
- **Внешний сервис полифиллов** — отдаёт набор под конкретный `User-Agent`, но добавляет сторонний домен в критический путь загрузки.
- **`@babel/plugin-transform-runtime`** — для библиотек: хелперы выносятся в общий рантайм и не дублируются в каждом модуле, глобальные объекты не патчатся.

```js
// Точечная загрузка: современные браузеры не платят за legacy-поддержку
const polyfills = [];
if (!('IntersectionObserver' in window)) polyfills.push(import('intersection-observer'));
if (!Object.groupBy) polyfills.push(import('core-js/actual/object/group-by'));
await Promise.all(polyfills);
```

Правило для библиотек: полифиллы не включаются в поставку. Библиотека объявляет минимальные требования к окружению, а решение о полифиллах принимает приложение — иначе потребитель получает дубли и неожиданный патч глобальных прототипов.

### Принципы создания standalone-библиотек с поддержкой разных форматов (например, ESM + CommonJS)

Библиотека должна работать в трёх мирах: современные сборщики (ESM), Node.js (CJS и ESM), браузер без сборщика (IIFE/UMD через тег `<script>`).

```js
// vite.config.js — сборка библиотеки в нескольких форматах
export default defineConfig({
  build: {
    lib: {
      entry: 'src/index.ts',
      name: 'MyLib',                       // глобальная переменная для IIFE/UMD
      fileName: (format) => `my-lib.${format}.js`,
      formats: ['es', 'cjs', 'umd'],
    },
    rollupOptions: {
      external: ['vue'],                   // peer-зависимости не бандлим
      output: { globals: { vue: 'Vue' } }, // как их найти в UMD-сборке
    },
  },
});
```

```json
{
  "name": "my-lib",
  "type": "module",
  "sideEffects": false,
  "main": "./dist/my-lib.cjs.js",
  "module": "./dist/my-lib.es.js",
  "unpkg": "./dist/my-lib.umd.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/my-lib.es.js",
      "require": "./dist/my-lib.cjs.js"
    },
    "./styles.css": "./dist/style.css"
  },
  "peerDependencies": { "vue": "^3.4.0" }
}
```

```html
<!-- Использование без сборщика: UMD-сборка регистрирует глобальную переменную -->
<script src="https://unpkg.com/vue@3"></script>
<script src="https://unpkg.com/my-lib/dist/my-lib.umd.js"></script>
<script>MyLib.install(Vue);</script>
```

Типичные ошибки двойной поставки: расхождение ESM- и CJS-копий с внутренним состоянием (dual package hazard — состояние дублируется, `instanceof` перестаёт работать), отсутствие `types` в `exports` (TypeScript не находит типы при `moduleResolution: bundler`), забытый `sideEffects` (tree shaking не работает у потребителя). Поставка проверяется автоматически — `publint` и `arethetypeswrong` в CI, плюс smoke-тесты импорта из Node в обоих форматах.

### Интеграция Module Federation с SSR и SSG

При серверном рендеринге ремоут нужно загрузить и выполнить в Node, а затем корректно передать на клиент информацию о том, какие чанки уже использованы.

Что для этого требуется:

- **Серверная сборка ремоута.** Отдельный таргет с `library: { type: 'commonjs-module' }`, чтобы контейнер грузился в Node.
- **Загрузка контейнера на сервере.** `remoteEntry` для Node скачивается или читается с диска и инициализируется тем же shared scope, что и на клиенте.
- **Единые версии.** Разные версии фреймворка на сервере и клиенте гарантированно дают hydration mismatch.
- **Манифест ассетов.** Хост собирает список чанков, задействованных при серверном рендере, и вставляет для них `preload`, иначе гидрация задержится на догрузке ремоутов.
- **Фолбэк.** Недоступный ремоут не должен ронять страницу: серверный рендер отдаёт заглушку, клиент повторяет попытку.

Для SSG к этому добавляется вопрос момента актуальности: содержимое ремоута фиксируется на этапе генерации. Если ремоут обновится, предрендеренные страницы устареют — поэтому либо статически рендерятся только собственные части, либо генерация перезапускается по вебхуку от ремоута (инкрементальная регенерация).

### Решение проблем совместимости версий зависимостей между приложениями

Конфликты версий — главная эксплуатационная проблема федерации и монорепозиториев. Работает комбинация мер:

- **Единый источник версий.** Общие зависимости объявлены в корне монорепозитория, `pnpm` с `overrides`/`resolutions` не даёт разъехаться версиям.
- **Явные peer-зависимости.** Библиотеки не тянут фреймворк за собой, а требуют его от приложения.
- **Политика singleton.** Для всего, что хранит состояние или контекст, — только один экземпляр на страницу.
- **Проверка дублей в CI.** `pnpm dedupe --check`, анализ бандла на несколько версий одного пакета, размерный бюджет как сигнал о дублях.
- **Согласованное обновление.** Мажорные обновления общих библиотек проводятся платформенной командой сразу для всех потребителей с кодмодами, а не «когда дойдут руки».
- **Диагностика.** При несовместимости федерация выдаёт предупреждение в консоль — оно должно попадать в мониторинг, а не теряться.

### Поддержка старых проектов с AMD и SystemJS и миграция на современные стандарты

AMD (`define`/`require`, RequireJS) и SystemJS решали задачу модульности до появления ESM: асинхронная загрузка в браузере и динамический реестр модулей. Встречаются в проектах, которые старше стандартных модулей, а также как рантайм-загрузчик в некоторых микрофронтенд-решениях.

```js
// AMD-модуль: зависимости объявляются массивом, значение возвращается из фабрики
define(['jquery', './utils'], function ($, utils) {
  return { render: () => $('#root').html(utils.template()) };
});
```

Порядок миграции, который не требует остановки разработки:

1. **Инвентаризация.** Построить граф модулей и найти точки входа, циклические зависимости и обращения к глобальным переменным.
2. **Совместимость на время перехода.** Сборщик подключается поверх существующего кода: Webpack понимает AMD напрямую, для SystemJS есть плагины; новый код пишется сразу в ESM.
3. **Автоматическая конвертация.** Кодмоды переводят `define`/`require` в `import`/`export`, ручной правки требуют динамические `require` и условные зависимости.
4. **Замена рантайм-загрузки.** Динамический `require` заменяется на `import()`, реестр SystemJS — на статический граф сборки или import maps.
5. **Удаление совместимости.** Только после того, как последний AMD-модуль конвертирован, из сборки убирается legacy-режим, а из бандла — загрузчик.

Экономическое обоснование обязательно: миграция окупается ускорением сборки, tree shaking и возможностью нанимать людей без знания устаревшего стека. Если проект в режиме поддержки и скоро выводится из эксплуатации, разумнее заморозить его на текущем тулчейне и зафиксировать версии.
