# Архитектура Web приложений — Senior

### Признаки хорошей архитектуры (разделение ответственности, использование абстракций и пр.)

Хорошая архитектура характеризуется чётким разделением ответственности (каждый модуль решает одну задачу и имеет одну причину для изменения), низкой связанностью и высокой связностью (изменения локализованы), использованием абстракций и инверсии зависимостей (бизнес-логика не зависит от конкретной реализации API/БД, а зависит от интерфейса), явными границами между слоями (UI, бизнес-логика, доступ к данным), предсказуемым однонаправленным потоком данных и тестируемостью без сложных моков инфраструктуры. Дополнительный признак — архитектурные правила формализованы и проверяются автоматически, а не держатся на устной договорённости команды.

Практика — линтер архитектурных границ (`eslint-plugin-boundaries`), формализующий слои FSD и не дающий нарушить направление зависимостей:

```js
// .eslintrc.js
module.exports = {
  plugins: ['boundaries'],
  settings: {
    'boundaries/elements': [
      { type: 'app', pattern: 'src/app/*' },
      { type: 'pages', pattern: 'src/pages/*' },
      { type: 'widgets', pattern: 'src/widgets/*' },
      { type: 'features', pattern: 'src/features/*' },
      { type: 'entities', pattern: 'src/entities/*' },
      { type: 'shared', pattern: 'src/shared/*' },
    ],
  },
  rules: {
    'boundaries/element-types': ['error', {
      default: 'disallow',
      rules: [
        { from: 'pages', allow: ['widgets', 'features', 'entities', 'shared'] },
        { from: 'widgets', allow: ['features', 'entities', 'shared'] },
        { from: 'features', allow: ['entities', 'shared'] }, // features не импортирует features
        { from: 'entities', allow: ['shared'] },
      ],
    }],
  },
};
```

Пример инверсии зависимостей на уровне структуры (доменная модель зависит от интерфейса `OrderRepository`, а не от конкретной реализации):

```
src/
  entities/
    order/
      model/
        Order.ts          — доменная модель с инвариантами (DDD-стиль)
        OrderRepository.ts — интерфейс (инверсия зависимостей)
      api/
        RestOrderRepository.ts — реализация
```

### Недостатки FSD и атомарного дизайна

FSD: высокий порог входа для команды, оверинжиниринг для маленьких проектов, неочевидно "куда положить общую фичу" между двумя срезами, слабая формализация состояния и DI, методология не решает задачу бизнес-моделирования (DDD). Atomic Design: неоднозначность границ уровней (часто непонятно, атом это или молекула), игнорирует бизнес-логику и данные — это чисто UI-таксономия, плохо масштабируется на уровень целого приложения. Вывод: ни одна методология не покрывает всё в одиночку, на практике их комбинируют друг с другом и с DDD.

Практика комбинирования на уровне структуры (FSD снаружи + Atomic Design внутри `shared/ui` + элементы DDD внутри `entities`):

```
src/
  entities/
    order/
      model/
        Order.ts
        OrderRepository.ts
      api/
        RestOrderRepository.ts
      ui/
  shared/
    ui/  atoms/ molecules/ organisms/   — atomic design для UI-кита
```

```
UI-компонент → useOrders() (хук/use-case) → OrderRepository (интерфейс) → RestOrderRepository (реализация)
```

### Плюсы и минусы разных способов рендеринга

Спектр стратегий: CSR (рендер в браузере при каждом запросе — простая инфраструктура, но медленный первый рендер и слабое SEO без доп. усилий), SSR (рендер на сервере при каждом HTTP-запросе — быстрый FCP и хорошее SEO, но дороже в инфраструктуре и есть риск "uncanny valley" при тяжёлой гидратации), SSG (рендер один раз при сборке — максимальная скорость и дешевизна, но не подходит для часто меняющихся данных), ISR (SSG + периодическая пересборка — баланс между свежестью и скоростью) и Streaming SSR/RSC (потоковый рендер с частью компонентов только на сервере, снижает объём JS на клиенте). Критерий выбора: публичный контент с упором на SEO → SSG/ISR; персонализированный часто меняющийся контент → SSR; внутренние админки без SEO → CSR достаточно; крупные приложения → гибридная per-route стратегия.

Практика — гибридная per-route стратегия в одном Next.js-приложении:

```
app/
  (marketing)/
    page.tsx           → SSG (лендинг, редко меняется, важно SEO)
  blog/[slug]/
    page.tsx           → ISR, revalidate: 3600 (контент меняется, но не мгновенно)
  product/[id]/
    page.tsx           → SSR (цена/наличие должны быть актуальны + SEO)
  dashboard/
    page.tsx           → CSR, "use client" (внутренняя админка, SEO не нужен)
```

```tsx
// app/dashboard/page.tsx
'use client'; // явно выключает серверный рендеринг для этого поддерева
export default function Dashboard() {
  const { data } = useSWR('/api/stats', fetcher);
  return <StatsPanel data={data} />;
}
```

Один проект осознанно сочетает все четыре стратегии — под каждый маршрут выбрана та, что даёт нужный баланс SEO/perf/актуальности данных.

### Монолит vs микрофронтенды (плюсы и минусы)

Монолит: проще на старте, единая сборка и деплой, нет проблем с версионированием общих зависимостей, ниже эксплуатационная сложность — но с ростом команды растёт связанность, конфликты в кодовой базе и время сборки/тестирования, а деплой одной части блокируется готовностью другой. Микрофронтенды: независимая разработка, тестирование и деплой частей разными командами, изоляция отказов, свобода выбора технологий per-team — но выше сложность инфраструктуры (оркестрация, общий рантайм, версии shared-зависимостей), риск дублирования кода/UI-несогласованности, сложнее end-to-end тестирование и общее состояние между частями. Выбор в первую очередь организационный: микрофронтенды оправданы при реальной необходимости автономности нескольких команд, а не как техническая мода.

### Шаблоны микрофронтендов

Основные шаблоны интеграции: build-time (npm-пакеты, теряется независимость деплоя), server-side composition (SSI/edge, быстрый первый рендер, сложнее клиентский интерактив), iframe (максимальная изоляция, но проблемы с адаптивностью/роутингом/a11y), Module Federation (настоящая независимость деплоя, общий рантайм, но риск конфликта версий), Web Components (фреймворк-агностичность через Custom Elements/Shadow DOM), Single-SPA/qiankun (оркестрация жизненного цикла нескольких SPA).

Практика — Module Federation (Webpack 5), самый распространённый run-time подход:

```js
// apps/host/webpack.config.js
new ModuleFederationPlugin({
  name: 'host',
  remotes: {
    checkout: 'checkout@https://checkout.acme.com/remoteEntry.js',
    catalog: 'catalog@https://catalog.acme.com/remoteEntry.js',
  },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});

// apps/checkout/webpack.config.js
new ModuleFederationPlugin({
  name: 'checkout',
  filename: 'remoteEntry.js',
  exposes: { './CheckoutWidget': './src/CheckoutWidget' },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});
```

```jsx
// apps/host/src/App.jsx
const CheckoutWidget = React.lazy(() => import('checkout/CheckoutWidget'));

function App() {
  return (
    <ErrorBoundary fallback={<CheckoutFallback />}>
      <Suspense fallback={<Spinner />}>
        <CheckoutWidget />
      </Suspense>
    </ErrorBoundary>
  );
}
```

Каждая команда (checkout, catalog) деплоит свой `remoteEntry.js` независимо; хост подгружает актуальную версию в рантайме без пересборки — именно независимость деплоя, ради которой применяется этот подход.

### Двухстороннее связывание (MVVM)

MVVM (Model-View-ViewModel) — паттерн, где View автоматически синхронизируется с ViewModel в обе стороны: изменение данных в модели обновляет UI, а ввод пользователя в UI сразу обновляет модель без явного написания обработчиков синхронизации (в отличие от однонаправленного потока данных React/Redux). Плюсы: меньше шаблонного кода для форм, интуитивно для UI с большим количеством связанных полей ввода (Vue, Angular, Knockout). Минусы: сложнее отследить, откуда пришло изменение состояния при отладке, риск неявных побочных эффектов и каскадных обновлений, хуже предсказуемость в крупных приложениях по сравнению с однонаправленным потоком.

Пример двухстороннего связывания во Vue через `v-model`:

```vue
<template>
  <input v-model="username" />
  <p>Привет, {{ username }}!</p>
</template>

<script setup>
import { ref } from 'vue';
const username = ref(''); // изменение в input автоматически обновляет username и наоборот
</script>
```
