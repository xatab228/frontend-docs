# Архитектура Web-приложений — Staff

### Превышает ожидания по уровню и глубине знаний Senior-уровня

Отдельного перечня тем для Staff в матрице нет: предполагается свободное владение материалом Junior–Senior и работа на уровне ландшафта, а не отдельного приложения. Зона ответственности смещается с «спроектировать приложение» на «спроектировать то, как множество команд строят приложения»: границы систем, общие платформенные решения, стандарты и их эволюция.

Три ожидания из матрицы применительно к архитектуре фронтенда раскрываются ниже.

### Выявление системных взаимосвязей, компромиссов и первопричин проблем

Архитектурная проблема почти никогда не выглядит как архитектурная. Она приходит как жалоба на скорость разработки, количество багов или сроки.

| Симптом | Первопричина | Системное решение |
|---|---|---|
| «Каждая правка задевает пол-приложения» | нет границ модулей, связность по общему состоянию | слои и домены с проверяемыми правилами импорта |
| «Релиз одной команды блокирует остальные» | общий цикл релиза при независимых доменах | разделение деплоя, микрофронтенды или feature toggles |
| «Одинаковый код в пяти местах» | нет общей библиотеки и владельца | shared-пакет с версионированием и контрактом |
| «Никто не понимает, откуда берутся данные» | смешение серверного, доменного и UI-состояния | явное разделение слоёв состояния, кеш-слой для серверных данных |
| «Новый человек входит в проект месяц» | неявные соглашения, отсутствие карты системы | документированная структура, ADR, генераторы модулей |
| «Производительность падает от релиза к релизу» | нет владельца метрик и бюджетов | бюджеты в CI, RUM, регулярный аудит |
| «Легаси невозможно тронуть» | отсутствие тестов и швов для замены | strangler-подход, характеризующие тесты, антикоррупционный слой |

Метод поиска первопричины: смотреть на данные, а не на мнения — частота изменений файлов (hotspots в git), число задетых модулей на один PR, время прохождения задачи от старта до прода, распределение багов по областям, метрики производительности по маршрутам. Устойчивая корреляция «много правок + много багов + много задетых модулей» указывает на архитектурную проблему точнее, чем любые обсуждения.

Компромиссы, которые нужно держать явными, а не решать по умолчанию:

- **Связность против гибкости.** Общая библиотека убирает дублирование, но связывает релизы команд.
- **Независимость деплоя против сложности.** Микрофронтенды дают автономию ценой рантайм-рисков, дублей зависимостей и общей наблюдаемости.
- **SSR/SSG против CSR.** SEO и время первого экрана против стоимости инфраструктуры и сложности гидрации.
- **Строгость архитектуры против скорости.** Жёсткие правила ускоряют жизнь на дистанции и замедляют старт нового продукта.
- **Единая платформа против свободы команд.** Общий стек снижает стоимость поддержки и ограничивает локальную оптимальность.

Каждое такое решение фиксируется как ADR — с контекстом, рассмотренными альтернативами, последствиями и условием пересмотра. Без записанного контекста через год решение выглядит произволом, и его отменяют, повторяя ту же ошибку.

```md
# ADR-021: Микрофронтенды только для доменов с независимым релизом

## Статус
Принято, 2026-05

## Контекст
Три команды делят один монолитный SPA. Релиз общий, среднее время от готовности
фичи до прода — 6 дней, из них 4 — ожидание релизного окна.

## Решение
Выделяем в отдельные микрофронтенды только домены с собственным циклом релиза
(checkout, admin). Остальное остаётся в монолите. Общий фреймворк и дизайн-система —
singleton-зависимости, версии фиксирует платформенная команда.

## Последствия
+ Независимый деплой двух доменов, ожидание релиза сокращается до часов.
− Появляется рантайм-риск недоступности ремоута: нужен фолбэк и мониторинг.
− Требуется общая система трейсинга с тегом приложения.

## Условие пересмотра
Если через 2 квартала время до прода не сократилось, а инцидентов интеграции больше 2/мес —
возвращаемся к единой сборке.
```

### Определение стандартов, улучшение процесса и методологии

Архитектурный стандарт, который не проверяется автоматически, существует только в документе. Поэтому каждое правило превращается в механизм.

Что стандартизируется на уровне платформы:

- **Структура проекта и границы слоёв** — единая схема (FSD, домены, слоистая) с автоматической проверкой правил импорта.
- **Управление состоянием** — явное разделение серверного, доменного и UI-состояния и рекомендованный инструмент для каждого.
- **Стратегия рендеринга** — правила выбора CSR/SSR/SSG/ISR по типу страницы, а не по предпочтениям команды.
- **Контракты с бекендом** — генерация типов из спецификации, contract testing в CI.
- **Общие пакеты** — дизайн-система, утилиты, конфигурации сборки и линтеров с semver и changeset-ами.
- **Наблюдаемость по умолчанию** — трейсинг, ошибки и WebVitals включены в шаблон приложения, а не добавляются вручную.
- **Бюджеты и качественные ворота** — размер бандла, LCP/INP, покрытие критичных сценариев тестами.

```js
// Архитектурные правила как исполняемый код: нарушение падает в CI, а не обсуждается в ревью
// .dependency-cruiser.js
module.exports = {
  forbidden: [
    {
      name: 'shared-не-знает-о-features',
      severity: 'error',
      from: { path: '^src/shared' },
      to: { path: '^src/(features|widgets|pages)' },
    },
    {
      name: 'нет-циклов',
      severity: 'error',
      from: {},
      to: { circular: true },
    },
    {
      name: 'домены-изолированы',
      severity: 'error',
      from: { path: '^src/domains/([^/]+)' },
      to: { path: '^src/domains/(?!$1)([^/]+)/(?!index)' }, // только через публичный index
    },
  ],
};
```

```bash
# Генератор нового модуля: стандарт применяется по умолчанию, а не переписывается вручную
nx g @company/plugin:domain checkout --with-store --with-e2e
```

Улучшение процесса — отдельная часть роли: архитектурное ревью на входе крупных инициатив (а не постфактум), реестр ADR как общая память, регулярный аудит соответствия кода заявленной структуре, планы миграции с кодмодами вместо запретов, обучающие разборы вместо повторяющихся замечаний. Хороший признак зрелости — новый продукт стартует из шаблона и получает правильную архитектуру бесплатно.

### Выход за рамки стандартных решений

Задачи, где готовых рецептов нет, обычно возникают на стыке систем и при работе с унаследованным ландшафтом.

**Постепенная замена легаси (strangler fig).** Старое приложение не переписывается целиком: новый код перехватывает маршруты по одному, а слой совместимости изолирует старые контракты.

```js
// Прокси-слой маршрутизации: новые страницы уходят в новое приложение, остальное — в легаси
const MIGRATED = new Set(['/checkout', '/orders']);

export function routeRequest(path) {
  return MIGRATED.has(path) ? modernApp.handle(path) : legacyApp.handle(path);
}

// Антикоррупционный слой: новая модель не наследует уродства старого контракта
export function toDomainOrder(legacy) {
  return {
    id: String(legacy.ORDER_ID),
    total: Number(legacy.SUM_TOTAL) / 100,
    status: LEGACY_STATUS_MAP[legacy.ST] ?? 'unknown',
  };
}
```

**Собственные платформенные механизмы.** Когда готовые решения не подходят: собственный контракт монтирования микрофронтендов, слой синхронизации offline-first, кастомный SSR-pipeline с потоковой отдачей, плагин-архитектура для расширения продукта внешними командами, движок фичефлагов с постепенным раскатом и автооткатом по метрикам.

**Проектирование под неопределённость.** Архитектура на этом уровне оценивается не только по тому, как хорошо она решает текущую задачу, но и по стоимости изменения решения: где швы для замены, что можно выключить флагом, какой у решения путь отката, что произойдёт при пятикратном росте команды или трафика.

Критерий, отличающий обоснованное нестандартное решение от усложнения: сформулирована проблема с числом, рассмотрены и отвергнуты стандартные варианты с объяснением почему, оценена стоимость сопровождения, назначен владелец, определены метрика успеха и условие отката. Всё это записано — иначе решение невозможно ни защитить, ни пересмотреть.
