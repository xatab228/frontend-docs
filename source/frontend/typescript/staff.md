# TypeScript — Staff

### Превышает ожидания по уровню и глубине знаний Senior-уровня

Отдельного списка тем для Staff в матрице нет: предполагается свободное владение всем материалом Junior–Senior и работа на уровне системы типов всей организации — типизация как инструмент проектирования и контроля, а не как способ убрать красные подчёркивания в редакторе.

Три ожидания из матрицы применительно к TypeScript выглядят так: находить первопричины проблем типизации и производительности компилятора, задавать стандарты типизации для всех проектов, решать задачи, для которых готовых паттернов нет.

### Выявление системных взаимосвязей, компромиссов и первопричин проблем

Типичные жалобы команд почти всегда имеют системный источник:

| Симптом | Первопричина | Системное решение |
|---|---|---|
| «Везде `any`, типы не помогают» | `strict: false`, типы пишутся постфактум под готовый код | включение строгости по шагам, типы как часть проектирования API |
| «IDE тормозит, `tsc` идёт минуты» | взрывной рост условных и mapped-типов, гигантские union, barrel-файлы | `--generateTrace`, упрощение типов, project references |
| «Типы расходятся с реальными ответами API» | ручное дублирование контракта | кодогенерация из OpenAPI/GraphQL, валидация на границе |
| «После обновления библиотеки всё сломалось» | зависимость от внутренних типов пакета, отсутствие фиксации версий | опора только на публичные типы, `typesVersions`, тесты типов |
| «Рантайм падает там, где типы зелёные» | типы не проверяют внешние данные | схемы-валидаторы на границе, `unknown` вместо `any` |
| «Каждая команда пишет свои утилитарные типы» | нет общего пакета типов и владельца | общий `@company/types` с версионированием |

Ключевой компромисс, который приходится удерживать осознанно: строгость против скорости разработки. Максимально точный тип может быть нечитаемым, дорогим для компилятора и хрупким при рефакторинге. Практическое правило — сложность типа оправдана там, где он защищает публичный контракт (библиотека, API-клиент, дизайн-система), и почти никогда не оправдана внутри продуктовой фичи.

```bash
# Диагностика производительности компилятора — не догадки, а данные
tsc --noEmit --extendedDiagnostics          # где уходит время: check, parse, emit
tsc --noEmit --generateTrace ./trace        # трейс для анализа в perfetto
npx @typescript/analyze-trace ./trace       # топ самых дорогих типов и файлов
```

```ts
// Частая первопричина медленной проверки: рекурсивный тип без ограничения глубины
type DeepPartial<T> = { [K in keyof T]?: DeepPartial<T[K]> };   // на больших схемах взрывается

// Дешевле и достаточно в 95% случаев
type PartialBy<T, K extends keyof T> = Omit<T, K> & Partial<Pick<T, K>>;
```

### Определение стандартов, улучшение процесса и методологии

Стандарт типизации работает, только если он проверяется автоматически и имеет путь миграции.

Что стандартизируется на уровне организации:

- **Базовый `tsconfig`** как публикуемый пакет, от которого наследуются все проекты.
- **Политика `any`.** Запрет через линтер, `unknown` как замена, исключения — только с комментарием и сроком.
- **Границы доверия.** Любые внешние данные (сеть, хранилище, `postMessage`, переменные окружения) проходят через валидатор схемы, а не приводятся через `as`.
- **Общие типы и утилиты** в одном пакете вместо копий в каждом репозитории.
- **Кодогенерация контрактов** вместо ручных типов API.
- **Тесты типов** для публичных библиотек — так же обязательны, как unit-тесты.
- **Бюджет времени проверки типов** в CI как метрика здоровья репозитория.

```json
// @company/tsconfig-base/tsconfig.json — единый источник строгости
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "moduleResolution": "bundler",
    "skipLibCheck": true,
    "incremental": true
  }
}
```

```ts
// Тест типов: контракт библиотеки защищён так же, как поведение
import { expectTypeOf } from 'vitest';

expectTypeOf(createClient({ baseUrl: '' }).get<User>('/users/1'))
  .resolves.toEqualTypeOf<User>();

// @ts-expect-error — вызов без обязательного параметра обязан не компилироваться
createClient();
```

Миграция унаследованного кода на строгость делается по шагам, а не одним PR: включение флагов по одному, `strict` для новых файлов через отдельный конфиг, `ts-expect-error` с TODO-ссылкой вместо `any`, счётчик оставшихся нарушений в CI, который может только уменьшаться.

### Выход за рамки стандартных решений

Задачи, где не хватает стандартных приёмов, обычно связаны с типобезопасностью на границе систем и с автоматизацией.

**Сквозная типобезопасность от бекенда до компонента.** Типы не пишутся руками, а генерируются из единого контракта и проверяются в рантайме на входе:

```ts
// Схема — единственный источник истины: из неё выводится и тип, и рантайм-валидация
const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
  role: z.enum(['admin', 'user']),
});
type User = z.infer<typeof UserSchema>;

export async function fetchUser(id: number): Promise<User> {
  const raw: unknown = await http.get(`/users/${id}`);
  return UserSchema.parse(raw);   // граница доверия: дальше типам можно верить
}
```

**Типобезопасные DSL и API.** Шаблонные литеральные типы и `infer` позволяют проверять строки на этапе компиляции — маршруты, ключи переводов, имена событий:

```ts
// Параметры маршрута выводятся из самой строки пути
type PathParams<S extends string> =
  S extends `${string}:${infer P}/${infer Rest}` ? P | PathParams<Rest>
  : S extends `${string}:${infer P}` ? P
  : never;

function navigate<S extends string>(path: S, params: Record<PathParams<S>, string>) {}

navigate('/users/:id/orders/:orderId', { id: '1', orderId: '2' }); // ок
// navigate('/users/:id', {});                                     // ошибка компиляции
```

**Собственные инструменты на TypeScript Compiler API.** Когда нужен анализ или массовая правка кодовой базы — правило линтера, кодмод, генератор документации по типам, проверка архитектурных границ:

```ts
// Кодмод/анализатор поверх компилятора: работа с реальным AST и типами, а не с регулярками
import { Project } from 'ts-morph';

const project = new Project({ tsConfigFilePath: 'tsconfig.json' });
for (const file of project.getSourceFiles('src/**/*.ts')) {
  file.getDescendantsOfKind(SyntaxKind.AsExpression)
    .filter((node) => node.getType().isAny())
    .forEach((node) => report(file.getFilePath(), node.getStartLineNumber()));
}
```

**Расширение чужих типов.** Аугментация модулей и глобальных интерфейсов для плагинов и мета-фреймворков, декларации для нетипизированных библиотек, `declare module` для нестандартных импортов сборщика — с тем же требованием: изолировать в одном файле, покрыть тестом типов, зафиксировать версию исходной библиотеки.

Критерий обоснованности любого продвинутого решения на уровне Staff остаётся тем же: оно снимает конкретный класс ошибок или ручной работы, читается остальной командой (или спрятано за простым фасадом), не роняет скорость компилятора и имеет план отката, если платформа предложит штатный механизм.
