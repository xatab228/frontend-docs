# Безопасность — Middle

### Протоколы аутентификации (OAuth, JWT и базовая аутентификация)

Basic Authentication — простейшая схема, при которой логин и пароль передаются в заголовке `Authorization` в виде Base64 (не шифрование, а лишь кодирование, поэтому обязателен HTTPS) при каждом запросе; используется редко из-за отсутствия механизма выхода из сессии и рисков хранения пароля на клиенте. OAuth 2.0 — протокол авторизации (не аутентификации в чистом виде), позволяющий приложению получить ограниченный доступ к ресурсам пользователя от имени третьей стороны без передачи пароля, через обмен временными токенами доступа (access token). JWT (JSON Web Token) — самодостаточный токен, содержащий закодированные (не обязательно зашифрованные) данные о пользователе и подпись, позволяющую серверу проверить его подлинность без обращения к базе данных на каждый запрос. Фронтенд обычно работает именно с JWT-токенами, полученными по OAuth-флоу, храня их в памяти или `httpOnly`-cookie и добавляя в заголовок `Authorization: Bearer <token>`.

```js
// JWT состоит из трёх частей: header.payload.signature
// eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJyb2xlIjoidXNlciJ9.signature

function decodeJwtPayload(token) {
  const payload = token.split('.')[1];
  return JSON.parse(atob(payload)); // { sub: "123", role: "user", exp: 1234567890 }
}

// Отправка запроса с JWT
fetch('/api/profile', {
  headers: { Authorization: `Bearer ${localStorage.getItem('token')}` },
});
```

```
# Basic Auth — заголовок запроса
Authorization: Basic base64(login:password)
```

На практике интеграция OAuth 2.0 / OIDC на фронтенде обычно выполняется через готовую библиотеку, реализующую Authorization Code Flow с PKCE (рекомендованный поток для SPA), либо вручную через редиректы:

```js
// Пример с oidc-client-ts
import { UserManager } from 'oidc-client-ts';

const userManager = new UserManager({
  authority: 'https://idp.example.com',
  client_id: 'frontend-app',
  redirect_uri: 'https://app.example.com/callback',
  response_type: 'code', // Authorization Code Flow
  scope: 'openid profile email',
});

// Инициировать логин
async function login() {
  await userManager.signinRedirect(); // редирект на IdP
}

// На странице /callback после возврата с IdP
async function handleCallback() {
  const user = await userManager.signinRedirectCallback();
  localStorage.setItem('access_token', user.access_token); // используем полученный JWT
}
```

После получения токена он прикладывается ко всем запросам к защищённому API (см. заголовок `Authorization: Bearer` выше), а роли из токена используются для условного рендеринга UI, как показано в разделе про RBAC.

### Понятие и устройство SSO (Single Sign On) и многофакторной аутентификации

SSO (Single Sign On) — механизм, при котором пользователь один раз проходит аутентификацию в централизованном сервисе (Identity Provider — IdP, например Keycloak, Okta, Azure AD) и получает доступ ко всем связанным приложениям без повторного ввода логина/пароля. Обычно реализуется через протоколы SAML или OpenID Connect: при заходе в приложение (Service Provider) пользователя редиректят на IdP, тот проверяет сессию (или запрашивает логин) и возвращает подписанный токен/утверждение, которое приложение проверяет и создаёт свою локальную сессию. Многофакторная аутентификация (MFA) требует подтверждения личности минимум двумя независимыми факторами из категорий «что-то, что ты знаешь» (пароль), «что-то, что у тебя есть» (одноразовый код из приложения-аутентификатора, SMS) и «что-то, чем ты являешься» (биометрия) — это резко снижает риск компрометации аккаунта даже при утечке пароля.

```
Пользователь → Приложение А (redirect на IdP, если нет сессии)
             → IdP: логин + MFA-код из Google Authenticator
             → IdP выдаёт токен, редирект обратно в Приложение А
Пользователь → Приложение Б → уже залогинен (сессия IdP валидна) → доступ без повторного ввода
```

### Основные угрозы безопасности данных при их хранении и передаче и важность обеспечения конфиденциальности, целостности и доступности данных

Триада CIA (Confidentiality, Integrity, Availability) описывает три ключевых свойства защищённых данных: конфиденциальность — данные доступны только тем, кому положено (нарушается утечками, перехватом трафика); целостность — данные не были изменены неавторизованно в процессе хранения или передачи (нарушается MITM-атаками, подменой пакетов); доступность — данные и сервис доступны легитимным пользователям тогда, когда нужно (нарушается DDoS-атаками, отказами инфраструктуры). Типичные угрозы: перехват незашифрованного трафика (защита — HTTPS/TLS), утечка БД с паролями в открытом виде (защита — хеширование), XSS-атаки, ворующие токены из `localStorage`, MITM-атаки на публичных Wi-Fi. Для фронтенд-разработчика ключевой практический вывод — никогда не передавать чувствительные данные по HTTP и минимизировать хранение токенов в местах, доступных JavaScript (например, предпочитать `httpOnly` cookie вместо `localStorage`, так как последний читается любым выполнившимся на странице скриптом, в том числе внедрённым через XSS).

### Принципы управления ролями и правами в приложениях

Управление доступом на основе ролей (RBAC — Role-Based Access Control) — модель, при которой права выдаются не напрямую пользователям, а ролям (admin, editor, viewer), а пользователю назначается одна или несколько ролей. Это упрощает администрирование: изменение прав роли автоматически применяется ко всем пользователям с этой ролью. На фронтенде роли и права обычно приходят в payload JWT-токена или отдельным запросом после логина, и на их основе строится условный рендеринг UI-элементов и роутинг — при этом критично понимать, что скрытие кнопки на клиенте это лишь UX-удобство, а не защита: реальная проверка прав обязана происходить на сервере при каждом запросе.

```jsx
// React: условный рендеринг на основе роли — только UX, не security-барьер
function AdminPanelLink({ user }) {
  if (!user.roles.includes('admin')) return null;
  return <a href="/admin">Панель администратора</a>;
}

// Роутинг с защитой маршрута
function ProtectedRoute({ user, requiredRole, children }) {
  if (!user.roles.includes(requiredRole)) {
    return <Navigate to="/403" replace />;
  }
  return children;
}
```

### Как обезопасить данные при хранении и передаче (encryption at rest/in transit)

Encryption in transit — шифрование данных во время передачи по сети, реализуется через TLS/HTTPS: весь трафик между браузером и сервером шифруется, что защищает от перехвата (MITM). Encryption at rest — шифрование данных, хранящихся на диске (в базе данных, файловой системе, бэкапах), защищающее от утечки в случае физического доступа к носителю или компрометации сервера хранения; реализуется на уровне БД (например, transparent data encryption) или диска. Для фронтенда encryption in transit — прямая ответственность (обязательный HTTPS, `Strict-Transport-Security` заголовок), а encryption at rest относится к бэкенду, но важно понимать полную цепочку защиты данных пользователя от браузера до диска.

```
# HSTS-заголовок — принуждает браузер всегда использовать HTTPS для домена
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

### SHA (Secure Hash Algorithms), их основное назначение

SHA — семейство криптографических хеш-функций, преобразующих входные данные произвольной длины в хеш фиксированной длины таким образом, что вычисление обратного преобразования вычислительно неосуществимо, а малейшее изменение входных данных полностью меняет хеш (лавинный эффект). Основные применения: проверка целостности файлов (сравнение хеша скачанного файла с эталонным), электронная подпись (подписывается не сам документ, а его хеш), и как компонент в схемах хеширования паролей (хотя для паролей сам по себе быстрый SHA не рекомендуется — используют bcrypt/Argon2, которые внутри тоже опираются на криптографические примитивы, но специально замедлены).

```js
// Web Crypto API — доступен прямо в браузере
async function sha256(text) {
  const encoder = new TextEncoder();
  const data = encoder.encode(text);
  const hashBuffer = await crypto.subtle.digest('SHA-256', data);
  return Array.from(new Uint8Array(hashBuffer))
    .map((b) => b.toString(16).padStart(2, '0'))
    .join('');
}

await sha256('hello'); // "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824"
```

На практике SHA применяется, например, для проверки целостности загружаемого на клиенте файла (стороннего скрипта из CDN) через Subresource Integrity:

```html
<script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>
<!-- браузер вычислит SHA-384 файла и сравнит с integrity, откажется исполнять при несовпадении -->
```

Использование `crypto.subtle.digest` (см. пример SHA-256 выше) для проверки целостности данных на клиенте — например, сравнения хеша загруженного файла перед отправкой на сервер, чтобы избежать повторной загрузки неизменённого контента.

### Основы работы с сертификатами (SSL/TLS сертификаты)

SSL/TLS-сертификат — часть инфраструктуры открытых ключей (PKI): сервер владеет парой ключей (публичный и приватный), сертификат содержит публичный ключ и подписан удостоверяющим центром. При установлении TLS-соединения (TLS handshake) браузер получает сертификат сервера, проверяет его подпись по цепочке доверия, затем стороны согласуют симметричный сеансовый ключ (через асимметричное шифрование или обмен ключами Diffie-Hellman), которым дальше шифруется весь трафик — асимметричная криптография используется только на этапе установления соединения, так как она значительно медленнее симметричной. Для разработчика важно различать домены сертификата: single-domain, wildcard (`*.example.com`, покрывает все поддомены) и multi-domain (SAN-сертификаты).

```
TLS Handshake (упрощённо):
1. Client Hello (поддерживаемые версии TLS, шифры)
2. Server Hello + сертификат сервера
3. Клиент проверяет сертификат, генерирует pre-master secret, шифрует публичным ключом сервера
4. Обе стороны вычисляют общий симметричный ключ сессии
5. Дальнейший трафик шифруется симметрично (AES)
```

### Отличия и области применения симметричных (AES) и асимметричных (RSA) алгоритмов шифрования

Симметричное шифрование (AES) использует один и тот же ключ для шифрования и расшифровки — оно быстрое и эффективно для больших объёмов данных, но требует безопасного способа передачи ключа обеим сторонам заранее. Асимметричное шифрование (RSA) использует пару ключей — публичный (для шифрования) и приватный (для расшифровки), что решает проблему обмена ключом (публичный ключ можно передавать открыто), но работает значительно медленнее и не подходит для шифрования больших объёмов данных. На практике их комбинируют: асимметричное шифрование используется только для безопасного обмена симметричным ключом сессии (как в TLS handshake), после чего основной трафик шифруется быстрым симметричным алгоритмом.

```
AES (симметричный):  encrypt(data, key) → cipher    decrypt(cipher, key) → data
RSA (асимметричный):  encrypt(data, publicKey) → cipher    decrypt(cipher, privateKey) → data
```

### Защита сайта от основных видов атак (XSS, SQL-инъекции)

Защита от XSS на фронтенде строится на том, чтобы никогда не вставлять непроверенный пользовательский ввод в DOM как HTML — использовать безопасные API вместо `innerHTML`, а если разметка всё же нужна — санитизировать её.

```js
// Небезопасно: пользовательский ввод интерпретируется как HTML
element.innerHTML = userComment; // риск XSS, если userComment содержит <script>

// Безопасно: textContent не интерпретирует HTML
element.textContent = userComment;

// Если разметка действительно нужна — санитизация
import DOMPurify from 'dompurify';
element.innerHTML = DOMPurify.sanitize(userComment);
```

Дополнительный уровень защиты — Content-Security-Policy, ограничивающая источники исполняемых скриптов:

```
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'
```

SQL-инъекции — угроза бэкенда, но фронтенд обязан не полагаться на клиентскую валидацию как единственную защиту и никогда не формировать «сырой» SQL из пользовательского ввода, если часть логики (например, в BFF-слое на Node.js) всё же обращается к БД:

```js
// Небезопасно: конкатенация строки
db.query(`SELECT * FROM users WHERE email = '${email}'`); // риск SQL-инъекции

// Безопасно: параметризованный запрос
db.query('SELECT * FROM users WHERE email = $1', [email]);
```
