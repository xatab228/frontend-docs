# Безопасность — Junior

### Понятия аутентификации и авторизации, их различие

Аутентификация — процесс подтверждения того, что пользователь является тем, за кого себя выдаёт (обычно через логин/пароль, токен или биометрию). Авторизация — процесс определения того, какие действия и ресурсы доступны уже аутентифицированному пользователю. Проще говоря, аутентификация отвечает на вопрос «кто ты?», а авторизация — на вопрос «что тебе разрешено делать?». На фронтенде это выражается, например, в том, что после логина сервер выдаёт токен (аутентификация), а при попытке открыть страницу админки клиент или сервер проверяет права доступа на основе роли из этого токена (авторизация).

```js
// Псевдо-пример на клиенте
async function login(email, password) {
  const res = await fetch('/api/auth/login', {
    method: 'POST',
    body: JSON.stringify({ email, password }),
    headers: { 'Content-Type': 'application/json' },
  });
  const { token } = await res.json(); // аутентификация прошла — получили токен
  localStorage.setItem('token', token);
}

function canAccessAdminPanel(user) {
  return user.role === 'admin'; // авторизация — проверка прав
}
```

### Основные меры защиты данных при хранении (пароли в зашифрованном виде, хеширование и пр.)

Пароли и другие чувствительные данные никогда не хранятся в открытом виде — вместо шифрования (которое обратимо) для паролей применяется хеширование с солью через специализированные алгоритмы (bcrypt, scrypt, Argon2), которые намеренно медленные и защищены от атак перебором и rainbow-таблицами. Соль (случайная строка, добавляемая к паролю перед хешированием) гарантирует, что одинаковые пароли дают разные хеши, что защищает от предвычисленных таблиц. Помимо паролей, чувствительные данные (токены, персональные данные) шифруются at rest (на диске/в БД) с помощью симметричных алгоритмов вроде AES. Для фронтенд-разработчика важно понимать, что пароль никогда не должен передаваться и логироваться в открытом виде, а хеширование выполняется на сервере, а не на клиенте.

```js
// Пример на бэкенде (Node.js), для понимания процесса — фронтенд этим не занимается
const bcrypt = require('bcrypt');

async function registerUser(password) {
  const hash = await bcrypt.hash(password, 10); // 10 — cost factor (сложность)
  // hash сохраняется в БД, исходный пароль нигде не хранится
  return hash;
}

async function checkPassword(password, hash) {
  return bcrypt.compare(password, hash); // сравнение без расшифровки хеша
}
```

### Основы работы firewall, антивирусов и gateways, их назначение

Firewall (межсетевой экран) фильтрует сетевой трафик по правилам (IP, порты, протоколы), блокируя нежелательные подключения между сетями или к серверу. Антивирус сканирует файлы и процессы на устройстве на предмет известных сигнатур вредоносного кода и подозрительного поведения. API Gateway — компонент на границе системы, через который проходят все внешние запросы к бэкенду: он выполняет аутентификацию, ограничение частоты запросов (rate limiting), маршрутизацию к нужным микросервисам и может отсекать вредоносные запросы ещё до попадания в бизнес-логику. Для фронтенд-разработчика это в первую очередь означает, что API, к которому обращается клиентское приложение, часто «спрятано» за gateway, который может возвращать 429 (Too Many Requests) или 403 (Forbidden) при подозрительной активности.

```
Браузер → CDN/Firewall → API Gateway (auth, rate limit, routing) → Микросервисы
```

### Понятие сертификата и его назначение

Цифровой сертификат — электронный документ, подтверждающий принадлежность открытого ключа определённому владельцу (сайту, организации) и подписанный доверенным удостоверяющим центром (Certificate Authority). SSL/TLS-сертификат используется для установления защищённого HTTPS-соединения: он подтверждает подлинность сервера перед браузером и позволяет зашифровать трафик между клиентом и сервером. Браузер проверяет цепочку доверия сертификата (chain of trust) до корневого доверенного центра и предупреждает пользователя (замок с предупреждением, ошибка `NET::ERR_CERT_AUTHORITY_INVALID`), если сертификат просрочен, самоподписан или не соответствует домену.

```
Браузер → проверяет сертификат сайта →
  подписан промежуточным CA →
    подписан корневым CA, встроенным в доверенное хранилище браузера/ОС
```

### Принципы доступа к файлам и директориям

Доступ к файлам и директориям в операционных системах регулируется правами (permissions) для трёх категорий субъектов — владельца (owner), группы (group) и всех остальных (others) — с тремя типами прав: чтение (read), запись (write) и выполнение (execute). В контексте веб-разработки этот принцип проявляется, например, в правах на файлы деплоя (кто может изменять статику на сервере), в правах на `.env`-файлы с секретами (обычно только владелец процесса может их читать) и в политике CORS, которая на уровне браузера определяет, какие источники (origin) могут читать ответы от определённого сервера — концептуально похожий принцип «кто к чему имеет доступ».

```bash
# Пример прав доступа в Unix-подобной ОС
-rw-r----- 1 deploy deploy  .env      # владелец: чтение/запись, группа: чтение, остальные: нет доступа
chmod 640 .env
```

## Практика (УМЕЕТ)

### Настраивать базовые правила firewall и антивируса

Базовая настройка firewall сводится к разрешению только необходимых портов и протоколов и блокировке всего остального по умолчанию (принцип «запрещено всё, что явно не разрешено»). На уровне облачного хостинга фронтенд-приложения это чаще всего задаётся через security groups/файрвол-правила облачного провайдера, а не через ручную настройку ОС.

```bash
# Пример через ufw (Uncomplicated Firewall) на Linux-сервере, отдающем статику
ufw default deny incoming        # запретить всё входящее по умолчанию
ufw default allow outgoing       # разрешить весь исходящий трафик
ufw allow 22/tcp                 # разрешить SSH для администрирования
ufw allow 443/tcp                # разрешить HTTPS
ufw allow 80/tcp                 # разрешить HTTP (обычно для редиректа на HTTPS)
ufw enable
```

Антивирус на сервере (например, ClamAV) настраивается схожим образом — включается регулярное сканирование директорий с загружаемыми пользователями файлами:

```bash
clamscan -r /var/www/uploads --infected --remove   # рекурсивное сканирование и удаление заражённых файлов
```

### Устанавливать SSL-сертификаты вручную

Классический способ — получить бесплатный сертификат через Let's Encrypt с помощью Certbot и подключить его в конфигурации веб-сервера (Nginx), который отдаёт собранный фронтенд.

```bash
# Получение сертификата для домена
certbot certonly --nginx -d example.com -d www.example.com
```

```nginx
# nginx.conf
server {
  listen 443 ssl;
  server_name example.com;

  ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

  root /var/www/frontend/dist;
  index index.html;
}

server {
  listen 80;
  server_name example.com;
  return 301 https://$host$request_uri; # редирект с HTTP на HTTPS
}
```

После установки сертификат нужно периодически обновлять (Let's Encrypt выдаёт сертификаты на 90 дней) — обычно это автоматизируется через cron-задачу `certbot renew`, что демонстрирует полный жизненный цикл ручной установки и поддержки сертификата.
