# Безопасность — Staff

## Дополнительные OWASP риски (DDoS, broken auth, sensitive data exposure)

**DDoS (Distributed Denial of Service)** — множество источников одновременно направляют трафик на сервис, исчерпывая его ресурсы (полосу, число соединений, CPU). Защита многослойная: CDN с поглощением трафика на границе сети (Cloudflare, Akamai), rate limiting на API Gateway, WAF для отсечения аномального трафика по паттернам.

**Broken Authentication** — класс уязвимостей в логике аутентификации: слабая политика паролей, отсутствие защиты от брутфорса, предсказуемые или не инвалидируемые токены сессий, отсутствие ограничения времени жизни токена. Всё это позволяет обойти или скомпрометировать механизм входа в обход штатного флоу.

**Sensitive Data Exposure** — недостаточная защита чувствительных данных на любом этапе жизненного цикла: передача без TLS, хранение без шифрования, избыточные поля в ответах API (`password_hash`, случайно попавший в JSON), логирование PII в открытом виде в системах мониторинга.

```js
// Пример защиты от sensitive data exposure на уровне API-контракта
function toPublicUserDto(user) {
  const { passwordHash, internalNotes, ...publicFields } = user; // явный allowlist полей
  return publicFields; // никогда не полагаться на "просто не выводить" по памяти
}
```

## Лучшие практики безопасной разработки (безопасность по умолчанию, многослойная защита)

**Secure by default** — самая безопасная конфигурация является конфигурацией по умолчанию, а не опцией, которую нужно осознанно включить: cookie по умолчанию `httpOnly` и `Secure`, CORS по умолчанию запрещает все origin-ы, новые эндпоинты по умолчанию требуют аутентификации.

**Defense in depth** — ни один отдельный механизм не считается достаточным, выстраивается несколько независимых слоёв: WAF на границе → валидация входных данных на API Gateway → авторизация в бизнес-логике → параметризованные запросы на уровне БД → шифрование данных at rest. Компрометация одного слоя не приводит к провалу всей системы.

Дополняющие принципы:

- **Least Privilege** — каждый компонент и пользователь получает минимально необходимый набор прав.
- **Fail secure** — при сбое система переходит в состояние «доступ запрещён», а не «разрешён».
- **Разделение доверенных и недоверенных зон** — данным с клиента не доверяют никогда, даже если клиент — собственное SPA.

```text
Многослойная защита фронтенд-приложения:
CDN/WAF (фильтрация трафика)
  → CSP-заголовки (ограничение источников скриптов в браузере)
    → Валидация ввода на клиенте (UX, не security-барьер)
      → Валидация и авторизация на API Gateway/бэкенде (реальный барьер)
        → Параметризованные запросы к БД
          → Шифрование данных at rest
```

## Разрабатывать стратегии безопасности, основанные на результатах сканирования и анализе уязвимостей

Стратегия строится на регулярном цикле: автоматическое сканирование (SAST/DAST/dependency scanning из senior.md) → приоритизация находок по матрице риска (вероятность × ущерб, см. senior.md) → включение фиксов критичных уязвимостей в спринт вне очереди, менее критичных — в технический долг с дедлайном → повторное сканирование для верификации фикса. Например, по результатам DAST-сканирования, регулярно находящего один и тот же класс уязвимости (скажем, отсутствие rate limiting на эндпоинте логина), формулируется системная стратегия — не точечный фикс, а внедрение единого middleware rate-limiting на уровне API Gateway для всех auth-эндпоинтов сразу, чтобы закрыть класс проблемы, а не единичный инцидент.

```js
// Пример системного фикса на уровне gateway/middleware вместо точечного патча одного эндпоинта
const rateLimit = require('express-rate-limit');

const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5, // не более 5 попыток логина за 15 минут с одного IP
  standardHeaders: true,
  message: 'Слишком много попыток входа, попробуйте позже',
});

app.use('/api/auth/login', authLimiter);
app.use('/api/auth/reset-password', authLimiter);
```

## Проводить аудиты безопасности, разработки стратегий противодействия угрозам и рисков, основанных на OWASP

Аудит безопасности — систематическая проверка приложения на соответствие чек-листу OWASP Top 10 (и ASVS — Application Security Verification Standard для более глубокого уровня), включающая ревью кода на предмет доверия к клиентским данным, проверку конфигурации CORS/CSP/заголовков безопасности, проверку схемы хранения секретов, тестирование флоу аутентификации на broken auth. Threat modeling (моделирование угроз, например по методологии STRIDE — Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) применяется на этапе проектирования новых фич для заблаговременного выявления рисков до написания кода, а не постфактум.

```text
STRIDE-анализ для фичи "загрузка аватара пользователя":
Spoofing        — можно ли загрузить файл от имени другого пользователя? (проверка сессии)
Tampering       — можно ли подменить файл после загрузки? (проверка content-type на бэкенде, не доверять расширению)
Repudiation     — логируется ли, кто и когда загрузил файл?
Info disclosure — не раскрывает ли путь к файлу внутреннюю структуру сервера?
DoS             — есть ли лимит на размер/количество загружаемых файлов?
Elevation       — может ли загруженный файл (например, .svg с JS) исполниться как скрипт?
```

## Эффективно реагировать на инциденты и нарушения

Реагирование на инцидент безопасности строится по стандартному циклу: обнаружение (алерты мониторинга, отчёты пользователей) → сдерживание (containment — например, немедленная инвалидация всех активных сессий/токенов при подозрении на утечку, временное отключение скомпрометированного эндпоинта) → устранение первопричины → восстановление сервиса → post-mortem без поиска виноватых (blameless), с фиксацией таймлайна и конкретных action items. Для фронтенд-команды типичный сценарий — обнаружена XSS-уязвимость, уже эксплуатируемая в проде: немедленный хотфикс (санитизация уязвимого поля или временное отключение фичи), принудительная инвалидация JWT (например, через понижение версии токена, проверяемой на бэкенде) и, при подтверждённой утечке cookie, обязательное уведомление затронутых пользователей с требованием сменить пароль.

```js
// Пример принудительной инвалидации всех токенов, выпущенных до инцидента
function isTokenValid(payload) {
  const TOKEN_MIN_VALID_ISSUED_AT = 1735689600; // timestamp момента ротации после инцидента
  return payload.iat >= TOKEN_MIN_VALID_ISSUED_AT;
}
```
