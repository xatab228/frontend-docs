# Жизненный цикл разработки ПО — Junior

### Общее понимание методологий разработки (Waterfall, Agile, Incremental, Iterative и др.), их плюсы и минусы, области применения

**Waterfall (каскадная модель)** — последовательный процесс, где каждая фаза (анализ, дизайн, реализация, тестирование, внедрение) начинается после завершения предыдущей. Плюс — предсказуемость и понятная документация; минус — изменения после старта почти невозможны, а заказчик видит результат только в конце.

**Agile** — семейство итеративных подходов (Scrum, Kanban, XP): продукт разрабатывается короткими циклами с постоянной обратной связью. Плюс — гибкость и быстрая адаптация к изменениям требований; минус — сложнее точно спланировать сроки и бюджет на старте.

**Incremental** делит продукт на функциональные части, которые разрабатываются и поставляются последовательно: каждая добавляет новую возможность к уже работающей системе.

**Iterative** делает упор не на разбиение по функциям, а на повторяющиеся циклы уточнения всего продукта: на первой итерации получают грубый прототип, на каждой следующей его дорабатывают.

На практике для фронтенд-проектов с часто меняющимися требованиями почти всегда выбирают Agile; Waterfall уместен при жёстких контрактных требованиях и фиксированном скоупе — встраиваемые системы, регулируемые отрасли.

### Что такое Release, может назвать его этапы

Релиз — процесс подготовки и передачи новой версии приложения пользователям, включающий не только сборку, но и весь путь от готового кода до продакшена. Типичные этапы: заморозка кода (code freeze) — фиксация набора изменений, которые войдут в релиз; сборка (build) — компиляция и бандлинг приложения под продакшен-конфигурацию; тестирование — прогон regression- и smoke-тестов на собранном артефакте; деплой — выкладка на продакшен-окружение (или поэтапно через staging); мониторинг после релиза — отслеживание ошибок и метрик, чтобы вовремя заметить регрессии. Для фронтенда типичный релиз включает сборку через `npm run build`, публикацию статических файлов на CDN/сервер и инвалидацию кэша браузера через хэши в именах файлов.

### Что такое контроль версий и для чего он нужен

Контроль версий — система, которая фиксирует историю изменений файлов проекта во времени, позволяя увидеть, кто и когда что изменил, откатиться к любой предыдущей версии и работать над разными частями кода параллельно, не мешая друг другу. Без контроля версий разработчики были бы вынуждены вручную копировать файлы проекта (`project_v1`, `project_v2_final`) и терять историю изменений при совместной работе. Git — самая распространённая распределённая система контроля версий: каждый разработчик имеет полную копию истории репозитория локально, что даёт возможность работать оффлайн, быстро переключаться между ветками и не зависеть от постоянной связи с сервером.

### Базовые техники работы с Git (клонирование репозитория, добавление, коммит и пр.)

```bash
# Клонировать удалённый репозиторий локально
git clone https://github.com/company/frontend-app.git
cd frontend-app

# Посмотреть состояние рабочей директории
git status

# Добавить изменённые файлы в индекс (staging area)
git add src/components/Button.tsx
git add .   # добавить все изменённые файлы

# Зафиксировать изменения коммитом с сообщением
git commit -m "fix: исправлен цвет кнопки в тёмной теме"

# Посмотреть историю коммитов
git log --oneline

# Отправить локальные коммиты на удалённый репозиторий
git push origin main
```

Базовый цикл работы: изменить файлы → `git add` (переместить изменения в staging area) → `git commit` (зафиксировать снимок состояния с сообщением) → `git push` (отправить коммиты на сервер). Понимание трёх состояний файла в Git — рабочая директория (working directory), индекс (staging area) и репозиторий (committed) — база, без которой сложно осмысленно пользоваться остальными командами.

Подключение к git-серверу обычно настраивается через SSH-ключ (безопаснее и не требует ввода пароля при каждой операции) либо через HTTPS с токеном доступа.

```bash
# Генерация SSH-ключа (один раз на машине)
ssh-keygen -t ed25519 -C "developer@example.com"
# Публичный ключ (~/.ssh/id_ed25519.pub) добавляется в настройках GitHub/GitLab

# Клонирование по SSH
git clone git@github.com:company/frontend-app.git

# Клонирование по HTTPS
git clone https://github.com/company/frontend-app.git

# Проверка, что удалённый репозиторий подключён корректно
git remote -v
```

На практике на старте достаточно уметь вносить изменения, фиксировать их коммитами и синхронизироваться с сервером в рамках одной ветки (обычно `main` или личной feature-ветки, выданной тимлидом):

```bash
git pull origin main          # подтянуть последние изменения перед началом работы
# ... правим файлы в редакторе ...
git add src/utils/formatDate.ts
git commit -m "feat: добавлена утилита форматирования даты"
git push origin main           # отправить изменения на сервер
```

Важно перед началом работы всегда делать `git pull`, чтобы не создавать лишних конфликтов, и делать коммиты небольшими логическими порциями, а не одним огромным коммитом в конце дня.
