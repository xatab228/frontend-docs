# Жизненный цикл разработки ПО — Middle

## Подходы Agile-методологии (Scrum, Kanban), артефакты, особенности и различия

**Scrum** организует работу в фиксированные итерации (спринты, обычно 1–2 недели), в конце каждой команда поставляет инкремент продукта.

- *Артефакты*: Product Backlog (приоритизированный список задач продукта), Sprint Backlog (задачи текущего спринта), Increment (работающий прирост функциональности).
- *Роли*: Product Owner (бэклог и приоритеты), Scrum Master (процесс), Development Team.
- *События*: планирование спринта, ежедневный стендап, обзор спринта (Sprint Review), ретроспектива.

**Kanban** не использует фиксированные итерации: работа течёт непрерывным потоком через доску со столбцами (To Do → In Progress → Review → Done), а ограничение WIP на каждом столбце не даёт команде набирать слишком много задач одновременно.

Kanban лучше подходит командам с постоянным потоком некрупных задач (саппорт, багфиксы), Scrum — проектам с чёткими целями на спринт и предсказуемым ритмом поставки.

На практике работа в спринте начинается с выбора задачи из Sprint Backlog, перевода её в статус "In Progress" на доске, и завершается переводом в "Done" после код-ревью и мержа:

```text
Sprint Backlog (спринт #14, 2 недели):
  [ ] SCRUM-101: Форма регистрации — верстка       (In Progress)
  [ ] SCRUM-102: Интеграция API регистрации         (To Do)
  [x] SCRUM-98:  Фикс бага в хедере                 (Done)
```
На ежедневном стендапе разработчик кратко отвечает на три вопроса: что сделал вчера, что планирует сегодня, есть ли блокеры.

## Принципы декомпозиции задач и способы оценки трудозатрат

Декомпозиция — разбиение крупной задачи (эпика) на более мелкие, независимо оцениваемые и тестируемые части, каждая из которых по возможности приносит самостоятельную ценность (принцип INVEST: Independent, Negotiable, Valuable, Estimable, Small, Testable). Для фронтенда типичная декомпозиция фичи: верстка UI-компонентов → интеграция с API → обработка ошибок и edge cases → покрытие тестами → адаптивность/доступность. Способы оценки трудозатрат: Planning Poker (команда независимо оценивает задачу в story points, затем обсуждает расхождения), T-shirt sizing (грубая оценка размера S/M/L/XL для крупных эпиков на ранней стадии), декомпозиция до атомарных подзадач с оценкой в часах. Story points измеряют относительную сложность, а не время напрямую, что снижает давление "успеть к сроку" и фокусирует на сложности и рисках задачи.

Пример декомпозиции задачи "Добавить форму регистрации" на подзадачи с оценкой в story points:

```text
Эпик: Форма регистрации пользователя
  ├─ Верстка формы (поля, валидация на клиенте) — 3 SP
  ├─ Интеграция с API регистрации — 2 SP
  ├─ Обработка ошибок сервера (занятый email, слабый пароль) — 2 SP
  ├─ Юнит-тесты для валидации — 1 SP
  └─ Адаптивная вёрстка под мобильные устройства — 2 SP
```

## Типы релизов (major, minor, hotfix, feature, patch) и их особенности

Используя семантическое версионирование (`MAJOR.MINOR.PATCH`): major-релиз содержит несовместимые (breaking) изменения API или интерфейса; minor-релиз добавляет новую функциональность с сохранением обратной совместимости; patch-релиз содержит только исправления багов без нового функционала. Feature-релиз — поставка отдельной новой фичи, часто через feature flag, что позволяет включать её выборочно. Hotfix — экстренное исправление критического бага в продакшене в обход обычного цикла релизов, обычно ветвится напрямую от продакшен-ветки, минуя ветку разработки.

```bash
git checkout -b hotfix/critical-payment-bug main
# ... исправление ...
git commit -m "fix: устранена ошибка округления суммы платежа"
git checkout main
git merge --no-ff hotfix/critical-payment-bug
git tag v2.4.1
git push origin main --tags
```

## Принципы организации рабочего процесса (GitFlow, trunk-based), их особенности

GitFlow — модель с несколькими долгоживущими ветками: `main` (продакшен), `develop` (интеграция фич), а также временные `feature/*`, `release/*` и `hotfix/*` ветки. Подходит для проектов с плановыми релизами и поддержкой нескольких версий одновременно, но добавляет накладные расходы на слияния и медленнее доставляет изменения в продакшен. Trunk-based development — все разработчики коммитят напрямую (или через короткоживущие feature-ветки на 1-2 дня) в единую основную ветку (`trunk`/`main`), опираясь на feature flags для скрытия незавершённого функционала. Подходит для команд с continuous delivery и высокой частотой релизов, снижает "merge hell" за счёт коротких веток, но требует зрелой культуры тестирования и CI, так как код в `main` должен быть постоянно готов к деплою.

```text
GitFlow:              main ── develop ── feature/x ── (merge back) ── release/1.2 ── main
Trunk-based:           main ── (short feature branch, 1 day) ── main (за feature flag)
```

На практике участие разработчика в релизном процессе выглядит так: подготовка feature-ветки к слиянию в `develop` согласно GitFlow, соблюдение code freeze перед релизом и корректная работа с типами релизов из раздела выше:

```bash
git checkout develop
git pull origin develop
git checkout -b feature/registration-form
# ... разработка ...
git push origin feature/registration-form
# Создаётся Merge Request в develop, проходит ревью и CI, затем мержится
```

## Инструменты для управления проектами и репозиториями программного кода (GitLab, GitHub)

GitLab и GitHub — платформы для хостинга Git-репозиториев с дополнительными инструментами вокруг разработки: issue tracker для задач и багов, Merge/Pull Request для код-ревью перед слиянием изменений, встроенный CI/CD (GitLab CI, GitHub Actions), Wiki для документации, а также доски задач (Boards) для управления бэклогом в стиле Kanban/Scrum прямо рядом с кодом. Ключевое отличие от классических таск-трекеров (Jira) — тесная интеграция задач с кодом: коммит или MR можно напрямую связать с issue (`Closes #42`), а CI-пайплайн запускается автоматически на каждый push или MR.

Например, в GitLab/GitHub issue связывается с задачей и автоматически закрывается при мерже:

```bash
git commit -m "fix: исправлена валидация email

Closes #142"
```
После мержа MR, issue #142 автоматически переводится в статус Closed, а карточка на доске проекта перемещается в колонку Done.

## Применять основные команды и операции Git (clone, add, commit, branch, pull, push, reset и др.)

```bash
git clone git@github.com:company/app.git
git checkout -b feature/new-header      # создать и переключиться на новую ветку
git add src/components/Header.tsx
git commit -m "feat: новый дизайн хедера"
git pull --rebase origin main            # подтянуть изменения, применив свои коммиты поверх
git push origin feature/new-header

git reset --soft HEAD~1   # отменить последний коммит, оставив изменения в staging
git reset --hard HEAD~1   # полностью отменить последний коммит и изменения (осторожно!)
```

## Объединять ветви и разрешать конфликты при слиянии

```bash
git checkout main
git merge feature/registration-form
# Auto-merging src/App.tsx
# CONFLICT (content): Merge conflict in src/App.tsx
```
```tsx
// src/App.tsx — конфликтующий участок до разрешения
<<<<<<< HEAD
import { Header } from './components/Header';
=======
import { Header } from './components/NewHeader';
>>>>>>> feature/registration-form
```
Разработчик вручную выбирает нужный вариант (или объединяет оба), удаляет маркеры конфликта `<<<<<<<`, `=======`, `>>>>>>>`, затем:
```bash
git add src/App.tsx
git commit -m "merge: разрешён конфликт импорта Header"
```
