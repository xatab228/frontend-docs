# Жизненный цикл разработки ПО — Staff

### KPI для оценки эффективности работы команды и отдельных участников

На уровне команды типичные KPI: velocity (объём выполненной работы за спринт в story points), cycle time (время от начала работы над задачей до её завершения), lead time (время от создания задачи до её выхода в продакшен), процент задач, возвращённых из QA, доля успешных деплоев без отката (change failure rate) и MTTR (mean time to recovery — среднее время восстановления после инцидента). На индивидуальном уровне метрики должны применяться осторожно — количество коммитов или строк кода легко манипулировать и они не отражают ценность работы, поэтому предпочтительны косвенные и командные показатели: качество код-ревью (доля найденных на ревью дефектов), участие в менторстве, снижение технического долга в закреплённых зонах ответственности. DORA-метрики (Deployment Frequency, Lead Time for Changes, Change Failure Rate, Time to Restore Service) — общепринятый индустриальный стандарт для оценки эффективности всей инженерной организации, а не отдельного человека.

### Принципы выбора оптимальной методики оценки трудозатрат в больших и/или комплексных проектах

В больших проектах выбор методики оценки зависит от уровня неопределённости и горизонта планирования: для дорожной карты на квартал уместна грубая относительная оценка (T-shirt sizing) на уровне эпиков, для ближайшего спринта — точная оценка в story points через Planning Poker на уровне декомпозированных задач. Staff-инженер обычно вводит калибровку оценок по историческим данным (velocity команды за последние N спринтов) вместо интуитивных догадок, а для высокорисковых задач (незнакомый стек, внешние зависимости) закладывает буфер через технику трёх точек (PERT) вместо единственного числа. Важный принцип — оценка должна периодически пересматриваться по мере снижения неопределённости (rolling wave planning), а не фиксироваться один раз в начале проекта.

### Принципы процесса и автоматизации релизов

Автоматизация релиза строится вокруг конвейера continuous delivery: каждый успешный мерж в основную ветку автоматически проходит сборку, тесты и (при выполнении условий) деплой без ручного вмешательства. Ключевые принципы: релиз должен быть воспроизводимым (одна и та же версия кода всегда собирается идентично — фиксация lock-файлов зависимостей), обратимым (возможность быстрого отката через blue-green/rollback), инкрементальным (мелкие частые релизы снижают риск по сравнению с редкими крупными), и observable (автоматический мониторинг метрик сразу после выкладки с автоматическим откатом при аномалиях).

```yaml
# .gitlab-ci.yml — фрагмент автоматизированного релиза с семантическим версионированием
release:
  stage: release
  image: node:20
  script:
    - npx semantic-release   # анализирует commit message (Conventional Commits)
                              # и автоматически определяет major/minor/patch,
                              # генерирует CHANGELOG, создаёт git tag и релиз
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

```
# Conventional Commits, на основе которых определяется тип релиза
fix: исправлена утечка памяти в модалке        → patch
feat: добавлен тёмный режим                     → minor
feat!: изменён публичный API компонента Button  → major (breaking change)
```

### Концепции стандартизации методологий и инструментов работы с Git

Стандартизация на уровне организации означает единый branching model (например, trunk-based для всех фронтенд-команд), единые соглашения об именовании веток и коммитов (Conventional Commits), общие git-хуки через `husky`/`lefthook`, зафиксированные в шаблоне репозитория, и единый набор защит веток (protected branches, обязательные approvals), применяемый через политику организации, а не вручную в каждом проекте. Цель — снизить когнитивную нагрузку при переходе разработчиков между командами и уменьшить количество ошибок, вызванных разными процессами в разных проектах.

```json
// package.json — единые git-хуки, применяемые ко всем репозиториям организации
{
  "scripts": {
    "prepare": "husky install"
  },
  "husky": {
    "hooks": {
      "commit-msg": "commitlint -E HUSKY_GIT_PARAMS",
      "pre-push": "npm run lint && npm run test"
    }
  }
}
```

## Практика (УМЕЕТ)

### Декомпозировать сложные задачи и точно оценивать трудозатраты на комплексные изменения или целый продукт

Для крупного продукта декомпозиция идёт каскадно: продукт → эпики → фичи → задачи, а оценка каждого уровня использует свою методику из раздела выше про оценку трудозатрат в больших проектах — T-shirt sizing для эпиков на дорожной карте, story points для задач в спринте.

```
Продукт: Личный кабинет 2.0 (T-shirt: XL, ~6 месяцев)
  ├─ Эпик: Новая система авторизации (T-shirt: L, ~1 месяц)
  │    ├─ Story: Форма логина с OAuth — 5 SP
  │    └─ Story: Восстановление пароля — 3 SP
  └─ Эпик: Дашборд аналитики (T-shirt: M, ~3 недели)
       └─ Story: Виджет графиков — 8 SP
```

### Проводить аудит и оптимизацию процессов разработки с использованием Agile-подходов

Аудит опирается на метрики из раздела про KPI: если cycle time растёт, а velocity стагнирует, staff-инженер анализирует доску задач на предмет узких мест (например, задачи подолгу висят в "Code Review" — значит нужно перераспределить ревьюеров или ввести SLA на ревью), проводит расширенную ретроспективу с командой и предлагает конкретные изменения процесса (лимит WIP, парное программирование для сложных задач).

### Проводить анализ и улучшать процесс релиза

Практическое улучшение процесса релиза — переход от ручных релизов раз в две недели к автоматизированному continuous delivery, описанному в разделе выше, с добавлением feature flags для отделения деплоя от релиза функциональности:

```ts
// Пример feature flag, позволяющего деплоить код без немедленного включения фичи
import { useFeatureFlag } from '@/shared/lib/feature-flags';

function CheckoutPage() {
  const isNewCheckoutEnabled = useFeatureFlag('new-checkout-flow');
  return isNewCheckoutEnabled ? <NewCheckoutFlow /> : <LegacyCheckoutFlow />;
}
```

### Принципы создания самодокументирующегося кода

Самодокументирующийся код минимизирует потребность в комментариях за счёт говорящих имён, малых функций с единственной ответственностью и явных типов вместо неявных допущений:

```ts
// Плохо: неясно, что делает функция и что означает магическое число
function calc(a: number, b: number) {
  return a * b * 0.2;
}

// Хорошо: имена и типы сами объясняют назначение
const VAT_RATE = 0.2;

function calculateValueAddedTax(priceExcludingVat: number, quantity: number): number {
  return priceExcludingVat * quantity * VAT_RATE;
}
```

### Настраивать рабочий процесс GitFlow для команды разработчиков

```bash
# Инициализация GitFlow-структуры веток в репозитории
git checkout -b develop main
git push -u origin develop

# Настройка protected branches в GitLab (через UI или API):
# main    — merge только через MR, 2 approvals, только maintainers могут push
# develop — merge только через MR, 1 approval

# Пример старта фичи в GitFlow
git checkout develop
git checkout -b feature/new-dashboard
# ... работа ...
git push origin feature/new-dashboard
# MR: feature/new-dashboard → develop

# Подготовка релиза
git checkout -b release/2.5.0 develop
# финальное тестирование, фиксы прямо в release-ветке
git checkout main && git merge --no-ff release/2.5.0 && git tag v2.5.0
git checkout develop && git merge --no-ff release/2.5.0
```
