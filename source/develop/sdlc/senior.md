# Жизненный цикл разработки ПО — Senior

### Принципы управления рабочим процессом в Jira или другом инструменте

Jira организует работу вокруг иерархии сущностей: Epic (крупная бизнес-цель) → Story/Task (конкретная работа) → Subtask, каждая с настраиваемым workflow (например, To Do → In Progress → Code Review → QA → Done) и переходами (transitions) между статусами, которые можно ограничивать правами и автоматизировать. Senior-разработчик обычно настраивает или влияет на структуру workflow под нужды команды: добавляет обязательные поля (Story Points, Fix Version), связывает задачи с ветками и MR через интеграцию с GitLab/GitHub (smart commits), настраивает JQL-фильтры и дашборды для отслеживания прогресса спринта (burndown chart) и метрик (velocity, cycle time). Хорошо настроенный процесс в Jira делает статус любой задачи прозрачным для всей команды без необходимости спрашивать в чате "а как там дела с X".

### Категории оценки трудозатрат разработки, может назвать несколько инструментов и методик

Категории оценки: относительная (story points, T-shirt sizing — сравнение сложности задач друг с другом, не в единицах времени), абсолютная (часы/дни — прямая оценка времени выполнения), вероятностная (три точки — оптимистичная/пессимистичная/наиболее вероятная оценка, используемая в PERT для расчёта ожидаемого времени). Методики и инструменты: Planning Poker (командная относительная оценка через карты с числами Фибоначчи), метод трёх точек (PERT: `E = (O + 4M + P) / 6`), исторические данные о velocity команды для калибровки будущих оценок, Delphi-метод (анонимный опрос экспертов с последующим обсуждением расхождений). На практике для фронтенд-фич с высокой неопределённостью (новый UI, незнакомая интеграция) лучше работает относительная оценка, а для рутинных задач — абсолютная оценка в часах.

### Варианты развертывания (blue-green, canary, rolling), их особенности

Blue-Green deployment держит два идентичных окружения (blue — текущее продакшен, green — новая версия); после проверки green трафик переключается на него мгновенно (обычно через балансировщик нагрузки или DNS), что даёт мгновенный откат при проблеме, но требует вдвое больше инфраструктуры. Canary deployment постепенно направляет небольшой процент реального трафика (например, 5%) на новую версию, отслеживая метрики ошибок, и постепенно увеличивает долю при отсутствии проблем — снижает риск за счёт постепенности, но требует хорошей инфраструктуры мониторинга и маршрутизации трафика. Rolling deployment постепенно заменяет старые инстансы новыми по одному или небольшими группами, не требуя дублирования инфраструктуры целиком, но в переходный период старая и новая версии работают одновременно, что требует обратной совместимости API/данных.

```yaml
# Пример canary-выкладки фронтенда через веса на Nginx/Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"   # 10% трафика на новую версию
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            backend:
              service:
                name: frontend-v2
```

### Продвинутые техники работы с Git (cherry pick, bisect, stash, interactive rebase)

```bash
# cherry-pick: перенести конкретный коммит из одной ветки в другую
git cherry-pick a1b2c3d

# bisect: бинарным поиском найти коммит, внёсший баг
git bisect start
git bisect bad                 # текущее состояние содержит баг
git bisect good v1.4.0         # эта версия была рабочей
# git будет чекаутить промежуточные коммиты, для каждого:
git bisect good   # или git bisect bad
git bisect reset   # завершить и вернуться на исходную ветку

# stash: временно отложить незакоммиченные изменения
git stash push -m "WIP: рефакторинг формы"
git checkout main
git pull
git stash pop      # вернуть отложенные изменения обратно

# interactive rebase: причесать историю коммитов перед мержем
git rebase -i HEAD~5
# в открывшемся редакторе: pick / squash / reword / drop для каждого коммита
```
`git bisect` особенно полезен для регрессий в больших кодовых базах, когда неизвестно, какой из десятков коммитов сломал функциональность — вместо ручного перебора git автоматизирует бинарный поиск за O(log n) шагов.

### Продвинутые возможности GitLab (merge request approvals, protected branches, CI pipelines)

Merge Request Approvals — правило, требующее одобрения от определённого числа ревьюеров (и опционально от конкретных кодовладельцев через `CODEOWNERS`) перед тем, как MR можно будет слить. Protected Branches защищают ключевые ветки (`main`, `develop`) от прямого push и force-push, разрешая изменения только через MR с прохождением CI и нужным числом апрувов. CI Pipelines — описанный в `.gitlab-ci.yml` набор стадий (build, test, lint, deploy), автоматически запускаемый на каждый push/MR.

```yaml
# .gitlab-ci.yml
stages: [install, lint, test, build, deploy]

install:
  stage: install
  script: npm ci
  cache:
    key: ${CI_COMMIT_REF_SLUG}
    paths: [node_modules/]

lint:
  stage: lint
  script: npm run lint

test:
  stage: test
  script: npm run test -- --coverage

build:
  stage: build
  script: npm run build
  artifacts:
    paths: [dist/]

deploy:
  stage: deploy
  script: ./scripts/deploy.sh
  only:
    - main
```

## Практика (УМЕЕТ)

### Вести техническую документацию

Пример ADR (Architecture Decision Record) — короткого документа, фиксирующего архитектурное решение и его причины:

```markdown
# ADR-007: Переход на TanStack Query для серверного состояния

## Статус
Принято

## Контекст
Ручное управление loading/error/cache состоянием через useEffect
приводит к дублирующемуся коду и рассинхронизации кэша между компонентами.

## Решение
Используем @tanstack/react-query для всех серверных запросов.

## Последствия
+ Автоматическое кэширование и рефетч
+ Меньше boilerplate-кода
- Дополнительная зависимость и кривая обучения для команды
```

### Брать на себя ведущую роль в команде по методологии Scrum и проводить планирование

Senior-разработчик модерирует Planning Poker: озвучивает задачу, собирает независимые оценки от каждого участника, при сильном расхождении (например, кто-то дал 2, а кто-то 8 story points) просит аргументировать оценки и приходит к консенсусу — это дополняет процесс декомпозиции и оценки, описанный в разделе выше.

### Эффективно организовывать рабочий процесс с использованием ветвей, использовать fast forward merge (--ff-only) и cherry-pick

```bash
# Fast-forward merge — используется, когда в main не было новых коммитов
# с момента создания feature-ветки, история остаётся линейной без merge-коммита
git checkout main
git merge --ff-only feature/small-fix
# Если fast-forward невозможен (main ушёл вперёд), команда явно упадёт с ошибкой,
# а не создаст неожиданный merge-коммит

# Cherry-pick при переносе исправления в release-ветку
git checkout release/2.3
git cherry-pick a1b2c3d
git push origin release/2.3
```
