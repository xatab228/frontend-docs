# Обеспечение качества — Junior

### Основные типы тестов (unit tests, integration tests, UI tests, E2E и пр.)

Unit-тесты проверяют отдельную функцию, компонент или модуль в изоляции от остальной системы, обычно с помощью моков внешних зависимостей — они самые быстрые и дешёвые, поэтому их должно быть больше всего. Integration-тесты проверяют, что несколько модулей корректно работают вместе (например, компонент вместе с реальным хранилищем состояния или реальным HTTP-клиентом с замоканным сервером). UI-тесты (компонентные тесты) проверяют рендер и поведение React/Vue-компонентов, включая взаимодействие пользователя (клики, ввод текста), без реального браузера. E2E-тесты (end-to-end) прогоняют пользовательский сценарий целиком в настоящем браузере через реальный UI и реальный (или staging) бэкенд — они самые надёжные с точки зрения реальности проверки, но и самые медленные и хрупкие. Эта иерархия описывается "пирамидой тестирования": много быстрых unit-тестов в основании, меньше integration-тестов посередине, минимум медленных E2E-тестов на вершине.

### Что такое Unit Tests и зачем они нужны, принципы написания unit-тестов (независимость, атомарность, воспроизводимость)

Unit-тест — автоматизированная проверка, что отдельная минимальная единица кода (функция, метод, компонент) ведёт себя правильно при заданных входных данных, без обращения к реальной сети, базе данных или файловой системе. Они нужны, чтобы находить регрессии сразу, не дожидаясь ручного тестирования, документировать ожидаемое поведение кода примерами и давать уверенность при рефакторинге. Принципы: независимость (каждый тест не зависит от результата или порядка выполнения других тестов и может запускаться в любом порядке), атомарность (тест проверяет одну конкретную вещь, а не сразу несколько сценариев в одной функции), воспроизводимость (тест всегда даёт одинаковый результат на одних и тех же входных данных — без обращения к `Date.now()`, `Math.random()` или реальному времени без моков).

```ts
// sum.test.ts
import { describe, it, expect } from 'vitest';
import { sum } from './sum';

describe('sum', () => {
  it('складывает два положительных числа', () => {
    expect(sum(2, 3)).toBe(5);
  });

  it('корректно обрабатывает отрицательные числа', () => {
    expect(sum(-2, 5)).toBe(3);
  });
});
```

### Методы контроля качества кода (статический анализ кода, динамический анализ кода)

Статический анализ проверяет код без его выполнения — читает исходный текст и ищет потенциальные проблемы: линтеры (ESLint) ловят стилистические ошибки и опасные паттерны, TypeScript-компилятор ловит несоответствия типов, а специализированные SAST-инструменты ищут уязвимости безопасности. Динамический анализ проверяет код во время реального выполнения — сюда относятся все виды автотестов (unit/integration/E2E), профилирование производительности в рантайме и инструменты вроде Chrome DevTools Coverage, находящие неиспользуемый код по факту исполнения. Разница ключевая: статический анализ находит проблему до запуска (быстрее в CI), динамический — только те проблемы, которые реально проявляются во время выполнения конкретного сценария.

```bash
npm run lint       # статический анализ через ESLint
npx tsc --noEmit    # статическая проверка типов без сборки
npm run test        # динамический анализ — реальный запуск тестов
```

### Что такое технический долг, причины его возникновения

Технический долг — метафора, описывающая накопившиеся в кодовой базе компромиссы (быстрые, но не идеальные решения), которые в моменте ускоряют поставку, но в будущем требуют дополнительных усилий на исправление — как и финансовый долг, он накапливает "проценты" в виде замедления разработки новых фич. Причины возникновения: сознательный компромисс ради соблюдения дедлайна, недостаток знаний о лучших практиках на момент написания кода, изменение требований, из-за которого старая архитектура перестала соответствовать новым нуждам, отсутствие тестов, из-за которого рефакторинг становится рискованным, и устаревание зависимостей/фреймворков со временем. Не весь техдолг — это плохо: осознанный техдолг, взятый ради соблюдения срока с планом "вернуть" его позже, — нормальная инженерная практика, в отличие от неосознанного долга, накапливающегося из-за небрежности.

### Принципы, цели и преимущества использования CI/CD

CI (Continuous Integration) — практика частой интеграции изменений кода в общую ветку с автоматическим прогоном сборки и тестов на каждый коммит/merge request, что позволяет находить конфликты и регрессии сразу, а не через недели изолированной разработки. CD (Continuous Delivery/Deployment) продолжает этот процесс автоматической подготовкой (Delivery) или прямой выкладкой (Deployment) прошедшего проверки кода в продакшен. Цели: сократить время между написанием кода и его попаданием к пользователю, снизить риск человеческой ошибки при ручной сборке/деплое, дать команде быструю обратную связь о качестве изменений. Преимущества для фронтенда конкретно: автоматический прогон линтера/тестов/сборки на каждый MR не даёт сломанному коду попасть в основную ветку, а автоматический деплой на staging-окружение по каждому MR ускоряет ревью визуальных изменений.

### Что такое Code Review и зачем он нужен

Code Review — процесс, при котором один или несколько разработчиков (кроме автора) просматривают изменения кода перед их слиянием в основную ветку, оставляя комментарии и запрашивая исправления при необходимости. Цели: находить баги и логические ошибки до продакшена, поддерживать единообразие стиля и архитектурных решений в проекте, распространять знания о кодовой базе между членами команды (не только автор знает, как работает этот код) и обучать менее опытных разработчиков через обратную связь от старших. В GitLab/GitHub Code Review реализуется через Merge/Pull Request — код нельзя слить в защищённую ветку без нужного числа одобрений (approvals).

### О значимости поддерживаемости и читаемости кода

Код читается значительно чаще, чем пишется — типичное соотношение оценивается как 10:1 в пользу чтения, поэтому оптимизация кода под читаемость почти всегда окупается быстрее, чем экономия времени на "красивое" именование или структуру при первом написании. Плохо читаемый код замедляет онбординг новых членов команды, увеличивает время на код-ревью, повышает риск внесения бага при изменении непонятного участка и делает рефакторинг рискованным занятием. Поддерживаемость подразумевает не только читаемость, но и низкую связанность модулей (изменение в одном месте не требует правок в десяти других) и наличие тестов, дающих уверенность при изменениях.

## Практика (УМЕЕТ)

### Писать unit-тесты для проверки отдельного модуля или компонента

Опираясь на принципы из раздела про unit-тесты выше (независимость, атомарность, воспроизводимость), пример теста для React-компонента:

```tsx
// Counter.test.tsx
import { render, screen, fireEvent } from '@testing-library/react';
import { describe, it, expect } from 'vitest';
import { Counter } from './Counter';

describe('Counter', () => {
  it('увеличивает значение при клике на кнопку', () => {
    render(<Counter initial={0} />);
    const button = screen.getByRole('button', { name: /increment/i });

    fireEvent.click(button);

    expect(screen.getByText('1')).toBeInTheDocument();
  });
});
```

### Использовать инструменты статического анализа кода (линтеры)

```json
// .eslintrc.json
{
  "extends": ["eslint:recommended", "plugin:react/recommended", "plugin:@typescript-eslint/recommended"],
  "rules": {
    "no-unused-vars": "error",
    "eqeqeq": "error",
    "react-hooks/rules-of-hooks": "error"
  }
}
```
```bash
npm run lint            # найти проблемы
npm run lint -- --fix   # автоматически исправить то, что можно исправить
```

### Проводить Code Review на соответствие Coding Best Practices

Пример комментария в Merge Request:

```
Файл: src/components/UserCard.tsx, строка 24

Предлагаю вынести повторяющуюся логику форматирования имени
в отдельную утилиту formatFullName(), она уже используется
в трёх местах (UserCard, UserList, UserProfile) с небольшими
различиями — стоит унифицировать.
```
Ревьюер проверяет соответствие принципам из разделов выше — читаемость, отсутствие дублирования, наличие тестов на новую логику — прежде чем поставить approve.

### Следовать правилам форматирования кода

```json
// .prettierrc
{
  "semi": true,
  "singleQuote": true,
  "trailingComma": "all",
  "printWidth": 100
}
```
```bash
npx prettier --write src/   # автоматически привести код к единому формату
```
Форматирование обычно автоматизируется через pre-commit хук, чтобы разработчику не приходилось помнить о запуске команды вручную:
```json
// package.json
{
  "husky": { "hooks": { "pre-commit": "prettier --write ." } }
}
```
