# Обеспечение качества — Staff

### Аспекты обеспечения качества на любом уровне (unit, integration, e2e)

На уровне организации staff-инженер отвечает не за отдельные тесты, а за баланс всей пирамиды тестирования между командами: следит, чтобы команды не скатывались в "перевёрнутую пирамиду" (много хрупких дорогих E2E-тестов и мало дешёвых unit-тестов), которая типично возникает, когда unit-тестирование воспринимается как формальность, а уверенность в код ищут через тяжёлые E2E-прогоны. Практически это выражается в общих стандартах: какой процент покрытия ожидается на каждом уровне, какие сценарии обязаны быть покрыты E2E (только критичные бизнес-пути — оплата, регистрация), а какие проверяются integration-тестами (взаимодействие компонентов) и unit-тестами (бизнес-логика в изоляции). Задача — минимизировать суммарное время обратной связи CI, сохраняя достаточную уверенность в отсутствии регрессий.

### Новые тенденции и технологии в анализе кода и тестировании

Ключевые тренды последних лет: AI-ассистированная генерация и ревью тестов (Copilot/Claude предлагают тестовые кейсы на основе сигнатуры функции, включая edge cases, которые человек может упустить), mutation testing (инструменты вроде Stryker намеренно вносят баги в код и проверяют, ловят ли их существующие тесты — даёт более честную оценку качества тестов, чем просто code coverage), visual regression testing (Chromatic/Percy автоматически сравнивают скриншоты UI между коммитами и ловят непреднамеренные визуальные регрессии), property-based testing (генерация случайных входных данных по заданным свойствам вместо ручного перечисления кейсов, например через fast-check в JS-экосистеме), shift-left security (интеграция SAST/dependency-scanning прямо в IDE разработчика, а не только в CI).

```ts
// Пример property-based теста через fast-check
import fc from 'fast-check';
import { describe, it, expect } from 'vitest';
import { reverseString } from './reverseString';

describe('reverseString', () => {
  it('двойной реверс возвращает исходную строку для любого ввода', () => {
    fc.assert(
      fc.property(fc.string(), (str) => {
        expect(reverseString(reverseString(str))).toBe(str);
      })
    );
  });
});
```

### Стратегии повышения качества кода на уровне организации

Стратегия на уровне организации строится на трёх опорах: стандартизация (единые style guide, ESLint-конфиги, шаблоны репозиториев, распространяемые через внутренний npm-пакет), автоматизация (Quality Gates, обязательные в каждом проекте, а не по желанию команды) и культура (Code Review Culture, менторство, внутренние гильдии по качеству кода). Практически это часто реализуется через "paved road" — заранее подготовленный, полностью настроенный шаблон проекта (с ESLint, Prettier, CI-пайплайном, тестовой инфраструктурой из коробки), которым командам проще воспользоваться, чем настраивать всё с нуля, что де-факто обеспечивает единообразие без принуждения.

```bash
# Единый npx-генератор нового проекта с преднастроенным качественным тулингом
npx create-company-frontend-app my-new-service
# Внутри: ESLint + Prettier + Husky + Vitest + Playwright + CI templates уже настроены
```

Опору на стандарты дополняет их формальное оформление и продвижение — например, в виде внутреннего Frontend Style Guide:

```
# Пример структуры внутреннего Frontend Style Guide
frontend-standards/
  01-code-style.md        (ESLint/Prettier конфиги, обоснования правил)
  02-testing-strategy.md  (пирамида тестирования, обязательные покрытия)
  03-architecture.md      (FSD-конвенции, границы слоёв)
  04-git-workflow.md      (trunk-based, conventional commits)
  05-accessibility.md     (обязательные a11y-проверки)
```
Стандарт продвигается не только документом, но и обеспечивающим его тулингом (общий ESLint-пакет `@company/eslint-config-frontend`, публикуемый во внутренний npm-registry), чтобы следование стандарту требовало минимум ручных усилий от команд.

Опора на культуру, в свою очередь, требует умения управлять изменениями и реформами: внедрение культурного изменения (например, обязательный mutation testing) проводится постепенно — сперва пилотируется в одной команде-волонтёре, собираются метрики влияния (сколько реальных пропущенных багов найдено), затем результаты презентуются на внутренней гильдии/митапе, и только после этого практика закрепляется в общем `CODE_REVIEW_GUIDELINES.md` или Quality Gate для всех команд — резкое директивное внедрение без демонстрации ценности обычно встречает сопротивление и формальное, а не искреннее соблюдение.

### Влияние технического долга на сроки, бюджет и качество продукта

Технический долг напрямую замедляет velocity команды со временем: каждая новая фича требует больше усилий, потому что разработчику приходится сначала разобраться в запутанной legacy-логике, аккуратно обойти хрупкие места без тестов и потратить время на ручную проверку регрессий, которые не ловятся автоматически. Это выражается в растущем lead time на одинаковые по сложности задачи, росте числа продакшен-инцидентов (change failure rate из DORA-метрик) и, как следствие, росте бюджета на поддержку по сравнению с бюджетом на новую функциональность. Невидимость техдолга для нетехнического менеджмента — отдельная проблема: в отличие от бага, техдолг не проявляется как видимый дефект, поэтому staff-инженер должен уметь переводить его в понятные бизнесу термины (скорость поставки фич, риск инцидентов), чтобы обосновать выделение времени на его устранение.

### Стратегии работы с Техдолгом (Tech Debt) (Strategic Debt Management)

Strategic Debt Management подразумевает осознанное управление техдолгом как портфелем, а не хаотичное исправление "что попадётся": ведение реестра техдолга с оценкой его стоимости (насколько замедляет разработку) и риска (что случится, если не исправить), приоритизация по принципу "исправлять техдолг в зонах, которые активно изменяются" (правило бойскаута — код, который трогаешь, оставляй чище, чем было, вместо отдельных "рефакторинговых спринтов", которые сложно продать бизнесу), выделение фиксированной доли capacity команды на техдолг в каждом спринте (например, 20%) вместо разового "давайте потратим месяц на рефакторинг". Ключевая стратегическая идея — не весь техдолг нужно устранять: техдолг в зоне кода, который скоро будет полностью переписан или выведен из эксплуатации, не стоит вложенных усилий.

```
# Пример реестра техдолга с приоритизацией по влиянию × частоте изменений
| Модуль            | Влияние на скорость | Частота изменений | Приоритет |
|-------------------|---------------------|--------------------|-----------|
| CheckoutFlow       | Высокое             | Высокая            | P0        |
| LegacyReportsPage  | Среднее             | Низкая (deprecated)| P3 (не трогать) |
| AuthModule         | Высокое             | Средняя            | P1        |
```

На практике эта стратегия реализуется прямо в процессе планирования — выделение фиксированной доли capacity под техдолг в Jira/Scrum-процессе:

```
Sprint Planning: из 40 SP capacity команды
  - 32 SP (80%) — новая функциональность
  - 8 SP (20%)  — техдолг, приоритизированный по реестру
                  (см. раздел про Strategic Debt Management выше)
```

### Принципы автоматизации и оптимизации процессов CI/CD

Оптимизация CI/CD на уровне организации фокусируется на сокращении времени обратной связи и стоимости выполнения: параллелизация независимых джобов (lint/typecheck/test запускаются одновременно, а не последовательно), кэширование зависимостей и промежуточных артефактов сборки между запусками, инкрементальные проверки (запуск тестов только для затронутых изменением модулей через affected-анализ, как в Nx/Turborepo), переиспользуемые CI-шаблоны на уровне организации вместо копипасты `.gitlab-ci.yml` в каждом репозитории.

```yaml
# .gitlab-ci.yml — параллельные независимые джобы + переиспользуемый шаблон
include:
  - project: 'platform/ci-templates'
    file: '/frontend-quality.yml'

stages: [check, build, deploy]

lint:
  extends: .frontend-lint-template
  stage: check

typecheck:
  extends: .frontend-typecheck-template
  stage: check

test:
  extends: .frontend-test-template
  stage: check
```

```bash
# Nx — запуск тестов только для затронутых изменением проектов в монорепозитории
npx nx affected -t test --base=main
```

На практике это означает, что команды используют инструменты для автоматизированного запуска тестов, не настраивая их с нуля — общий переиспользуемый CI-шаблон для всех фронтенд-репозиториев, на который команды подключаются одной строкой (см. `include` выше), вместо того чтобы каждая команда настраивала пайплайн с нуля. Поддержка таких пайплайнов на уровне организации означает версионирование переиспользуемых шаблонов как отдельного продукта с собственным changelog, аналогично примеру `platform/ci-templates` выше, чтобы breaking-изменения шаблона не ломали все команды одновременно.

### Метрики и подходы контроля качества в процессе разработки ПО (скорость команды (velocity), количество дефектов, среднее время на исправление багов, ..)

Ключевые метрики контроля качества на уровне организации: velocity (для отслеживания тренда, а не сравнения команд между собой — у разных команд разная калибровка story points), defect density (количество дефектов на тысячу строк кода или на фичу — индикатор качества процесса разработки), MTTR (Mean Time To Resolution — среднее время от обнаружения бага до исправления), escape rate (доля дефектов, найденных в продакшене, а не на этапе тестирования — чем ниже, тем эффективнее внутренние процессы QA). Staff-инженер использует эти метрики не для наказания отдельных разработчиков, а для выявления системных проблем процесса — например, растущий escape rate обычно значит, что Quality Gate недостаточно строгий или тестовое покрытие критичных путей неполное.

### Стратегии создания Code Review culture

Здоровая культура код-ревью строится на нескольких принципах: ревью комментарии формулируются как предложения, а не приказы ("предлагаю..." вместо "переделай"), разделение блокирующих замечаний (must fix) от необязательных пожеланий (nit/nitpick), маркируемых явно, чтобы автор понимал приоритет; ожидание быстрого времени отклика на ревью (SLA, например до 4 рабочих часов), чтобы не блокировать коллег надолго; ротация ревьюеров, чтобы знания о кодовой базе не концентрировались у одного человека; обучение через ревью — старшие разработчики объясняют "почему", а не просто указывают "что не так". Внедряется через явный документ-гайдлайн и регулярные ретроспективы именно по процессу ревью (не только по продукту).

```markdown
# CODE_REVIEW_GUIDELINES.md
- `nit:` — необязательное пожелание, не блокирует merge
- `blocking:` — обязательно к исправлению перед merge
- Ответ на ревью ожидается в течение 4 рабочих часов
- Ревьюер обязан объяснить "почему", ссылкой на принцип/документацию,
  а не только указать "что не так"
```

### Проводить масштабные рефакторинги в комплексных проектах

Масштабный рефакторинг проводится поэтапно через strangler fig (упомянутый в senior-материале), но на уровне staff добавляется формальный план миграции с измеримыми чекпоинтами:

```
Migration Plan: Redux → Zustand (12 модулей)
  Этап 1 (спринт 1-2): новая инфраструктура state management, оба сосуществуют
  Этап 2 (спринт 3-6): миграция модулей по одному, начиная с наименее связанных
  Этап 3 (спринт 7): удаление Redux, финальная проверка bundle size
  Метрика успеха: 0 регрессий в E2E-сьюте на каждом этапе, bundle size не растёт
```

Такие миграции опираются на автоматизацию и инструменты, облегчающие механическую часть рефакторинга по всей кодовой базе:

```bash
# ts-morph — программный API для безопасных массовых трансформаций TypeScript
npm install ts-morph
```
```ts
// migrate-imports.ts — автоматическая замена импортов по всему проекту
import { Project } from 'ts-morph';

const project = new Project({ tsConfigFilePath: 'tsconfig.json' });
project.getSourceFiles('src/**/*.ts').forEach((file) => {
  file.getImportDeclarations().forEach((imp) => {
    if (imp.getModuleSpecifierValue() === 'redux') {
      imp.setModuleSpecifier('zustand');
    }
  });
});
project.saveSync();
```
