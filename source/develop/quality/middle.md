# Обеспечение качества — Middle

## Основы покрытия кода тестами (code coverage)

Code coverage — метрика, показывающая, какой процент строк, ветвлений (branches), функций и операторов исходного кода был выполнен во время прогона тестов. Основные виды покрытия: line coverage (доля выполненных строк), branch coverage (доля пройденных веток условий — важнее, чем line coverage, так как строка может выполниться, но не все её условные ветки), function coverage и statement coverage. Высокий процент покрытия не гарантирует отсутствие багов — тест может выполнить строку кода, не проверив реальный результат (тест без содержательных assert), поэтому покрытие — необходимое, но не достаточное условие качества тестов.

```bash
npm run test -- --coverage
```
```text
# Пример отчёта покрытия (vitest/jest)
File           | % Stmts | % Branch | % Funcs | % Lines
---------------|---------|----------|---------|--------
formatDate.ts  |   90.0  |   75.0   |  100.0  |  90.0
```

На практике измерение покрытия настраивается через конфигурацию тест-раннера и порогом падения:

```ts
// vitest.config.ts
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
      thresholds: { lines: 80, branches: 70 },
    },
  },
});
```
```bash
npm run test -- --coverage
open coverage/index.html   # визуальный HTML-отчёт по покрытию
```

## Различные подходы к написанию unit-тестов (test doubles, stubbing, mocking)

Test double — общий термин для объекта, подменяющего реальную зависимость в тесте. Основные виды: dummy (объект-заглушка, передаётся, но никогда реально не используется, нужен только чтобы удовлетворить сигнатуру), stub (возвращает заранее заданные ответы на вызовы, не проверяет, как именно его вызывали), mock (как stub, но дополнительно проверяет факт и параметры вызова — использовался ли метод и с какими аргументами), spy (оборачивает реальную функцию, позволяя отслеживать вызовы, сохраняя оригинальное поведение), fake (упрощённая, но рабочая реализация — например, in-memory база данных вместо реальной). Mocking обычно нужен для внешних зависимостей (сетевые запросы, время, случайные числа), stubbing — когда важен только предсказуемый возврат значения, а не факт вызова.

```ts
import { vi, describe, it, expect } from 'vitest';
import { fetchUser } from './api';
import { greetUser } from './greetUser';

vi.mock('./api'); // mock всего модуля

describe('greetUser', () => {
  it('вызывает fetchUser с правильным id и формирует приветствие', async () => {
    vi.mocked(fetchUser).mockResolvedValue({ name: 'Анна' });

    const result = await greetUser(42);

    expect(fetchUser).toHaveBeenCalledWith(42);   // проверка вызова — это mock
    expect(result).toBe('Привет, Анна!');
  });
});
```

На практике эти test double применяются при структурировании целых тестовых наборов через `describe`-блоки и переиспользуемые mock-фабрики:

```ts
// test/mocks/user.factory.ts
export const createMockUser = (overrides = {}) => ({
  id: 1,
  name: 'Тестовый пользователь',
  age: 25,
  ...overrides,
});

// UserProfile.test.tsx
describe('UserProfile', () => {
  describe('когда пользователь совершеннолетний', () => {
    it('отображает кнопку покупки', () => {
      const user = createMockUser({ age: 25 });
      render(<UserProfile user={user} />);
      expect(screen.getByRole('button', { name: /купить/i })).toBeInTheDocument();
    });
  });

  describe('когда пользователь несовершеннолетний', () => {
    it('скрывает кнопку покупки', () => {
      const user = createMockUser({ age: 15 });
      render(<UserProfile user={user} />);
      expect(screen.queryByRole('button', { name: /купить/i })).not.toBeInTheDocument();
    });
  });
});
```

Отдельная важная часть написания unit-тестов — создание тестовых сценариев, покрывающих граничные случаи, а не только "счастливый путь":

```ts
describe('calculateDiscount', () => {
  it.each([
    [0, 0],       // граничный случай: нулевая сумма
    [100, 10],    // обычный случай
    [-50, 0],     // граничный случай: отрицательная сумма не должна давать скидку
    [1_000_000, 100_000], // большое значение
  ])('для суммы %i возвращает скидку %i', (amount, expectedDiscount) => {
    expect(calculateDiscount(amount)).toBe(expectedDiscount);
  });
});
```

## Методы обеспечения безопасности кода через статический анализ (SAST, DAST)

SAST (Static Application Security Testing) анализирует исходный код без его выполнения, находя потенциально уязвимые паттерны — использование `eval()` с непроверенным вводом, потенциальный XSS через `dangerouslySetInnerHTML` без санитизации, устаревшие зависимости с известными CVE. DAST (Dynamic Application Security Testing) тестирует уже запущенное приложение "снаружи", как это делал бы атакующий — отправляет вредоносные запросы (SQL-инъекции, XSS-пейлоады) и анализирует реальные ответы сервера. Для фронтенда SAST чаще применяется через `npm audit`/Snyk (уязвимые зависимости) и ESLint security-плагины, а DAST — через инструменты вроде OWASP ZAP, сканирующие уже развёрнутое приложение.

```bash
npm audit                      # SAST-подобная проверка известных уязвимостей в зависимостях
npm audit fix
```
```js
// eslint-plugin-security пример правила, ловящего опасный паттерн
// .eslintrc.js
module.exports = {
  plugins: ['security'],
  rules: {
    'security/detect-object-injection': 'warn',
    'react/no-danger': 'error', // предупреждает об использовании dangerouslySetInnerHTML
  },
};
```

## Различия между качественным и некачественным сложно поддерживаемым кодом

Качественный код характеризуется говорящими именами, единственной ответственностью функций/компонентов (Single Responsibility), низкой связанностью (изменение в одном модуле не требует правок в десятке других), явной обработкой ошибок и наличием тестов, которые документируют ожидаемое поведение. Некачественный код обычно проявляется через "code smells": длинные функции, делающие сразу много всего, дублирование логики в разных местах вместо переиспользуемой абстракции, глубокую вложенность условий, магические числа/строки без объяснения смысла, скрытые побочные эффекты (функция, называющаяся `getUserName`, но по пути ещё и изменяющая глобальное состояние) и отсутствие тестов, из-за чего любое изменение рискованно.

```ts
// Плохо: смешанная ответственность, магическое число, скрытый side-effect
function proc(u) {
  if (u.age > 18) {
    localStorage.setItem('lastUser', u.name); // неожиданный побочный эффект
    return u.name + ' - ' + (u.balance * 0.87);
  }
}

// Хорошо: явные типы, единственная ответственность, без скрытых эффектов
const DISCOUNT_RATE = 0.87;

function calculateDiscountedBalance(user: User): number {
  return user.balance * DISCOUNT_RATE;
}
```

На практике следование этому принципу означает, в частности, использование понятных и описательных имён переменных, функций и классов:

```ts
// Плохо
const d = new Date();
const u = users.filter(x => x.a);

// Хорошо
const currentDate = new Date();
const activeUsers = users.filter(user => user.isActive);
```

## Когда и каким образом использовать комментарии

Комментарии должны объяснять "почему", а не "что" — если код нуждается в комментарии, объясняющем, что он делает, чаще правильнее переименовать переменную/функцию так, чтобы код объяснял себя сам. Уместные случаи для комментариев: неочевидное бизнес-решение или обходной путь (workaround) для бага сторонней библиотеки со ссылкой на issue, предупреждение о неочевидных побочных эффектах, TODO с указанием контекста и (желательно) тикета.

```ts
// Плохо — комментарий дублирует то, что и так очевидно из кода
// увеличиваем count на 1
count++;

// Хорошо — комментарий объясняет неочевидную причину
// Safari до версии 16 не поддерживает structuredClone для File-объектов,
// поэтому используем ручное клонирование. См. WEBKIT-12345.
const cloned = manualCloneForSafari(file);
```

## Понятие качества в разработке ПО и важности внедрения процесса Quality Gates

Качество ПО — многомерное понятие, включающее функциональную корректность, производительность, безопасность, поддерживаемость и удобство использования; для фронтенда сюда же относится доступность (accessibility) и визуальная консистентность UI. Quality Gate — формализованный набор условий, которые изменение кода обязано пройти прежде, чем попасть дальше по конвейеру (например, в продакшен): минимальный процент покрытия тестами, отсутствие критических уязвимостей, отсутствие новых code smells сверх порога, успешный прогон линтера. Важность в том, что Quality Gate делает стандарт качества измеримым и автоматически проверяемым, а не зависящим от внимательности конкретного ревьюера.

```yaml
# sonar-project.properties — пример условий quality gate в SonarQube
sonar.qualitygate.wait=true
# Условия (настраиваются в UI SonarQube):
# - Coverage on New Code >= 80%
# - Duplicated Lines on New Code < 3%
# - Maintainability Rating on New Code = A
# - Security Hotspots Reviewed = 100%
```

## Принципы Clean Code

Ключевые принципы Clean Code (по Роберту Мартину): говорящие имена, раскрывающие намерение без необходимости комментария; функции должны делать одну вещь и делать её хорошо (Single Responsibility на уровне функции); маленький размер функций — если функция не помещается на экране, вероятно, её стоит разбить; минимум аргументов функции (в идеале 0-2, длинный список параметров — признак того, что стоит выделить объект); отсутствие дублирования (DRY); явная обработка ошибок вместо игнорирования; консистентное форматирование во всём проекте.

```ts
// Нарушение Clean Code: длинный список параметров, неясные булевы флаги
function createUser(name: string, age: number, isAdmin: boolean, sendEmail: boolean, dryRun: boolean) {}

// Соответствует Clean Code: объект параметров, явные имена
interface CreateUserOptions {
  name: string;
  age: number;
  isAdmin?: boolean;
  sendWelcomeEmail?: boolean;
}

function createUser(options: CreateUserOptions) {}
```

## Применять различные методы контроля качества кода

Комбинация из статического и динамического анализа, описанных выше, в едином npm-скрипте, который также используется в CI:

```json
// package.json
{
  "scripts": {
    "quality": "npm run lint && tsc --noEmit && npm run test -- --coverage && npm audit"
  }
}
```

## Анализировать кодовую базу на предмет наличия Техдолга (Tech Debt)

```bash
# Поиск TODO/FIXME как индикаторов известного техдолга
grep -rn "TODO\|FIXME" src/ | wc -l

# Устаревшие зависимости
npm outdated

# Сложность кода — SonarQube выявляет высокую цикломатическую сложность
```
```text
# Пример фиксации найденного техдолга в issue-трекере, а не молчаливого игнорирования
TECH-DEBT-234: LegacyOrderForm.tsx использует устаревший Redux-паттерн
  connect() вместо hooks, усложняет типизацию. Оценка рефакторинга: 5 SP.
```

## Проводить Code Review на соответствие функциональности и качество кода

Ревью на этом уровне проверяет не только стиль (как в разделе Junior), но и соответствие принципам Clean Code и отсутствие новых code smells из разделов выше:

```text
Комментарий в MR:
Функция `processOrder` сейчас делает валидацию, расчёт суммы и отправку
уведомления — это нарушает Single Responsibility. Предлагаю разбить на
`validateOrder`, `calculateOrderTotal` и `notifyOrderCreated`, так будет
проще тестировать и переиспользовать логику.
```
