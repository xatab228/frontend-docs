# Протоколы, API — Junior

### Виды и назначение структур передачи данных (JSON, YAML, XML)

JSON (JavaScript Object Notation) — самый распространённый формат для веб-API: компактный, нативно парсится в JS через `JSON.parse`/`JSON.stringify`, поддерживает объекты, массивы, строки, числа, булевы значения и `null`. XML — более многословный формат с открывающими/закрывающими тегами и атрибутами, до сих пор встречается в старых корпоративных API и SOAP-сервисах, поддерживает схемы (XSD) для строгой валидации структуры. YAML — человекочитаемый формат с отступами вместо скобок, обычно используется не для передачи данных по сети, а для конфигурационных файлов (Docker Compose, Kubernetes-манифесты, CI-пайплайны), поскольку его удобно читать и редактировать вручную.

```json
{ "id": 1, "name": "Товар", "price": 999.99, "inStock": true }
```
```xml
<product id="1"><name>Товар</name><price>999.99</price></product>
```
```yaml
product:
  id: 1
  name: Товар
  price: 999.99
```

### Что такое API, особенности версионирования API

API (Application Programming Interface) — контракт, по которому одна программа может обращаться к функциональности другой, не зная деталей её внутренней реализации: набор доступных методов/эндпоинтов, форматов запросов и ответов. Версионирование нужно, чтобы менять API, не ломая уже работающих клиентов (например, старую версию мобильного приложения) — старая версия продолжает работать, пока клиенты не перейдут на новую. Основные способы: версия в URL (`/api/v1/users`), в заголовке (`Accept: application/vnd.api+json;version=2`) или в query-параметре (`?version=2`) — версия в URL самая простая и наглядная, поэтому чаще всего встречается на практике.

### Документирование API (OpenAPI/Swagger)

OpenAPI (ранее Swagger) — стандарт описания REST API в машиночитаемом формате (YAML/JSON): для каждого эндпоинта описываются путь, метод, параметры, тело запроса, возможные коды ответа и схема данных. По этому описанию можно автоматически сгенерировать интерактивную документацию (Swagger UI), клиентский SDK или TypeScript-типы, что для фронтенд-разработчика особенно ценно — не нужно вручную писать типы под ответ API, они генерируются из общего контракта.

```yaml
# openapi.yaml — фрагмент описания эндпоинта
paths:
  /users/{id}:
    get:
      summary: Получить пользователя по id
      parameters:
        - { name: id, in: path, required: true, schema: { type: integer } }
      responses:
        '200':
          content:
            application/json:
              schema: { $ref: '#/components/schemas/User' }
```

### Основы протоколов HTTP и HTTPS

HTTP (HyperText Transfer Protocol) — протокол прикладного уровня для обмена данными между клиентом и сервером по модели запрос-ответ: клиент отправляет запрос с методом, путём, заголовками и (опционально) телом, сервер отвечает статус-кодом, заголовками и телом. HTTPS — тот же HTTP, но поверх TLS-шифрования: данные между клиентом и сервером шифруются, что защищает от перехвата и подмены (man-in-the-middle), а браузеры сегодня требуют HTTPS для многих API (Service Worker, геолокация, доступ к камере).

```
GET /api/products/1 HTTP/1.1
Host: example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 1, "name": "Товар" }
```

### Архитектурный стиль REST

REST (Representational State Transfer) — стиль проектирования API поверх HTTP, где каждый ресурс (например, пользователь, товар) имеет свой URL, а действия над ним выражаются HTTP-методами: `GET` — получить, `POST` — создать, `PUT`/`PATCH` — обновить, `DELETE` — удалить. Ключевые принципы: statelessness (сервер не хранит состояние клиента между запросами — каждый запрос содержит всю нужную информацию), единообразный интерфейс (ресурсы адресуются URL, представлены обычно в JSON) и использование стандартных HTTP-кодов ответа для обозначения результата.

```
GET    /api/products        — список товаров
GET    /api/products/1      — один товар
POST   /api/products        — создать товар
PUT    /api/products/1      — заменить товар целиком
DELETE /api/products/1      — удалить товар
```

### Концепции Stateful и Stateless

Stateless (без сохранения состояния) — сервер не хранит информацию о предыдущих запросах клиента: каждый запрос самодостаточен и содержит всё необходимое (например, токен авторизации в заголовке), поэтому любой инстанс backend может обработать любой запрос — это упрощает горизонтальное масштабирование. Stateful — сервер хранит состояние сессии между запросами (например, классическая сессия на основе cookie с id сессии, хранящейся в памяти сервера) — это требует, чтобы повторные запросы одного пользователя попадали на тот же сервер (sticky session), что усложняет масштабирование. Современные REST API проектируются stateless, а состояние аутентификации переносят в самодостаточные токены (JWT) вместо серверных сессий.

### Основные подходы к коммуникации (синхронная и асинхронная)

Синхронная коммуникация — отправитель ждёт ответа перед тем, как продолжить выполнение (классический `fetch`/`await` запрос к REST API: код "останавливается" до получения ответа). Асинхронная коммуникация — отправитель не ждёт немедленного ответа: сообщение может быть обработано позже (через очередь сообщений) или ответ приходит отдельным событием (WebSocket-сообщение, webhook). Синхронный подход проще в реализации и отладке, но создаёт временную связанность между сторонами (если получатель недоступен — вызывающий получает ошибку сразу); асинхронный подход устойчивее к временной недоступности получателя, но сложнее в отладке и требует дополнительной инфраструктуры.

```js
// синхронный (в смысле ожидания ответа) HTTP-запрос
const res = await fetch('/api/products');
const products = await res.json();

// асинхронное уведомление о событии — не ждём ответа, просто подписываемся
const socket = new WebSocket('wss://example.com/events');
socket.onmessage = (event) => console.log('Новое событие:', event.data);
```

## Практика (УМЕЕТ)

### Определить структуру передачи данных

Для эндпоинта, отдающего список товаров с ценой и наличием, оптимальна JSON-структура (компактность и нативная поддержка в JS), а не XML/YAML, которые для передачи по сети избыточны или не предназначены:

```json
{ "products": [{ "id": 1, "name": "Товар", "price": 999.99, "inStock": true }] }
```

### Писать REST сервисы и делать REST API запросы

```js
// простой REST-эндпоинт на Express
app.get('/api/products/:id', (req, res) => {
  const product = db.find(req.params.id);
  if (!product) return res.status(404).json({ error: 'Not found' });
  res.json(product);
});
```
```js
// запрос к REST API с клиента
const res = await fetch('/api/products/1');
if (!res.ok) throw new Error(`Ошибка ${res.status}`);
const product = await res.json();
```

### Делать основные HTTP-запросы (GET, POST, PUT, DELETE)

```js
await fetch('/api/products/1');                                   // GET
await fetch('/api/products', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Новый товар', price: 100 }),
});                                                                 // POST
await fetch('/api/products/1', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Товар', price: 150 }),
});                                                                 // PUT
await fetch('/api/products/1', { method: 'DELETE' });               // DELETE
```

### Настраивать синхронные вызовы между сервисами

На уровне фронтенда синхронный вызов — это последовательное ожидание ответа перед следующим действием, например при оформлении заказа: сначала дожидаемся подтверждения оплаты, и только затем создаём заказ.

```js
async function checkout(cart) {
  const payment = await fetch('/api/payments', { method: 'POST', body: JSON.stringify(cart) });
  if (!payment.ok) throw new Error('Оплата не прошла');
  const order = await fetch('/api/orders', { method: 'POST', body: JSON.stringify(cart) });
  return order.json();
}
```
