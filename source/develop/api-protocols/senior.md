# Протоколы, API — Senior

### Общие принципы работы сокетов и транспортных протоколов (HTTP/HTTP 2.0, IP, WebSocket, SSE)

Сокет — программная абстракция конца сетевого соединения (IP-адрес + порт), через которую приложение читает и пишет байты в сеть; TCP-сокет обеспечивает надёжную доставку с контролем порядка и потерь, UDP-сокет — без гарантий, но с меньшей задержкой. HTTP/1.1 открывает по соединению на несколько параллельных запросов ограниченно (обычно 6 на хост в браузере) и страдает от head-of-line blocking на уровне запросов. HTTP/2 мультиплексирует множество запросов в одном TCP-соединении через независимые потоки (streams), добавляет сжатие заголовков (HPACK) и server push — это устраняет блокировку на уровне HTTP, хотя блокировка на уровне TCP (при потере пакета) остаётся (её решает уже HTTP/3 поверх QUIC/UDP). WebSocket — отдельный протокол, начинающийся с HTTP-рукопожатия (`Upgrade: websocket`), после которого соединение становится полнодуплексным: обе стороны могут слать сообщения в любой момент без нового запроса — используется для realtime-функциональности (чаты, live-обновления). SSE (Server-Sent Events) — однонаправленный канал сервер→клиент поверх обычного HTTP-соединения с `Content-Type: text/event-stream`, проще WebSocket (работает через `EventSource`, авто-переподключение встроено), но не подходит, когда клиенту нужно часто отправлять данные обратно.

```js
// SSE: сервер стримит события, браузер получает их одно за другим
const events = new EventSource('/api/notifications');
events.onmessage = (e) => console.log('Событие:', JSON.parse(e.data));
```

### Концепцию Whitelist/Blacklist по IP

Whitelist (allowlist) — разрешение доступа только явно перечисленным IP-адресам/подсетям, всё остальное блокируется по умолчанию — более строгая и безопасная модель, применяется для админ-панелей, внутренних API, CI-раннеров. Blacklist (denylist) — блокировка конкретных известных вредоносных IP при разрешённом доступе всем остальным — применяется, когда сервис публичный и нельзя заранее знать всех легитимных клиентов, но обнаружены источники злоупотреблений. Для фронтенд-разработчика это чаще всего проявляется на уровне nginx/API Gateway перед приложением, а не в коде самого фронтенда.

```nginx
location /admin/ {
    allow 10.0.0.0/8;
    allow 192.168.1.100;
    deny all;
    proxy_pass http://admin-backend;
}
```

### Проблемы, связанные с транзитивными и циклическими зависимостями

Транзитивная зависимость — зависимость зависимости (пакет A зависит от B, который зависит от C — C транзитивно тянется в проект A); проблема в том, что разные пакеты могут требовать несовместимые версии одной и той же транзитивной зависимости (dependency hell), а также в непрозрачности security-рисков — уязвимость может прийти из пакета, о существовании которого разработчик не подозревал. Циклическая зависимость — когда модуль A импортирует B, а B (прямо или через цепочку) импортирует обратно A; в JS/TS это часто не приводит к ошибке сборки, но на рантайме один из модулей может получить `undefined` вместо экспортируемого значения, поскольку в момент его первого выполнения зависимый модуль ещё не успел проинициализироваться (проблема порядка инициализации ESM/CommonJS).

```js
// a.js
import { b } from './b.js';
export const a = 'A depends on ' + b;   // b может быть undefined при цикле

// b.js
import { a } from './a.js';
export const b = 'B depends on ' + a;
```

### Возможные подходы к реализации идемпотентности на различных уровнях системы

На уровне API — идемпотентный ключ, передаваемый клиентом (`Idempotency-Key`), который сервер сохраняет вместе с результатом первого выполнения и возвращает его же при повторе (пример на Middle-уровне). На уровне базы данных — уникальные constraints (`UNIQUE`) на бизнес-ключ операции, из-за чего повторная вставка того же логического события просто упадёт с ошибкой конфликта, которую обработчик трактует как "уже сделано". На уровне очереди сообщений — дедупликация по `message-id` на стороне брокера или консьюмера (Kafka поддерживает exactly-once семантику через идемпотентного продюсера и транзакции). На уровне клиента — генерация ключа идемпотентности один раз при создании формы/действия и его переиспользование при всех ретраях, а не генерация нового ключа на каждую попытку.

### Методы пулинга (database connection pooling, thread pooling, connection pooling, session pooling)

Database connection pooling — пул заранее открытых соединений к БД, которые сервис переиспользует между запросами вместо открытия нового соединения на каждый запрос (открытие соединения к БД — дорогая операция из-за аутентификации и TCP/TLS-хендшейка). Thread pooling — пул заранее созданных потоков ОС для обработки задач, избегающий накладных расходов на создание/уничтожение потока под каждую задачу. Connection pooling в общем смысле — то же самое для любых сетевых соединений (HTTP keep-alive пул на стороне HTTP-клиента, например `http.Agent` в Node.js). Session pooling — переиспользование уже аутентифицированных сессий (например, к внешнему API) вместо повторной аутентификации на каждый вызов. Хотя пулинг обычно настраивается на backend, фронтенд-разработчик, пишущий BFF-слой на Node.js, напрямую конфигурирует пул соединений к базе или внешнему API.

```js
// пул соединений к PostgreSQL в BFF-сервисе на Node.js
import { Pool } from 'pg';
const pool = new Pool({ max: 20, idleTimeoutMillis: 30000 });

app.get('/api/orders', async (req, res) => {
  const { rows } = await pool.query('SELECT * FROM orders WHERE user_id = $1', [req.user.id]);
  res.json(rows);
});
```

### Способы обнаружения и обработки дублирующихся запросов

Дубликаты возникают, например, когда пользователь дважды кликает кнопку отправки формы или клиент ретраит запрос после таймаута, не зная, дошёл ли оригинал. Обнаружение: идемпотентные ключи (см. выше), сравнение хэша тела запроса за короткий интервал времени, уникальные constraints в БД. Обработка на фронтенде — дизейбл кнопки сразу после клика и дебаунс повторных сабмитов, чтобы не плодить дубликаты уже на источнике проблемы, а не только полагаться на backend.

```js
async function submitOrder(payload) {
  const btn = document.querySelector('#submit');
  if (btn.disabled) return;      // защита от двойного клика
  btn.disabled = true;
  try {
    await fetch('/api/orders', {
      method: 'POST',
      headers: { 'Idempotency-Key': orderIdempotencyKey },
      body: JSON.stringify(payload),
    });
  } finally {
    btn.disabled = false;
  }
}
```

## Практика (УМЕЕТ)

### Умеет выбирать правильную архитектуру API исходя из особенностей задачи

Публичный API для сторонних интеграторов с широкой аудиторией → REST (простота, кэшируемость, знакомость). Дашборд, агрегирующий данные из множества связанных сущностей с разной вложенностью на разных экранах → GraphQL (клиент сам решает, что забирать, без over/under-fetching). Внутреннее высоконагруженное взаимодействие между микросервисами с строгими SLA по задержке → gRPC.

### Проектировать интеграции RESTful API, gRPC, graphQL, WebSocket

Комбинированный пример: BFF агрегирует REST-запрос к легаси-сервису, gRPC-вызов к внутреннему сервису рекомендаций и отдаёт результат фронтенду через GraphQL, а обновления цены транслирует через WebSocket:

```js
const resolvers = {
  Query: {
    product: async (_, { id }) => {
      const [details, recommendations] = await Promise.all([
        fetch(`http://legacy/products/${id}`).then(r => r.json()),   // REST
        grpcClient.getRecommendations({ productId: id }),             // gRPC
      ]);
      return { ...details, recommendations };
    },
  },
};
```

### Эффективно разрешать проблемы, связанные с транзитивными и циклическими зависимостями

Для транзитивных зависимостей — lock-файлы (`package-lock.json`) для фиксации точных версий, `npm audit`/Dependabot для контроля уязвимостей, и явное overrides/resolutions при конфликте версий. Для циклических — вынесение общего кода в третий модуль, от которого зависят оба (разрыв цикла), либо ленивый импорт внутри функции вместо импорта на верхнем уровне модуля.

```js
// разрыв цикла: и a.js, и b.js зависят от shared.js, но не друг от друга
// shared.js
export const shared = 'общая часть';
```

### Настраивать rate limiting/throttling и тестировать API

```nginx
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
server {
    location /api/ {
        limit_req zone=api_limit burst=20 nodelay;
        proxy_pass http://backend;
    }
}
```
Тестирование лимита — серия быстрых запросов и проверка, что после превышения приходит `429 Too Many Requests` с заголовком `Retry-After`.

### Работать с масштабируемым и архитектурными решениями, включающими идемпотентность операций

Практическая связка идемпотентного ключа на клиенте, уникального constraint в БД и защиты от дублирующего клика (все примеры выше) — законченная демонстрация идемпотентности на всех уровнях: UI не даёт отправить дважды случайно, сеть может ретраить безопасно благодаря ключу, а БД — последний рубеж защиты от гонки.

### Применять пулинг ресурсов

Настройка пула соединений к БД в BFF-сервисе (пример выше) и переиспользование HTTP-агента с keep-alive для исходящих запросов к внешним API вместо нового TCP-соединения на каждый вызов:

```js
import http from 'node:http';
const agent = new http.Agent({ keepAlive: true, maxSockets: 50 });
fetch('http://internal-service/data', { agent });
```
