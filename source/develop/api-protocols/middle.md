# Протоколы, API — Middle

### Формат, особенности и области применения различных структур передачи данных

JSON доминирует в REST/GraphQL API благодаря компактности и нативной поддержке в JS/TS, но не поддерживает типы вроде дат или бинарных данных напрямую — их кодируют строками. Protocol Buffers (Protobuf) — бинарный формат, используемый в gRPC: данные сериализуются по заранее описанной `.proto`-схеме в компактное бинарное представление, что даёт меньший размер и более быструю (де)сериализацию, чем JSON, ценой нечитаемости "на глаз" и необходимости генерации кода из схемы. MessagePack — бинарный аналог JSON, применяется, когда нужна скорость JSON-подобной модели данных без строгой схемы Protobuf. XML с XSD-схемами по-прежнему встречается в enterprise/SOAP-интеграциях, где критична строгая валидация структуры до обработки. Выбор формата на фронтенде почти всегда JSON, если только не используется gRPC-Web или высоконагруженный realtime-канал, где важен размер полезной нагрузки.

На практике выбор оптимальной структуры для конкретного случая выглядит так: для обычного REST-эндпоинта — JSON (см. пример из Junior-уровня); для высоконагруженного internal-сервиса между микросервисами, где важна скорость и строгая типизация, — Protobuf/gRPC:

```proto
// user.proto
message User {
  int32 id = 1;
  string name = 2;
}
```

### Понятие и устройство cookie (атрибуты: domain, path, secure, httpOnly, sameSite)

Cookie — небольшой фрагмент данных, который сервер просит браузер сохранить и автоматически отправлять обратно с последующими запросами на тот же сайт, обычно используется для хранения id сессии или токена. Атрибуты управляют её видимостью и безопасностью: `Domain` определяет, для каких доменов cookie отправляется (без указания — только для точного хоста); `Path` ограничивает cookie конкретным префиксом URL; `Secure` разрешает отправку только по HTTPS; `HttpOnly` запрещает доступ к cookie из JavaScript (`document.cookie`), защищая от кражи через XSS; `SameSite` (`Strict`/`Lax`/`None`) ограничивает отправку cookie при кросс-сайтовых запросах, защищая от CSRF — `None` требует обязательного `Secure`.

```
Set-Cookie: session_id=abc123; Domain=example.com; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=3600
```

### Разницу, плюсы и минусы использования различных архитектурных стилей API (REST, gRPC, GraphQL)

REST прост в освоении, использует стандартные HTTP-методы и коды, легко кэшируется на уровне HTTP/CDN, но страдает от over-fetching (клиент получает больше полей, чем нужно) и under-fetching (нужно несколько запросов, чтобы собрать связанные данные). GraphQL решает эту проблему единым эндпоинтом, где клиент сам описывает, какие поля и связанные сущности ему нужны за один запрос, но усложняет кэширование на HTTP-уровне (обычно один POST-эндпоинт) и требует продуманной защиты от слишком "дорогих" запросов (query complexity limits). gRPC использует Protobuf и HTTP/2, даёт строгую типизацию контракта, поддерживает потоковую передачу (streaming) в обе стороны и высокую производительность, но плохо читается человеком без инструментов и в браузере требует gRPC-Web с прокси-слоем, так как браузеры не дают полного доступа к HTTP/2 трейлерам.

```graphql
# GraphQL: клиент запрашивает ровно нужные поля пользователя и его последние 3 заказа
query {
  user(id: 1) {
    name
    orders(limit: 3) { id total }
  }
}
```

### Коды состояний (1хх, 2хх, 3xx, 4xx, 5xx)

1xx (информационные, например `100 Continue`) — запрос принят, обработка продолжается. 2xx (успех) — `200 OK` (успешный запрос), `201 Created` (ресурс создан), `204 No Content` (успех без тела ответа). 3xx (редиректы) — `301 Moved Permanently` (постоянный редирект, кэшируется браузером), `302 Found` (временный редирект), `304 Not Modified` (ресурс не изменился, использовать кэш). 4xx (ошибка клиента) — `400 Bad Request` (некорректные данные), `401 Unauthorized` (не авторизован), `403 Forbidden` (авторизован, но нет прав), `404 Not Found`, `409 Conflict` (конфликт состояния, например дубликат), `429 Too Many Requests`. 5xx (ошибка сервера) — `500 Internal Server Error`, `502 Bad Gateway` (proxy не смог получить корректный ответ от backend), `503 Service Unavailable`.

### Инструменты тестирования API (Hoppscotch, Postman, HTTPie или др.)

Postman и Hoppscotch — GUI-клиенты для ручного и коллекционного тестирования API: позволяют сохранять запросы в коллекции, задавать переменные окружения (base URL, токены), писать pre-request/post-response скрипты и запускать коллекции автоматически (Newman для CI). HTTPie/curl — CLI-инструменты, удобные для быстрой проверки эндпоинта прямо из терминала или встраивания в скрипты и CI.

```bash
http POST https://api.example.com/users name=Alice email=alice@example.com   # HTTPie
curl -X POST https://api.example.com/users -H 'Content-Type: application/json' -d '{"name":"Alice"}'
```

### Batch-операции и их преимущества

Batch-операция объединяет несколько логических действий в один HTTP-запрос вместо отправки отдельного запроса на каждое, снижая накладные расходы на установку соединения, TLS-хендшейк и сетевую задержку (особенно заметно на мобильных сетях с высоким RTT). Преимущества: меньше запросов — меньше суммарной задержки, возможность обработать операции атомарно на сервере (всё или ничего), снижение нагрузки на API Gateway/rate limiter.

Аналогично batch-удалению можно объединить несколько чтений в один запрос через query-параметр списка id: `GET /api/products?ids=1,2,3` вместо трёх отдельных `GET`.

```js
// вместо 3 отдельных DELETE-запросов — один batch-запрос
await fetch('/api/products/batch-delete', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ ids: [1, 2, 3] }),
});
```

### Понятие пулинга (Pooling) и его цели

Пулинг — переиспользование заранее созданных дорогих ресурсов (соединений, потоков) вместо создания нового при каждом обращении, поскольку установка соединения (особенно TLS) — дорогая операция. Цель — снизить задержку и нагрузку за счёт отказа от повторной инициализации. Пример, знакомый фронтенд-разработчику, — HTTP keep-alive/connection pooling в браузере: браузер переиспользует TCP-соединение для нескольких последовательных запросов к одному хосту вместо открытия нового на каждый.

### Принципы идемпотентности операций

Операция идемпотентна, если повторное её выполнение с теми же параметрами приводит к тому же результату, что и однократное — важно для устойчивости к сетевым сбоям, когда клиент не уверен, дошёл ли предыдущий запрос, и вынужден повторить его. `GET`, `PUT`, `DELETE` идемпотентны по спецификации HTTP (повторный `PUT` с теми же данными оставит ресурс в том же состоянии; повторный `DELETE` уже удалённого ресурса просто вернёт 404/204, но не создаст побочных эффектов), а `POST` — нет (повторный `POST` обычно создаёт второй ресурс), поэтому для операций создания, которые должны быть безопасно повторяемы (например, оплата), используют идемпотентный ключ.

На практике клиент генерирует уникальный ключ идемпотентности для операции оплаты:

```js
const idempotencyKey = crypto.randomUUID();
await fetch('/api/payments', {
  method: 'POST',
  headers: { 'Idempotency-Key': idempotencyKey, 'Content-Type': 'application/json' },
  body: JSON.stringify({ amount: 1000 }),
});
// при повторной отправке с тем же ключом (например, после таймаута) сервер
// вернёт результат первой попытки, а не создаст второй платёж
```

### Эффективно обмениваться данными по протоколам HTTP, WebSocket

HTTP — для разовых запрос-ответ операций (см. `fetch` примеры Junior-уровня); WebSocket — для постоянного двустороннего канала, например обновления корзины в реальном времени:

```js
const ws = new WebSocket('wss://example.com/cart-updates');
ws.onopen = () => ws.send(JSON.stringify({ type: 'subscribe', cartId: 42 }));
ws.onmessage = (e) => updateCartUI(JSON.parse(e.data));
```

### Разрабатывать и версионировать API и сервисы

```js
// версия API в пути — старая версия продолжает работать для старых клиентов
app.get('/api/v1/users/:id', getUserV1);
app.get('/api/v2/users/:id', getUserV2); // добавлено поле avatarUrl
```

### Проектировать API с использованием API Gateway

API Gateway — единая точка входа перед несколькими backend-сервисами, берущая на себя аутентификацию, rate limiting, маршрутизацию и агрегацию ответов, так что фронтенд обращается к одному домену вместо знания адресов всех микросервисов.

```nginx
location /api/users/    { proxy_pass http://users-service:4001/; }
location /api/orders/   { proxy_pass http://orders-service:4002/; }
```
