# Протоколы, API — Staff

## Самые свежие исследования в области сетевых протоколов и форматов данных

**HTTP/3 поверх QUIC** (транспорт на UDP вместо TCP) решает head-of-line blocking на уровне транспорта: потеря одного пакета больше не блокирует все мультиплексированные потоки, как в HTTP/2 поверх TCP. Установка соединения совмещена с TLS-хендшейком (0-RTT для повторных подключений), что особенно заметно на нестабильных мобильных сетях.

**Бинарные self-describing форматы** (Cap'n Proto, FlatBuffers) исключают этап десериализации: данные читаются прямо из буфера без промежуточного парсинга. Актуально для высокочастотных realtime-сценариев — игры, финтех.

**gRPC-Web и Connect** — более простая альтернатива поверх обычного HTTP/1.1+JSON или бинарного протокола с единым контрактом, снижающая порог входа в типизированные бинарные протоколы для браузерных клиентов.

```text
HTTP/3 (QUIC/UDP) — устраняет TCP head-of-line blocking
  └── независимые потоки не блокируют друг друга при потере пакета
HTTP/2 (TCP)      — мультиплексирование на уровне HTTP, но блокировка на уровне TCP остаётся
HTTP/1.1          — по соединению на ограниченное число параллельных запросов
```

## Универсальные теории и подходы к проектированию API

На уровне организации API проектируется не как набор разрозненных эндпоинтов, а как продукт с собственным жизненным циклом:

- **API-first.** Контракт (OpenAPI / GraphQL SDL / Protobuf) проектируется и согласовывается до написания кода, а сервер и клиенты генерируются или валидируются против него.
- **Richardson Maturity Model** — шкала «REST-зрелости» API: от простого RPC поверх HTTP до полного HATEOAS, где ответы содержат ссылки на доступные следующие действия.
- **Backend for Frontend (BFF)** — тонкий агрегирующий слой под каждую фронтенд-платформу (веб, мобильное приложение), изолирующий её от общих внутренних сервисов.

На уровне governance добавляются единый API-каталог (Backstage, портал разработчика в API Gateway) и контроль обратной совместимости через contract testing (Pact) в CI — чтобы breaking change обнаруживался до релиза, а не в проде у потребителей.

```yaml
# пример contract-теста (Pact): фронтенд фиксирует ожидаемый контракт от backend
# — CI backend-сервиса прогоняет этот контракт и падает при breaking change
consumer: frontend-app
provider: orders-service
interactions:
  - description: "получить заказ по id"
    request: { method: GET, path: /orders/1 }
    response: { status: 200, body: { id: 1, status: "shipped" } }
```

Практический пример внедрения инновационных подходов к проектированию API и форматов данных — переход большого фронтенд-монолита на end-to-end типизированный API через tRPC вместо ручного поддержания REST-контракта и отдельных TS-типов:

```ts
// server/router.ts — единственный источник истины для типов
export const appRouter = router({
  getProduct: publicProcedure
    .input(z.object({ id: z.number() }))
    .query(({ input }) => db.products.findById(input.id)),
});
export type AppRouter = typeof appRouter;

// client.ts — типы подтягиваются автоматически, без ручной синхронизации
const product = await trpc.getProduct.query({ id: 1 }); // TS знает точную форму product
```

## Современные отраслевые тренды и будущие направления развития в контексте разработки API

Основные направления развития:

- **Сквозные типизированные контракты** (tRPC, GraphQL codegen, OpenAPI-to-TypeScript) — стирание границы между типами бекенда и фронтенда без ручной синхронизации.
- **Edge-first API** — выполнение части API-логики на CDN edge-узлах ближе к пользователю, что снижает задержку для персонализации и A/B-тестов.
- **AsyncAPI** — аналог OpenAPI для событийных и message-driven API: формализует документирование WebSocket/Kafka-контрактов так же, как OpenAPI формализует REST.
- **API как продукт для LLM-агентов** — структурированные самоописывающиеся API, которые агент интерпретирует без предварительного знания домена, и стандарты вроде MCP для унифицированного доступа инструментов к внешним системам.

Для фронтенд-платформы это означает переход от «написать типы вручную под ответ API» к «получить типы автоматически из единого источника истины», что убирает целый класс рассинхронизаций между клиентом и сервером.

## Проектировать высоконагруженные асинхронные архитектуры с учетом SLA

Пример: сервис обработки загружаемых пользователем изображений с жёстким SLA на отклик API (клиент должен получить ответ до 200 мс), при том что сама обработка занимает секунды. Решение — API немедленно принимает запрос и возвращает `202 Accepted` со ссылкой на статус, тяжёлая обработка уходит в очередь и выполняется асинхронно, а клиент узнаёт о завершении через WebSocket/SSE или поллинг статуса — так синхронный контракт API остаётся быстрым независимо от реальной длительности работы.

```js
// быстрый ответ API, тяжёлая работа — асинхронно через очередь
app.post('/api/images', async (req, res) => {
  const jobId = crypto.randomUUID();
  await queue.publish('image-processing', { jobId, file: req.body.file });
  res.status(202).json({ jobId, statusUrl: `/api/jobs/${jobId}` }); // SLA соблюдён
});

// клиент узнаёт о завершении через SSE, не блокируя UI ожиданием
const events = new EventSource(`/api/jobs/${jobId}/stream`);
events.onmessage = (e) => {
  const { status, resultUrl } = JSON.parse(e.data);
  if (status === 'done') showImage(resultUrl);
};
```
