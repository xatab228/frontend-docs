# Инфраструктура и Cloud — Junior

### Что такое облачная архитектура (cloud native), и чем она отличается от классической архитектуры

Классическая архитектура подразумевает развёртывание приложения на заранее выделенных серверах: конфигурация железа фиксирована, масштабирование — ручное и медленное (докупить/арендовать новый сервер), а падение одной машины часто означает простой сервиса. Cloud native — подход, при котором приложение изначально проектируется под облачную инфраструктуру: оно состоит из слабо связанных сервисов, упаковано в контейнеры, масштабируется горизонтально и автоматически (auto-scaling), устойчиво к отказу отдельных инстансов (self-healing) и управляется декларативно через API облака или оркестратора, а не вручную через SSH. Для фронтенд-разработчика это выражается в том, что статика раздаётся через CDN и объектное хранилище (S3-совместимое), а не с одного сервера, а сборка и деплой встроены в CI/CD пайплайн, который сам создаёт нужное число контейнеров под нагрузку.

```yaml
# пример декларативного описания фронтенд-приложения для облака (упрощённый Kubernetes Deployment)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-app
spec:
  replicas: 3            # облако само поддерживает 3 запущенных инстанса
  selector:
    matchLabels: { app: frontend }
  template:
    metadata:
      labels: { app: frontend }
    spec:
      containers:
        - name: frontend
          image: registry.example.com/frontend-app:1.4.0
          ports: [{ containerPort: 80 }]
```

### Простейшие аспекты инфраструктуры (сети, виртуальные машины, контейнеры)

Сеть — совокупность правил и каналов, по которым компьютеры обмениваются данными (IP-адреса, порты, DNS для превращения доменного имени в адрес). Виртуальная машина (VM) — программная эмуляция целого компьютера со своей операционной системой поверх гипервизора, что даёт полную изоляцию, но требует больше ресурсов и времени на старт. Контейнер — изолированный процесс, использующий ядро хостовой ОС, но с собственной файловой системой и сетевым пространством; он легче и стартует за секунды, поэтому контейнеры — стандарт для упаковки и деплоя фронтенд-приложений (например, сборки на Node.js/nginx).

```bash
# базовые сетевые команды, полезные при отладке фронтенд-приложения
ping api.example.com          # проверить доступность хоста
curl -I https://api.example.com   # проверить, отвечает ли сервер и какие заголовки отдаёт
nslookup api.example.com      # узнать, в какой IP резолвится домен
```

### Общие представления об контейнеризации и Docker

Контейнеризация — упаковка приложения вместе со всеми его зависимостями (рантайм, библиотеки, конфигурация) в единый образ, который одинаково запускается на ноутбуке разработчика, в CI и на проде — решается проблема «у меня работает, а на сервере нет». Docker — самый распространённый инструмент контейнеризации: `Dockerfile` описывает, как собрать образ, `docker build` создаёт образ, `docker run` запускает из него контейнер. Для фронтенд-разработчика типичный сценарий — собрать статические файлы (`npm run build`) и упаковать их в лёгкий образ с nginx для раздачи.

```dockerfile
# Dockerfile — простой пример для фронтенд-приложения
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

На практике базовый набор действий с виртуальными машинами и контейнерами выглядит так: подключиться к виртуальной машине по SSH, а на локальной машине — собрать и запустить Docker-контейнер с фронтенд-приложением, используя `Dockerfile` выше.

```bash
# подключение к виртуальной машине
ssh user@192.168.1.10

# сборка и запуск контейнера с собранным фронтенд-приложением
docker build -t frontend-app:latest .
docker run -d -p 8080:80 --name frontend frontend-app:latest

# проверка, что контейнер работает
docker ps
curl http://localhost:8080
```

### Общие представления о работе брокеров сообщений и их роли в архитектуре систем

Брокер сообщений — промежуточный сервис, через который одни части системы (продюсеры) отправляют сообщения, а другие (консьюмеры) их получают и обрабатывают, не обращаясь друг к другу напрямую. Это позволяет разъединить сервисы во времени и в пространстве: отправитель не ждёт, пока получатель обработает сообщение, а если получатель временно недоступен, сообщение просто ждёт в очереди. Примеры брокеров — RabbitMQ, Kafka, ActiveMQ. Во фронтенд-контексте с брокерами напрямую работают редко (это, как правило, backend-инфраструктура), но фронтенд может получать уведомления о событиях, порождённых через брокер, посредством WebSocket или Server-Sent Events, которые backend-сервис транслирует наружу.

### Различия между кэшем в памяти, кэшем на диске и удаленными кешами

Кэш в памяти (in-memory, например переменная в рантайме приложения или `Map` в браузере) — самый быстрый, но исчезает при перезапуске процесса и не разделяется между инстансами. Кэш на диске (например, HTTP-кэш браузера, сохраняющий файлы в файловой системе) переживает перезапуск процесса/вкладки, но медленнее оперативной памяти. Удалённый кэш (Redis, Memcached) хранится на отдельном сервере и доступен сразу нескольким инстансам приложения — это медленнее локального кэша из-за сетевого запроса, зато данные консистентны между всеми репликами backend. Во фронтенде аналог этой иерархии — память JS-приложения (быстро, теряется при обновлении страницы), `localStorage`/IndexedDB (диск браузера, переживает перезагрузку), и HTTP-кэш/CDN (общий для всех пользователей ресурс).
