# Инфраструктура и Cloud — Middle

## Принципы и основные концепции распределенных систем

Распределённая система — набор независимых сервисов, взаимодействующих по сети и вместе образующих единое приложение. Ключевые концепции: отсутствие общей памяти (сервисы обмениваются данными только через сеть, что вносит задержки и вероятность сбоя), необходимость договариваться о согласованности данных между узлами, отказоустойчивость (система должна продолжать работать при падении части узлов) и наблюдаемость (без единого процесса сложно понять, что происходит, без логов/метрик/трейсинга). Для фронтенда распределённость проявляется, например, в том, что один запрос браузера может пройти через CDN, reverse proxy, API Gateway и несколько микросервисов, прежде чем вернётся ответ — и на каждом шаге может возникнуть задержка или ошибка, которую нужно уметь корректно обработать на клиенте (таймауты, ретраи).

## Что такое Reverse Proxy и его роль в доставке контента

Reverse Proxy — сервер, стоящий перед одним или несколькими backend-серверами и принимающий все входящие запросы от клиентов, перенаправляя их дальше по определённым правилам (по пути, домену, заголовку). Роль в доставке контента: терминирование TLS (шифрование/расшифровка HTTPS в одном месте), балансировка нагрузки между несколькими инстансами приложения, раздача статики напрямую с диска (минуя backend), сжатие ответов (gzip/brotli) и кэширование. Самый распространённый reverse proxy для фронтенд-приложений — nginx: он одновременно раздаёт собранный статический бандл и проксирует API-запросы на backend, что избавляет от проблем с CORS в проде.

```nginx
# nginx.conf — reverse proxy перед SPA и API
server {
    listen 80;
    server_name example.com;

    location / {
        root /usr/share/nginx/html;
        try_files $uri /index.html;   # SPA fallback для client-side роутинга
    }

    location /api/ {
        proxy_pass http://backend:4000/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

На практике самый частый сценарий с proxy — настройка dev-сервера, чтобы фронтенд обращался к `/api/*` без проблем с CORS, аналогично тому, как это делает production reverse proxy выше.

```js
// vite.config.js
export default {
  server: {
    proxy: {
      '/api': {
        target: 'https://staging-api.example.com',
        changeOrigin: true,
        secure: false, // для self-signed сертификатов на staging
      },
    },
  },
};
```

## Общий принцип работы CDN (Content Delivery Network)

CDN — сеть географически распределённых серверов (edge-узлов), кэширующих статический (а иногда и динамический) контент ближе к пользователю. Когда браузер запрашивает файл, DNS CDN направляет запрос на ближайший к пользователю edge-сервер; если файл уже закэширован там — он отдаётся немедленно, если нет — edge-сервер запрашивает его у origin-сервера, кэширует и отдаёт, а последующие запросы других пользователей из того же региона обслуживаются уже из кэша. Для фронтенда это резко снижает время загрузки статических ассетов (JS/CSS/изображения/шрифты) и разгружает origin-сервер. Управление кэшированием на CDN выполняется HTTP-заголовками.

```http
Cache-Control: public, max-age=31536000, immutable   # для файлов с хэшем в имени (main.a1b2c3.js)
Cache-Control: no-cache                               # для index.html, чтобы всегда проверять актуальность
```

## Принципы контейнеризации и оркестрации

Контейнеризация упаковывает приложение и его зависимости в переносимый образ (см. Docker). Оркестрация — управление множеством контейнеров в продакшене: автоматический запуск нужного числа реплик, перезапуск упавших контейнеров, распределение нагрузки между ними, раскатка новых версий без простоя (rolling update) и обнаружение сервисов друг другом. Kubernetes — самый распространённый оркестратор: он оперирует декларативными манифестами (сколько реплик, какой образ, какие ресурсы) и сам приводит реальное состояние кластера к описанному.

```yaml
# упрощённый пример service + deployment для фронтенд-приложения в Kubernetes
apiVersion: v1
kind: Service
metadata: { name: frontend-svc }
spec:
  selector: { app: frontend }
  ports: [{ port: 80, targetPort: 80 }]
  type: ClusterIP
```

На практике сборка и запуск Docker-образа выглядят так:

```bash
docker build -t frontend-app:1.0 .
docker run --rm -p 3000:80 frontend-app:1.0
docker images        # посмотреть список собранных образов
docker logs -f <container_id>   # посмотреть логи запущенного контейнера
```

## Архитектура и принципы работы брокеров сообщений (Kafka, RabbitMQ/ActiveMQ)

**RabbitMQ / ActiveMQ** реализуют классическую модель очередей: продюсер публикует сообщение в exchange, exchange маршрутизирует его в одну или несколько очередей по правилам (direct, topic, fanout), консьюмер читает и подтверждает обработку (ack), после чего сообщение удаляется. Модель хорошо подходит для задач и уведомлений.

**Kafka** устроена иначе: это распределённый лог событий, разбитый на партиции. Продюсеры дописывают сообщения в конец партиции, консьюмеры читают их в своём темпе, и сообщение не удаляется после прочтения — оно хранится заданное время и может быть прочитано повторно любым числом независимых консьюмеров. Отсюда пригодность Kafka для event streaming и восстановления состояния из истории событий.

Для фронтенда оба брокера обычно скрыты за backend-сервисом: до клиента события доходят через WebSocket/SSE-шлюз, который backend поднимает поверх подписки на очередь или топик.

На практике публикация сообщения в RabbitMQ из Node.js-сервиса — типичный случай, когда фронтенд-команда поддерживает свой BFF/edge-сервис:

```js
import amqp from 'amqplib';

async function sendMessage() {
  const conn = await amqp.connect('amqp://localhost');
  const channel = await conn.createChannel();
  const queue = 'user.events';

  await channel.assertQueue(queue, { durable: true });
  channel.sendToQueue(queue, Buffer.from(JSON.stringify({ type: 'PAGE_VIEW', userId: 42 })));

  await channel.close();
  await conn.close();
}
```

## Принципы кеширования для улучшения производительности приложения

Кеширование — сохранение результата дорогой операции (сетевого запроса, вычисления, рендера) для повторного использования без повторного выполнения этой операции. Ключевые принципы: у каждой закэшированной записи должен быть срок жизни (TTL) или явный механизм инвалидации, иначе пользователь увидит устаревшие данные; кэшировать стоит то, что запрашивается часто и меняется редко; уровень кэширования выбирается по месту, ближайшему к потребителю (браузер → CDN → reverse proxy → приложение → БД), поскольку чем ближе кэш к пользователю, тем меньше задержка. Во фронтенде кеширование применяется на уровне HTTP (`Cache-Control`, `ETag`), на уровне запросов к API (React Query/SWR кэшируют ответы в памяти) и на уровне офлайн-хранилища (Service Worker + Cache API).

## Распространенные инструменты кеширования (Redis, Memcached)

Redis — key-value хранилище в памяти с богатым набором структур данных (строки, хэши, списки, множества, sorted set), поддержкой персистентности на диск, TTL для ключей и pub/sub — используется как кэш ответов API, хранилище сессий и брокер для очередей задач. Memcached — более простое и легковесное key-value хранилище только строк в памяти, без персистентности, оптимизированное под максимальную скорость простых операций get/set — используется, когда не нужна сложная структура данных, а важна минимальная задержка. С точки зрения фронтенд-разработчика оба инструмента чаще всего видны косвенно — через заголовок `X-Cache: HIT/MISS` в ответе API или через ускорение повторных запросов, но иногда фронтенд-разработчик настраивает их напрямую при работе с BFF (Backend for Frontend).

```js
// пример использования Redis как кэша в BFF-слое (Node.js, ioredis)
import Redis from 'ioredis';
const redis = new Redis();

async function getProduct(id) {
  const cached = await redis.get(`product:${id}`);
  if (cached) return JSON.parse(cached);

  const product = await fetch(`https://api.internal/products/${id}`).then(r => r.json());
  await redis.set(`product:${id}`, JSON.stringify(product), 'EX', 60); // TTL 60 секунд
  return product;
}
```

Базовый паттерн cache-aside выше (проверить кэш → при промахе сходить в источник → записать в кэш) на практике дополняется явной инвалидацией при изменении данных:

```js
async function updateProduct(id, data) {
  await api.put(`/products/${id}`, data);
  await redis.del(`product:${id}`); // инвалидация устаревшего кэша после изменения
}
```
