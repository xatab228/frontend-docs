# Инфраструктура и Cloud — Senior

### Методы и подходы проектирования распределенных систем (сервисы с балансировкой нагрузки, sidecar, двухфазный коммит, разделение запросов по типам данных)

Балансировка нагрузки распределяет входящие запросы между несколькими инстансами сервиса (round-robin, least-connections, по хэшу клиента для sticky-сессий), повышая пропускную способность и отказоустойчивость. Sidecar — вспомогательный контейнер, запускаемый рядом с основным сервисом в одном поде и берущий на себя сквозные задачи (mTLS, логирование, ретраи, сбор метрик), не затрагивая код самого сервиса — основа паттерна service mesh (Istio, Linkerd). Двухфазный коммит (2PC) — протокол согласования транзакции между несколькими узлами: на фазе prepare координатор спрашивает всех участников, готовы ли они закоммитить, и только если все ответили "да", на фазе commit транзакция подтверждается везде; минус — блокировка ресурсов на время согласования и уязвимость к падению координатора. Разделение запросов по типам данных — маршрутизация запросов на чтение и запись на разные бэкенды (например, чтение — из read-реплики или кэша, запись — в мастер-БД), что снижает нагрузку на основной источник данных. Для фронтенда эти паттерны важны при проектировании BFF-слоя: например, sidecar-прокси перед BFF может сам добавлять трейсинг-заголовки, не требуя изменений в коде BFF.

### Методы отладки распределенных систем

Основной инструмент — distributed tracing: каждому входящему запросу присваивается уникальный `trace-id`, который прокидывается через все сервисы в заголовках (`traceparent` из стандарта W3C Trace Context), а каждый сервис добавляет свой `span` с временными метками, что позволяет собрать полную карту прохождения запроса и найти, на каком шаге возникла задержка или ошибка. Дополняют трейсинг централизованные логи (агрегация через ELK/Loki с возможностью фильтрации по `trace-id`) и метрики (RED-метрики: Rate, Errors, Duration на каждый сервис). Фронтенд-разработчик участвует в этом, прокидывая `trace-id` из ответа backend в свои логи ошибок и добавляя его в заголовки исходящих запросов, если несколько фронтенд-сервисов вызывают друг друга (например, BFF → микросервис).

```js
// проброс trace-id, полученного от backend, в последующий запрос
const traceId = response.headers.get('x-trace-id');
fetch('/api/next-step', { headers: { 'x-trace-id': traceId } });
```

### Подходы к настройке балансировщиков нагрузки и прокси

Балансировщик может работать на L4 (транспортный уровень, балансирует TCP-соединения без анализа содержимого — быстрее) или L7 (прикладной уровень, видит HTTP-заголовки/путь и может маршрутизировать по ним, добавлять заголовки, терминировать TLS). Алгоритмы: round-robin (по очереди), least-connections (туда, где меньше активных соединений), ip-hash (один клиент всегда попадает на один и тот же backend — нужно для sticky-сессий WebSocket). Health checks регулярно опрашивают backend-инстансы и исключают из ротации неотвечающие.

```nginx
upstream backend_pool {
    least_conn;
    server backend1.internal:4000 max_fails=3 fail_timeout=30s;
    server backend2.internal:4000 max_fails=3 fail_timeout=30s;
}

server {
    location /api/ {
        proxy_pass http://backend_pool;
        proxy_next_upstream error timeout http_502;  # ретрай на другой инстанс при ошибке
    }
}
```

### Подходы к CDN (edge computing, content routing)

Edge computing — выполнение не только статической раздачи, но и вычислений непосредственно на edge-узле CDN, максимально близко к пользователю (Cloudflare Workers, Vercel Edge Functions, AWS Lambda@Edge): это позволяет персонализировать ответ, переписывать заголовки, делать A/B-редиректы или даже частичный SSR без похода на origin-сервер, снижая задержку. Content routing — правила, по которым CDN решает, откуда и как отдавать контент: geo-routing (ближайший дата-центр), routing по типу устройства/заголовкам, failover на резервный origin при недоступности основного.

```js
// пример edge-функции: A/B-редирект прямо на CDN, без похода на origin
export default {
  async fetch(request) {
    const bucket = Math.random() < 0.5 ? 'a' : 'b';
    const url = new URL(request.url);
    url.searchParams.set('variant', bucket);
    return fetch(url, request);
  },
};
```

### Принципы масштабирования и балансировки нагрузки в Kubernetes или другом оркестраторе

Kubernetes масштабирует поды горизонтально (Horizontal Pod Autoscaler) на основе метрик — обычно CPU/памяти, но можно и по кастомным метрикам (например, RPS через Prometheus Adapter). Service — стабильная точка входа с встроенной L4-балансировкой между всеми подами с нужным label; Ingress добавляет L7-маршрутизацию по домену/пути и терминирование TLS перед сервисами.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: frontend-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: frontend }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
```

### Принципы управления данными в брокере сообщений

В Kafka управление данными строится вокруг партиционирования (сообщения с одним ключом всегда попадают в одну партицию, что гарантирует порядок в её пределах), retention (сколько времени/места хранить сообщения до удаления, независимо от того, прочитаны ли они) и consumer group (несколько консьюмеров делят партиции между собой для параллельной обработки, при этом offset — позиция чтения — хранится отдельно на консьюмера/группу, что позволяет перечитать историю). В RabbitMQ управление данными строится вокруг durable-очередей (переживают перезапуск брокера), persistent-сообщений (пишутся на диск) и политик TTL/dead-letter exchange для сообщений, которые не удалось обработать. Общий принцип для обеих систем — акты подтверждения (ack/nack) определяют, когда сообщение считается успешно обработанным и может быть удалено или закоммичен offset.

### Различные стратегии кеширования (Write-Through, Write-Behind, Cache-Aside)

Cache-Aside (Lazy Loading) — приложение само проверяет кэш, при промахе читает из источника и кладёт в кэш (пример из Middle-уровня); просто в реализации, но первый запрос всегда медленный, а данные могут временно расходиться с источником до истечения TTL. Write-Through — запись сразу идёт и в кэш, и в источник данных синхронно, поэтому кэш никогда не устаревает, но каждая запись становится медленнее из-за двойной операции. Write-Behind (Write-Back) — запись сначала попадает только в кэш, а в источник данных сбрасывается асинхронно батчами позже — быстрая запись, но риск потери данных при падении кэша до сброса. Выбор зависит от требований: для часто читаемых, редко меняемых данных — Cache-Aside; для данных, где недопустима рассинхронизация кэша и источника, — Write-Through; для высокочастотной записи с допустимой задержкой согласованности — Write-Behind.

```js
// Write-Through: запись синхронно идёт и в БД, и в кэш
async function updateUserWriteThrough(id, data) {
  await db.users.update(id, data);
  await redis.set(`user:${id}`, JSON.stringify(data));
}
```

### Настраивать и использовать инструменты кеширования

Настройка Redis как кэша сессий/API-ответов в BFF-слое с явным TTL и инвалидацией была показана на Middle-уровне; на Senior-уровне добавляется выбор конкретной стратегии под задачу (см. ниже) и мониторинг hit-rate через `INFO stats` Redis.

### Выбирать подходящую стратегию кеширования в зависимости от требований проекта

Каталог товаров с редкими изменениями и высокой читаемостью → Cache-Aside с TTL в несколько минут. Профиль пользователя, который должен быть мгновенно консистентен после правки в личном кабинете → Write-Through. Массовое логирование событий аналитики от фронтенда → Write-Behind, чтобы не блокировать пользовательский запрос на запись в БД.

### Использовать Kubernetes и другие оркестраторы для построения масштабируемых кластеров

Комбинация Deployment (из Middle-уровня), Service, Ingress и HorizontalPodAutoscaler (см. выше) образует полностью масштабируемое развёртывание: Ingress принимает трафик снаружи, Service балансирует между подами, HPA добавляет/убирает поды по нагрузке.

### Проектировать event-driven и message-driven архитектуры с использованием брокеров сообщений

```js
// пример: фронтенд-BFF публикует событие в Kafka при действии пользователя,
// а отдельный consumer-сервис асинхронно его обрабатывает
import { Kafka } from 'kafkajs';

const kafka = new Kafka({ clientId: 'bff', brokers: ['kafka:9092'] });
const producer = kafka.producer();

async function publishUserAction(userId, action) {
  await producer.connect();
  await producer.send({
    topic: 'user-actions',
    messages: [{ key: String(userId), value: JSON.stringify({ action, ts: Date.now() }) }],
  });
}
```

Такая архитектура развязывает BFF от сервисов-обработчиков: BFF не ждёт завершения обработки и может быстро ответить пользователю, а число подписчиков на топик можно наращивать независимо.
