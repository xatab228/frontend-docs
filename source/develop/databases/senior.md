### Уровни изоляции транзакций (Read Uncommitted, Read Committed, Repeatable Read, Serializable)

Уровни изоляции регулируют компромисс между согласованностью параллельных транзакций и производительностью, определяя, какие аномалии допустимы. Read Uncommitted — транзакция видит незафиксированные изменения других транзакций (dirty read), самый слабый и редко используемый уровень. Read Committed (по умолчанию в PostgreSQL) — транзакция видит только зафиксированные данные, но повторное чтение той же строки в рамках одной транзакции может дать другой результат, если другая транзакция успела закоммититься между чтениями (non-repeatable read). Repeatable Read (по умолчанию в MySQL/InnoDB) — гарантирует, что повторное чтение той же строки в рамках транзакции всегда даёт одинаковый результат, но допускает phantom read (повторный запрос с условием `WHERE` может вернуть новые строки, добавленные другой транзакцией). Serializable — самый строгий уровень, гарантирующий, что результат параллельного выполнения транзакций эквивалентен их последовательному выполнению в каком-то порядке; исключает все аномалии, но ценой производительности (больше блокировок или откатов по конфликту).

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1; -- прочитано 100
-- другая транзакция коммитит UPDATE accounts SET balance = 200 WHERE id = 1
SELECT balance FROM accounts WHERE id = 1; -- всё ещё 100 благодаря Repeatable Read
COMMIT;
```

### О транзакционной обработке в SQL и способности обрабатывать ошибки, используя транзакции для обеспечения целостности данных

Транзакционная обработка ошибок строится на том, что любая ошибка внутри блока транзакции (нарушение constraint, deadlock, явное исключение в коде приложения) должна приводить к полному откату (`ROLLBACK`), а не к частичному применению изменений — это прямое следствие атомарности из ACID. На практике для сложных многошаговых операций используются savepoints — промежуточные точки внутри транзакции, позволяющие откатить только часть операций, не прерывая всю транзакцию целиком. Retry-логика для транзакций, упавших из-за serialization failure на уровне Serializable, — стандартная практика: приложение перехватывает специфичную ошибку БД и повторяет транзакцию, поскольку такой отказ означает конфликт с другой параллельной транзакцией, а не ошибку данных.

```sql
BEGIN;
INSERT INTO orders (user_id, total) VALUES (1, 150.00);
SAVEPOINT before_items;

INSERT INTO order_items (order_id, product_id, qty) VALUES (LASTVAL(), 999, 1); -- допустим, упало (product_id не существует)
ROLLBACK TO SAVEPOINT before_items; -- откатываем только order_items, заказ остаётся

COMMIT;
```

### Принципы индексации и оптимизации запросов в NoSQL базах данных

В документоориентированных БД (MongoDB) оптимизация запросов начинается с анализа плана выполнения через `explain()`, показывающего, использовался ли индекс (`IXSCAN`) или произошло полное сканирование коллекции (`COLLSCAN`). Ключевой принцип построения составных индексов — правило ESR (Equality, Sort, Range): поля с точным совпадением идут первыми в индексе, затем поля сортировки, затем поля диапазонной фильтрации, что позволяет БД максимально эффективно использовать структуру индекса. В отличие от реляционных БД, в NoSQL также важно проектирование самой схемы под паттерн доступа (embedding vs referencing) — денормализация (встраивание связанных данных прямо в документ) часто предпочтительнее `$lookup` (аналог `JOIN` в MongoDB), так как соединения в документных БД дороже, чем в реляционных.

```js
// Индекс по правилу ESR: status (equality) → createdAt (sort) → total (range)
db.orders.createIndex({ status: 1, createdAt: -1, total: 1 });

db.orders.find({ status: "shipped", total: { $gt: 100 } })
  .sort({ createdAt: -1 })
  .explain("executionStats"); // проверка, использован ли индекс
```

### Принципы и особенности горизонтального и вертикального масштабирования

Горизонтальное масштабирование БД усложняется тем, что данные и запросы нужно распределять между узлами так, чтобы сохранить производительность и согласованность — отсюда возникают паттерны шардирования (распределение данных по ключу шардирования) и репликации (см. ниже), а также необходимость выбирать между строгой и eventual-согласованностью при чтении с реплик. Вертикальное масштабирование БД проще операционно (не требует изменения логики приложения), но упирается в физические лимиты одного сервера и создаёт риск длительного простоя при апгрейде (не растёт «на лету» без даунтайма в большинстве конфигураций). На практике зрелые системы комбинируют оба подхода: вертикально масштабируют, пока это экономически оправдано, и переходят к горизонтальному масштабированию (шардирование + реплики для чтения) при достижении пределов одного узла или требований по отказоустойчивости.

### Различия между репликацией, шардированием и партиционированием

Репликация — копирование одних и тех же данных на несколько серверов (реплик) для повышения доступности (при падении одной реплики данные остаются доступны на других) и распределения нагрузки на чтение (реплики для чтения, один primary для записи); не решает проблему объёма данных, так как каждая реплика хранит полный набор данных. Шардирование (sharding) — разделение данных по разным серверам по ключу шардирования (shard key), так что каждый сервер хранит только часть данных — решает проблему объёма и нагрузки на запись, но усложняет запросы, затрагивающие несколько шардов, и требует продуманного выбора ключа шардирования, чтобы избежать «горячих» шардов. Партиционирование (partitioning) — разделение данных на части в пределах одного сервера/БД (например, по диапазону дат или хешу), что ускоряет запросы и обслуживание (можно удалить целую партицию вместо миллионов `DELETE`), но, в отличие от шардирования, не распределяет нагрузку между физическими серверами.

```sql
-- Партиционирование по диапазону дат (PostgreSQL) — в пределах одной БД
CREATE TABLE events (
  id BIGINT,
  created_at DATE NOT NULL,
  payload JSONB
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
```

```
Шардирование (MongoDB) — данные распределены по разным физическим серверам по shard key
Shard A: users с userId % 3 == 0
Shard B: users с userId % 3 == 1
Shard C: users с userId % 3 == 2
```

### Использовать и настраивать разные уровни изоляции транзакций

Практическая настройка уровня изоляции под конкретный сценарий — резервирование последнего билета на мероприятие требует Serializable, чтобы исключить продажу одного места двум покупателям одновременно:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT available_seats FROM events WHERE id = 1 FOR UPDATE;
-- если available_seats > 0:
UPDATE events SET available_seats = available_seats - 1 WHERE id = 1;
INSERT INTO tickets (event_id, user_id) VALUES (1, 42);

COMMIT;
-- при конфликте с параллельной транзакцией СУБД вернёт serialization_failure —
-- приложение обязано перехватить её и повторить транзакцию (retry)
```

### Проектировать нормализованную схему реляционной базы данных

Применение принципов нормализации (1NF из junior.md плюс устранение частичных и транзитивных зависимостей до 3NF) на схеме интернет-магазина — вынесение категории товара в отдельную таблицу вместо дублирования её названия в каждой строке товара:

```sql
-- Ненормализовано: название категории дублируется в каждой строке товара
-- products: id, name, category_name, category_description

-- Нормализовано до 3NF: категория вынесена, зависимости только от первичного ключа
CREATE TABLE categories (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  description TEXT
);

CREATE TABLE products (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(200) NOT NULL,
  category_id INT NOT NULL,
  FOREIGN KEY (category_id) REFERENCES categories(id)
);
```

Проектирование схемы и CRUD-операций для коллекции заказов в MongoDB с использованием денормализации (см. принцип embedding из раздела про индексацию NoSQL выше):

### Писать сложные SQL-запросы с использованием условий, сортировки, группировки, объединений, агрегатных функций и подзапросов

Отчётный запрос, комбинирующий подзапрос, `JOIN`, группировку и оконную функцию — топ-3 самых дорогих заказа по каждому пользователю:

```sql
SELECT name, order_id, total
FROM (
  SELECT
    users.name,
    orders.id AS order_id,
    orders.total,
    ROW_NUMBER() OVER (PARTITION BY users.id ORDER BY orders.total DESC) AS rank
  FROM users
  INNER JOIN orders ON orders.user_id = users.id
  WHERE orders.status = 'completed'
) ranked
WHERE rank <= 3
ORDER BY name, total DESC;
```

### Создавать и использовать хранимые процедуры, функции и триггеры для обработки данных на стороне сервера баз данных

Триггер, автоматически поддерживающий кэшированный счётчик заказов пользователя при вставке новой записи, и хранимая процедура для оформления заказа целиком на стороне БД:

```sql
-- Триггер: автоматическое обновление счётчика при новом заказе
CREATE TRIGGER trg_increment_order_count
AFTER INSERT ON orders
FOR EACH ROW
UPDATE users SET orders_count = orders_count + 1 WHERE id = NEW.user_id;

-- Хранимая процедура: оформление заказа с проверкой остатка на складе
DELIMITER //
CREATE PROCEDURE place_order(IN p_user_id INT, IN p_product_id INT, IN p_qty INT)
BEGIN
  DECLARE current_stock INT;
  SELECT stock INTO current_stock FROM products WHERE id = p_product_id FOR UPDATE;

  IF current_stock < p_qty THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Недостаточно товара на складе';
  END IF;

  UPDATE products SET stock = stock - p_qty WHERE id = p_product_id;
  INSERT INTO orders (user_id, product_id, qty) VALUES (p_user_id, p_product_id, p_qty);
END //
DELIMITER ;

CALL place_order(42, 7, 2);
```
