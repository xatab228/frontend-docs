# Базы данных — Middle

### Основные принципы ACID (Atomicity, Consistency, Isolation, Durability)

ACID — набор гарантий, обеспечиваемых транзакциями в реляционных БД. Atomicity (атомарность) — транзакция выполняется целиком или не выполняется вообще: если один из шагов упал, все изменения откатываются (`ROLLBACK`). Consistency (согласованность) — транзакция переводит базу из одного валидного состояния в другое, не нарушая ограничения (constraints, внешние ключи, уникальность). Isolation (изолированность) — параллельно выполняющиеся транзакции не видят промежуточных, незафиксированных изменений друг друга (степень изоляции настраивается уровнями, см. senior.md). Durability (устойчивость) — после успешного коммита (`COMMIT`) изменения сохраняются даже при сбое питания или падении сервера сразу после подтверждения. Классический пример, где нужны все четыре свойства — банковский перевод: списание с одного счёта и зачисление на другой должны либо произойти оба, либо ни один.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT; -- если между этими шагами произойдёт сбой, вся транзакция откатится (Atomicity)
```

На практике это выглядит так — реализация перевода средств между счетами с явной обработкой ошибок и откатом, применяющая атомарность из описания выше:

```js
// Node.js + pg (PostgreSQL)
async function transferFunds(client, fromId, toId, amount) {
  try {
    await client.query('BEGIN');
    const { rows } = await client.query(
      'SELECT balance FROM accounts WHERE id = $1 FOR UPDATE', [fromId] // блокировка строки
    );
    if (rows[0].balance < amount) throw new Error('Insufficient funds');

    await client.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, fromId]);
    await client.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toId]);
    await client.query('COMMIT');
  } catch (err) {
    await client.query('ROLLBACK'); // атомарность: откат при любой ошибке
    throw err;
  }
}
```

### Назначения и принципы ограничений (constraints)

Ограничения (constraints) — правила на уровне схемы БД, гарантирующие целостность данных независимо от того, какое приложение и как их записывает. Основные виды: `NOT NULL` (значение обязательно), `UNIQUE` (значения в столбце не повторяются), `PRIMARY KEY` (комбинация `NOT NULL` + `UNIQUE`, идентифицирует строку), `FOREIGN KEY` (значение обязано существовать в связанной таблице), `CHECK` (произвольное булево условие на значение), `DEFAULT` (значение по умолчанию, если не указано явно). Ограничения — последний рубеж защиты целостности данных: даже если валидация на фронтенде или бэкенде пропустит некорректные данные из-за бага, БД физически не позволит их сохранить.

```sql
CREATE TABLE products (
  id INT PRIMARY KEY AUTO_INCREMENT,
  sku VARCHAR(50) NOT NULL UNIQUE,
  price DECIMAL(10, 2) NOT NULL CHECK (price >= 0),
  stock INT NOT NULL DEFAULT 0,
  category_id INT,
  FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE SET NULL
);
```

На практике эти ограничения применяются при проектировании схемы — например, для блога с отношением один-ко-многим (пользователь → статьи) и многие-ко-многим (статьи ↔ теги через промежуточную таблицу):

```sql
CREATE TABLE users (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL
);

CREATE TABLE articles (
  id INT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(255) NOT NULL,
  author_id INT NOT NULL,
  FOREIGN KEY (author_id) REFERENCES users(id) -- один-ко-многим: у пользователя много статей
);

CREATE TABLE tags (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE article_tags ( -- связующая таблица для многие-ко-многим
  article_id INT NOT NULL,
  tag_id INT NOT NULL,
  PRIMARY KEY (article_id, tag_id),
  FOREIGN KEY (article_id) REFERENCES articles(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id) REFERENCES tags(id) ON DELETE CASCADE
);
```

### Основные термины и концепции NoSQL (коллекция, документ, ключ-значение)

Коллекция (collection) — аналог таблицы в документоориентированных БД (например, MongoDB), группа документов, обычно относящихся к одной сущности, но, в отличие от таблицы, без обязательной единой схемы для всех документов внутри. Документ (document) — аналог строки, но представляет собой самодостаточную структуру (обычно JSON/BSON), способную содержать вложенные объекты и массивы, что позволяет хранить связанные данные в одной записи без `JOIN`. Модель ключ-значение (key-value) — простейшая модель, где данные адресуются по уникальному ключу без какой-либо внутренней структуры значения с точки зрения БД (значением может быть строка, число, сериализованный объект); Redis — характерный пример.

```js
// Документ в коллекции orders (MongoDB) — вложенные данные без JOIN
{
  _id: ObjectId("..."),
  userId: 42,
  items: [
    { productId: 7, qty: 2, price: 19.99 },
    { productId: 3, qty: 1, price: 49.99 },
  ],
  status: "shipped",
}
```

### Семейства NoSQL-баз данных и особенности каждой, принципы BASE

Четыре основных семейства: документоориентированные (MongoDB, CouchDB — гибкая вложенная структура), ключ-значение (Redis, DynamoDB — максимальная простота и скорость), колоночные/wide-column (Cassandra, HBase — оптимизированы под запись огромных объёмов и запросы по диапазону ключа), графовые (Neo4j — оптимизированы под запросы по связям между сущностями, например социальные графы или рекомендательные системы). Принцип BASE (Basically Available, Soft state, Eventually consistent) — альтернатива ACID, характерная для многих NoSQL-систем: система остаётся доступной почти всегда (Basically Available) даже ценой временной несогласованности, промежуточное состояние может быть неконсистентным (Soft state), но система гарантированно приходит к согласованному состоянию через некоторое время без новых записей (Eventually consistent). BASE выбирается осознанно в системах, где доступность и скорость важнее мгновенной согласованности — например, счётчик лайков может на секунду отличаться на разных репликах.

### Теорему CAP и ее применение к NoSQL БД

Теорема CAP утверждает, что распределённая система не может одновременно гарантировать все три свойства при наличии сетевого разрыва (partition): Consistency (все узлы видят одинаковые данные в любой момент), Availability (система отвечает на каждый запрос, даже если часть узлов недоступна), Partition Tolerance (система продолжает работать при разрыве сети между узлами). Поскольку разрывы сети в распределённых системах неизбежны, Partition Tolerance фактически обязателен, и реальный выбор — между C и A: CP-системы (например, MongoDB в конфигурации с сильной согласованностью, HBase) при разрыве сети откажут в ответе, но не отдадут устаревшие данные; AP-системы (Cassandra, DynamoDB по умолчанию) продолжат отвечать даже при разрыве, допуская временную рассогласованность между узлами. Выбор между CP и AP определяется бизнес-требованиями: для баланса банковского счёта критична консистентность (CP), для ленты соцсети временная рассогласованность приемлема ради доступности (AP).

### Общее понимание горизонтального и вертикального масштабирования

Вертикальное масштабирование (scale up) — увеличение мощности одного сервера (больше CPU, RAM, более быстрый диск); просто в реализации (не требует изменений в архитектуре приложения), но имеет физический потолок и создаёт единую точку отказа. Горизонтальное масштабирование (scale out) — добавление большего числа серверов, между которыми распределяется нагрузка/данные; практически неограниченно и повышает отказоустойчивость, но требует архитектуры, спроектированной под распределённость (партиционирование данных, согласованность между узлами, балансировка нагрузки) — именно поэтому многие NoSQL-системы изначально проектировались с прицелом на горизонтальное масштабирование, тогда как классические реляционные БД исторически проще масштабировать вертикально.

### Различия в индексации между реляционными базами данных, NoSQL хранилищами и поисковыми движками

В реляционных БД индексы (обычно B-tree) строятся на конкретных столбцах и ускоряют точный поиск, диапазонные запросы и сортировку, но требуют явного проектирования под ожидаемые запросы. В документоориентированных NoSQL БД (MongoDB) индексы работают похожим образом, но могут строиться и на вложенных полях документа, а также поддерживают специализированные типы — например, составные индексы по нескольким полям с учётом порядка обращения в запросах. Поисковые движки (Elasticsearch, Algolia) используют принципиально другую структуру — инвертированный индекс (inverted index), сопоставляющий каждое слово списку документов, где оно встречается, что оптимизировано под полнотекстовый поиск, релевантность и нечёткое совпадение — задачу, для которой B-tree индексы реляционных БД плохо приспособлены.

```js
// MongoDB: составной индекс — ускоряет запросы, фильтрующие по обоим полям вместе
db.orders.createIndex({ userId: 1, status: 1 });
```

На практике выбор подходящего индекса зависит от типа данных и операций: для колонки, часто используемой в точном поиске и `JOIN` (`author_id`), подходит обычный B-tree индекс; для колонки, по которой часто ищут диапазоном или сортируют (`created_at`), также используется B-tree; а для полнотекстового поиска по содержимому статьи — специализированный полнотекстовый индекс вместо обычного:

```sql
CREATE INDEX idx_articles_author_id ON articles(author_id);      -- ускоряет JOIN и точный поиск
CREATE INDEX idx_articles_created_at ON articles(created_at);    -- ускоряет ORDER BY / диапазонные запросы

-- Полнотекстовый индекс — для поиска по содержимому, где обычный B-tree неэффективен
CREATE FULLTEXT INDEX idx_articles_content ON articles(content);
SELECT * FROM articles WHERE MATCH(content) AGAINST('database indexing' IN NATURAL LANGUAGE MODE);
```

Составной индекс создаётся, когда запрос регулярно фильтрует по нескольким полям одновременно (аналогично примеру MongoDB из раздела про индексацию выше), с порядком столбцов, соответствующим порядку фильтрации в реальных запросах приложения.
