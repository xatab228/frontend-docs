# Базы данных — Junior

### Основные понятия реляционных баз данных (таблицы, поля, primary/foreign key и т.д.)

Реляционная база данных хранит данные в виде таблиц (relations), где каждая строка (row/record) — отдельная запись, а каждый столбец (column/field) — атрибут этой записи определённого типа. Первичный ключ (primary key) — столбец или набор столбцов, однозначно идентифицирующих строку в таблице (значения не повторяются и не бывают `NULL`). Внешний ключ (foreign key) — столбец, ссылающийся на первичный ключ другой (или той же) таблицы, устанавливающий связь между записями и обеспечивающий ссылочную целостность (нельзя вставить заказ со ссылкой на несуществующего пользователя). Эти связи — основа того, как реляционная модель избегает дублирования данных, разбивая информацию на связанные таблицы вместо одной плоской.

```sql
CREATE TABLE users (
  id INT PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE orders (
  id INT PRIMARY KEY AUTO_INCREMENT,
  user_id INT NOT NULL,
  total DECIMAL(10, 2),
  FOREIGN KEY (user_id) REFERENCES users(id) -- связь orders → users
);
```

### Концепция нормализация данных до первой нормальной формы

Нормализация — процесс организации данных в таблицах для устранения избыточности и аномалий при изменении данных. Первая нормальная форма (1NF) требует, чтобы: каждая ячейка содержала атомарное (неделимое) значение, а не список или составную структуру; все значения в столбце были одного типа; и в таблице существовал первичный ключ, однозначно идентифицирующий строку. Таблица, где в одном поле через запятую хранится несколько телефонов пользователя, нарушает 1NF — такие данные нужно вынести в отдельную таблицу со связью один-ко-многим.

```
-- Нарушает 1NF: составное значение в одной ячейке
| id | name  | phones               |
| 1  | Alice | 111-222, 333-444     |

-- Соответствует 1NF: атомарные значения, связь через отдельную таблицу
users:  | id | name  |
        | 1  | Alice |

phones: | id | user_id | phone     |
        | 1  | 1       | 111-222   |
        | 2  | 1       | 333-444   |
```

На практике, взяв «плохую» таблицу с составными значениями из примера выше, приведение к 1NF выполняется разбиением на две связанные таблицы: основную сущность и таблицу для многозначного атрибута со ссылкой на неё через внешний ключ.

```sql
-- До 1NF (составное значение в phones недопустимо)
-- users_bad: id, name, phones ("111-222, 333-444")

-- После нормализации до 1NF
CREATE TABLE users (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100)
);

CREATE TABLE phones (
  id INT PRIMARY KEY AUTO_INCREMENT,
  user_id INT NOT NULL,
  phone VARCHAR(20) NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

INSERT INTO users (id, name) VALUES (1, 'Alice');
INSERT INTO phones (user_id, phone) VALUES (1, '111-222'), (1, '333-444');
```

### Примеры нереляционных баз данных (MongoDB, Redis, Cassandra и др.), отличие от реляционных и области применения

Нереляционные (NoSQL) базы данных отказываются от строгой табличной структуры и жёстких связей ради гибкости схемы и производительности при определённых паттернах доступа.

- **MongoDB** — документоориентированная БД: данные хранятся как JSON-подобные документы (BSON) без обязательной единой схемы для всех документов коллекции. Подходит для быстро меняющихся, слабоструктурированных данных — например, профилей пользователей с разным набором полей.
- **Redis** — хранилище ключ-значение, держащее данные преимущественно в оперативной памяти, отсюда крайне низкая задержка. Применяется как кэш, хранилище сессий, очередь сообщений.
- **Cassandra** — колоночная (wide-column) БД для линейного горизонтального масштабирования и высокой доступности при записи огромных объёмов данных (телеметрия, логи), ценой более слабых гарантий согласованности.

Общее отличие от реляционных БД: там схема фиксирована, а данные нормализованы; NoSQL-решения жертвуют частью строгости и согласованности ради скорости разработки, гибкости схемы или горизонтальной масштабируемости.

```js
// MongoDB — документ без жёсткой схемы
{
  _id: ObjectId("..."),
  name: "Alice",
  tags: ["admin", "beta-tester"],
  address: { city: "Berlin", zip: "10115" }
}
```

```
# Redis — ключ-значение
SET session:abc123 '{"userId": 42}' EX 3600   # с TTL в 3600 секунд
GET session:abc123
```

### Базовые операторы SQL (SELECT, INSERT, UPDATE, DELETE) и функции (joins, group by, aggregate functions)

`SELECT` читает данные, `INSERT` добавляет новую строку, `UPDATE` изменяет существующие строки, `DELETE` удаляет строки — четыре базовые CRUD-операции SQL. `JOIN` объединяет строки из нескольких таблиц по условию связи (чаще всего по внешнему ключу): `INNER JOIN` возвращает только совпадающие строки в обеих таблицах, `LEFT JOIN` — все строки левой таблицы плюс совпадения из правой (или `NULL`, если совпадений нет). `GROUP BY` группирует строки с одинаковым значением столбца для последующего применения агрегатных функций (`COUNT`, `SUM`, `AVG`, `MAX`, `MIN`), которые вычисляют одно значение по группе строк.

```sql
SELECT * FROM users WHERE id = 1;
INSERT INTO users (email) VALUES ('alice@example.com');
UPDATE users SET email = 'new@example.com' WHERE id = 1;
DELETE FROM users WHERE id = 1;

-- JOIN + GROUP BY + агрегатная функция: сумма заказов по каждому пользователю
SELECT users.name, COUNT(orders.id) AS orders_count, SUM(orders.total) AS total_spent
FROM users
LEFT JOIN orders ON orders.user_id = users.id
GROUP BY users.id, users.name;
```

На практике эти операторы и функции комбинируются в реальных задачах — например, получить список пользователей с числом заказов, отсортированный по сумме потраченных денег, только для тех, кто сделал хотя бы один заказ:

```sql
SELECT users.name, COUNT(orders.id) AS orders_count, SUM(orders.total) AS total_spent
FROM users
INNER JOIN orders ON orders.user_id = users.id
GROUP BY users.id, users.name
HAVING COUNT(orders.id) > 0
ORDER BY total_spent DESC;
```

Такой запрос комбинирует `JOIN` (связывание таблиц), `GROUP BY` и агрегатные функции (`COUNT`, `SUM`), `HAVING` (фильтрация по агрегату, в отличие от `WHERE`, который фильтрует строки до группировки) и `ORDER BY` — типичный набор для отчётных запросов, с которыми сталкивается фронтенд/фуллстек-разработчик при построении дашбордов.

### Понятия индексов, для чего они нужны, влияние индексации на производительность приложения

Индекс — дополнительная структура данных (обычно B-дерево), создаваемая на одном или нескольких столбцах таблицы, позволяющая СУБД находить нужные строки без полного перебора таблицы (full table scan). Без индекса поиск по столбцу требует проверки каждой строки — `O(n)`; с индексом поиск сводится к `O(log n)`, что критично для таблиц с миллионами строк. Индексы ускоряют операции чтения (`SELECT` с `WHERE`, `JOIN`, `ORDER BY`), но замедляют операции записи (`INSERT`/`UPDATE`/`DELETE`), так как индекс тоже нужно обновлять при каждом изменении данных, и занимают дополнительное место на диске — поэтому индексы создаются осознанно, обычно на столбцах, часто используемых в условиях фильтрации и связях, а не на всех подряд.

```sql
-- Без индекса: поиск по email требует полного сканирования таблицы users
SELECT * FROM users WHERE email = 'alice@example.com';

-- Создание индекса ускоряет такие запросы
CREATE INDEX idx_users_email ON users(email);
```
