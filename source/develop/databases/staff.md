# Базы данных — Staff

## Техники оптимизаций запросов и транзакций

Оптимизация запросов начинается с анализа плана выполнения (`EXPLAIN ANALYZE` в PostgreSQL, `EXPLAIN` в MySQL). План показывает, использует ли запрос индексы, сколько строк реально сканируется на каждом шаге и где возникают дорогие операции: sequential scan на большой таблице, sort на диске вместо памяти, nested loop join на больших наборах данных.

Ключевые техники ускорения запросов:

- **Покрывающие индексы** (covering index) — индекс содержит все столбцы, нужные запросу, и СУБД не обращается к самой таблице.
- **Явный список столбцов** вместо `SELECT *` — меньше данных читается и передаётся.
- **Денормализация «горячих» путей чтения** там, где `JOIN` стал узким местом.
- **Батчинг** множества мелких запросов в один — устранение проблемы N+1.
- **Партиционирование** больших таблиц (см. senior.md) для запросов, затрагивающих только часть данных.

Для транзакций работают другие рычаги:

- Минимизировать время удержания блокировок: короткие транзакции, медленная внешняя логика — за их пределами.
- Выбирать минимально достаточный уровень изоляции вместо Serializable «на всякий случай».
- Использовать оптимистичные блокировки (проверка версии строки при `UPDATE`) вместо пессимистичных (`SELECT ... FOR UPDATE`), когда вероятность конфликта низка.

```sql
-- Покрывающий индекс: запрос обслуживается целиком из индекса, без обращения к таблице
CREATE INDEX idx_orders_covering ON orders(user_id, status) INCLUDE (total, created_at);

EXPLAIN ANALYZE
SELECT user_id, status, total, created_at FROM orders WHERE user_id = 42 AND status = 'shipped';
-- план покажет "Index Only Scan" вместо "Seq Scan" при удачном покрывающем индексе
```

```sql
-- Оптимистичная блокировка через версионирование строки
UPDATE products SET stock = stock - 1, version = version + 1
WHERE id = 7 AND version = 3; -- если version уже изменилась параллельной транзакцией, 0 строк обновится
```

На практике эти техники применяются в комплексном проектировании и оптимизации реляционных и NoSQL баз данных — объединении нормализации транзакционного ядра схемы (senior.md) с целевой денормализацией «горячих» путей чтения и покрывающими индексами. Например, в реляционной схеме заказов таблица `orders` остаётся нормализованной для целостности записи, но для быстрого отображения списка заказов в UI создаётся материализованное представление, агрегирующее данные из нескольких таблиц:

```sql
CREATE MATERIALIZED VIEW order_summary AS
SELECT
  orders.id,
  users.name AS user_name,
  orders.total,
  orders.status,
  orders.created_at
FROM orders
JOIN users ON users.id = orders.user_id;

CREATE UNIQUE INDEX ON order_summary(id);
REFRESH MATERIALIZED VIEW CONCURRENTLY order_summary; -- обновление без блокировки чтения
```

Для NoSQL-части — проектирование схемы MongoDB под конкретный паттерн чтения (embedding для данных, читаемых всегда вместе, referencing для данных с независимым жизненным циклом или неограниченным ростом вложенного массива), что было заложено ещё в senior.md, здесь расширяется явным контролем размера документа (лимит 16MB в MongoDB) как архитектурным ограничением при выборе между embedding и referencing.

Похожим образом эти техники используются и для оптимизации и масштабирования баз данных под большие объёмы данных — комбинация партиционирования, шардирования и read-реплик для системы с большим объёмом данных. Например, таблица событий, партиционированная по месяцу (см. senior.md) на каждом шарде, с шардированием по `tenant_id` между несколькими серверами, и read-репликами на каждом шарде для разгрузки аналитических запросов от транзакционной нагрузки:

```sql
-- Партиционирование внутри шарда (управление старыми данными без дорогого DELETE)
DROP TABLE events_2025_01; -- вместо DELETE FROM events WHERE created_at < '2025-02-01' по миллионам строк
```

```js
// Направление аналитических запросов на read-реплику вместо primary (Node.js + pg)
const readPool = new Pool({ host: 'replica.db.internal' });
const writePool = new Pool({ host: 'primary.db.internal' });

async function getAnalyticsReport() {
  return readPool.query('SELECT ... FROM events ...'); // не нагружает primary, принимающий записи
}

async function createEvent(data) {
  return writePool.query('INSERT INTO events ...', [data]); // только через primary
}
```

Такой подход демонстрирует применение всех техник горизонтального масштабирования из senior.md (репликация, шардирование, партиционирование) в едином архитектурном решении, а не по отдельности.

## Современные тренды и технологии в области баз данных (NewSQL, Hybrid Transactional/Analytical Processing)

**NewSQL** — класс распределённых БД (CockroachDB, Google Spanner, YugabyteDB, TiDB), совмещающих горизонтальную масштабируемость и отказоустойчивость NoSQL с полными гарантиями ACID и привычным SQL-интерфейсом. Технически это достигается консенсус-протоколами (Raft, Paxos) для репликации со строгой консистентностью и автоматическим шардированием, прозрачным для приложения.

**HTAP (Hybrid Transactional/Analytical Processing)** — подход, устраняющий отдельный ETL-пайплайн между OLTP-системой (много мелких чтений и записей) и OLAP-хранилищем (тяжёлые агрегирующие запросы). Аналитические запросы выполняются прямо на актуальных транзакционных данных, без задержки репликации в отдельное хранилище. Примеры: TiDB, SingleStore, SAP HANA.

```text
Традиционный подход:            HTAP-подход:
OLTP БД → ETL (задержка) → OLAP БД     Единая БД, обслуживающая
                                          и транзакционные, и аналитические запросы
                                          без отдельного ETL-этапа
```

## Принципы оптимизации и безопасности SQL-запросов

Оптимизация и безопасность SQL-запросов пересекаются в одной практике — параметризованных запросах (prepared statements). Помимо защиты от SQL-инъекций (см. security/senior.md), они позволяют СУБД кэшировать план выполнения и переиспользовать его при повторных вызовах с другими параметрами.

Принципы безопасности на уровне БД:

- **Наименьшие привилегии** для сервисных аккаунтов: отдельный пользователь БД без прав `DROP`/`ALTER` для обычного веб-приложения.
- **Row-level security** для многоарендных (multi-tenant) систем — ограничение видимости строк на уровне самой БД, а не только в коде.
- **Шифрование чувствительных столбцов** (`pgcrypto` и подобные расширения).
- **Аудит-логирование** обращений к чувствительным таблицам.

Принципы оптимизации на уровне архитектуры запросов:

- Не применять функции к индексируемому столбцу в `WHERE`: `WHERE YEAR(created_at) = 2026` индекс не использует, `WHERE created_at >= '2026-01-01'` — использует.
- Прогонять `EXPLAIN` до деплоя изменений схемы в прод.
- Вести регулярный аудит медленных запросов (`pg_stat_statements`, slow query log).

```sql
-- Row-Level Security (PostgreSQL) — изоляция данных арендатора на уровне БД, а не только в коде
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.current_tenant')::INT);
-- даже при ошибке в коде приложения пользователь физически не увидит чужие строки
```
