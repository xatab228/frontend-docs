### Техники оптимизаций запросов и транзакций

Оптимизация запросов начинается с анализа плана выполнения (`EXPLAIN ANALYZE` в PostgreSQL, `EXPLAIN` в MySQL), который показывает, использует ли запрос индексы, сколько строк реально сканируется на каждом шаге и где возникают дорогие операции (sequential scan на большой таблице, sort в памяти vs на диске, nested loop join на больших наборах данных). Ключевые техники: покрывающие индексы (covering index — индекс содержит все столбцы, нужные запросу, так что СУБД не обращается к самой таблице), избегание `SELECT *` в пользу явного списка нужных столбцов, денормализация «горячих» путей чтения там, где `JOIN` становится узким местом, батчинг множества мелких запросов в один (устранение проблемы N+1), партиционирование больших таблиц (см. senior.md) для ускорения запросов, затрагивающих только часть данных. Для транзакций — минимизация времени удержания блокировок (короткие транзакции, вынесение медленной внешней логики за пределы транзакции), выбор минимально достаточного уровня изоляции вместо Serializable «на всякий случай», и использование оптимистичных блокировок (проверка версии строки при `UPDATE`) вместо пессимистичных (`SELECT ... FOR UPDATE`) в сценариях с низкой вероятностью конфликта, чтобы не блокировать параллельные транзакции без необходимости.

```sql
-- Покрывающий индекс: запрос обслуживается целиком из индекса, без обращения к таблице
CREATE INDEX idx_orders_covering ON orders(user_id, status) INCLUDE (total, created_at);

EXPLAIN ANALYZE
SELECT user_id, status, total, created_at FROM orders WHERE user_id = 42 AND status = 'shipped';
-- план покажет "Index Only Scan" вместо "Seq Scan" при удачном покрывающем индексе
```

```sql
-- Оптимистичная блокировка через версионирование строки
UPDATE products SET stock = stock - 1, version = version + 1
WHERE id = 7 AND version = 3; -- если version уже изменилась параллельной транзакцией, 0 строк обновится
```

### Современные тренды и технологии в области баз данных (NewSQL, Hybrid Transactional/Analytical Processing)

NewSQL — класс распределённых БД (CockroachDB, Google Spanner, YugabyteDB, TiDB), стремящихся совместить горизонтальную масштабируемость и отказоустойчивость NoSQL-систем с полными гарантиями ACID и привычным SQL-интерфейсом реляционных БД — то есть избежать компромисса CAP-теоремы, который вынуждал классические NoSQL-системы жертвовать строгой согласованностью. Технически это достигается за счёт консенсус-протоколов (Raft, Paxos) для репликации данных между узлами с сохранением строгой консистентности и автоматического шардирования, прозрачного для приложения. HTAP (Hybrid Transactional/Analytical Processing) — архитектурный подход, устраняющий необходимость в отдельном ETL-пайплайне между OLTP-системой (транзакционная нагрузка — много мелких чтений/записей) и OLAP-хранилищем (аналитическая нагрузка — тяжёлые агрегирующие запросы по большим объёмам), позволяя выполнять аналитические запросы напрямую на актуальных транзакционных данных без задержки репликации в отдельное хранилище (TiDB, SingleStore, SAP HANA — примеры HTAP-систем).

```
Традиционный подход:            HTAP-подход:
OLTP БД → ETL (задержка) → OLAP БД     Единая БД, обслуживающая
                                          и транзакционные, и аналитические запросы
                                          без отдельного ETL-этапа
```

### Принципы оптимизации и безопасности SQL-запросов

Оптимизация и безопасность SQL-запросов пересекаются в одной ключевой практике — параметризованных запросах (prepared statements): помимо защиты от SQL-инъекций (см. security/senior.md), они позволяют СУБД кэшировать план выполнения запроса и переиспользовать его при повторных вызовах с другими параметрами, что снижает накладные расходы на парсинг и построение плана. Принципы безопасности на уровне БД: принцип наименьших привилегий для сервисных аккаунтов приложения (отдельный пользователь БД без прав `DROP`/`ALTER` для обычного веб-приложения), row-level security для многоарендных (multi-tenant) систем — ограничение видимости строк на уровне самой БД, а не только в коде приложения, шифрование чувствительных столбцов (`pgcrypto` и подобные расширения) и аудит-логирование обращений к чувствительным таблицам. Принципы оптимизации на уровне архитектуры запросов: избегать функций на индексируемом столбце в `WHERE` (`WHERE YEAR(created_at) = 2026` не использует индекс на `created_at`, тогда как `WHERE created_at >= '2026-01-01'` использует), использовать `EXPLAIN` до деплоя изменений схемы в прод, вести регулярный аудит медленных запросов (`pg_stat_statements`, slow query log).

```sql
-- Row-Level Security (PostgreSQL) — изоляция данных арендатора на уровне БД, а не только в коде
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.current_tenant')::INT);
-- даже при ошибке в коде приложения пользователь физически не увидит чужие строки
```

### Проектировать и оптимизировать реляционные и NoSQL базы данных

Комплексное проектирование объединяет нормализацию транзакционного ядра схемы (senior.md) с целевой денормализацией «горячих» путей чтения и покрывающими индексами (см. раздел выше) — например, в реляционной схеме заказов таблица `orders` остаётся нормализованной для целостности записи, но для быстрого отображения списка заказов в UI создаётся материализованное представление, агрегирующее данные из нескольких таблиц:

```sql
CREATE MATERIALIZED VIEW order_summary AS
SELECT
  orders.id,
  users.name AS user_name,
  orders.total,
  orders.status,
  orders.created_at
FROM orders
JOIN users ON users.id = orders.user_id;

CREATE UNIQUE INDEX ON order_summary(id);
REFRESH MATERIALIZED VIEW CONCURRENTLY order_summary; -- обновление без блокировки чтения
```

Для NoSQL-части — проектирование схемы MongoDB под конкретный паттерн чтения (embedding для данных, читаемых всегда вместе, referencing для данных с независимым жизненным циклом или неограниченным ростом вложенного массива), что было заложено ещё в senior.md, здесь расширяется явным контролем размера документа (лимит 16MB в MongoDB) как архитектурным ограничением при выборе между embedding и referencing.

### Оптимизировать и масштабировать базы данных для обработки больших объемов данных

Комбинация партиционирования, шардирования и read-реплик для системы с большим объёмом данных — например, таблица событий, партиционированная по месяцу (см. senior.md) на каждом шарде, с шардированием по `tenant_id` между несколькими серверами, и read-репликами на каждом шарде для разгрузки аналитических запросов от транзакционной нагрузки:

```sql
-- Партиционирование внутри шарда (управление старыми данными без дорогого DELETE)
DROP TABLE events_2025_01; -- вместо DELETE FROM events WHERE created_at < '2025-02-01' по миллионам строк
```

```js
// Направление аналитических запросов на read-реплику вместо primary (Node.js + pg)
const readPool = new Pool({ host: 'replica.db.internal' });
const writePool = new Pool({ host: 'primary.db.internal' });

async function getAnalyticsReport() {
  return readPool.query('SELECT ... FROM events ...'); // не нагружает primary, принимающий записи
}

async function createEvent(data) {
  return writePool.query('INSERT INTO events ...', [data]); // только через primary
}
```

Такой подход демонстрирует применение всех техник горизонтального масштабирования из senior.md (репликация, шардирование, партиционирование) в едином архитектурном решении, а не по отдельности.
