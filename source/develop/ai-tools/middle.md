# Работа с инструментами ИИ — Middle

### Ограничения ИИ, LLM и агентов, как выбрать подходящие сценарии использования

LLM обладают рядом принципиальных ограничений, которые важно учитывать при встраивании их в рабочий процесс. Во-первых, галлюцинации — модель может уверенно сгенерировать несуществующий API-метод библиотеки или неверную сигнатуру функции, поэтому код, полученный от ИИ, всегда нужно компилировать и тестировать, а не доверять на слово. Во-вторых, ограниченное контекстное окно — модель не видит весь проект целиком, если её явно не снабдить нужными файлами, из-за чего сгенерированный код может не учитывать существующие соглашения проекта. В-третьих, отсутствие «памяти» между независимыми сессиями (если не используются специальные механизмы) и детерминированная невоспроизводимость — один и тот же промпт может дать разные ответы. Хорошие сценарии для ИИ: генерация шаблонного кода (боилерплейт компонентов, типов, тестов), объяснение чужого кода, рефакторинг по чётким правилам, написание документации. Плохие сценарии: критичная бизнес-логика без ревью, работа с секретами и приватными данными в облачных моделях, задачи, где нужна 100% детерминированная корректность без последующей проверки человеком.

### Принципы использования ИИ для генерации тестов или проверки кода

ИИ хорошо справляется с генерацией unit-тестов, потому что тестовые сценарии часто следуют предсказуемым паттернам (happy path, граничные значения, ошибочный ввод), и модель может по сигнатуре функции быстро накидать набор кейсов, которые разработчик потом дополняет и проверяет. Для проверки кода (code review) ИИ используется как первый фильтр: он ловит очевидные проблемы — незакрытые промисы, отсутствие обработки ошибок, нарушения типизации — до того, как код попадёт к живому ревьюеру, экономя время команды.

```ts
// Функция для которой нужно сгенерировать тесты
export function clampPage(page: number, totalPages: number): number {
  if (totalPages <= 0) return 1;
  return Math.min(Math.max(page, 1), totalPages);
}
```

```ts
// Тесты, сгенерированные ИИ по промпту
// "напиши unit-тесты на vitest для clampPage, покрой граничные случаи"
import { describe, it, expect } from 'vitest';
import { clampPage } from './clampPage';

describe('clampPage', () => {
  it('возвращает 1, если page меньше 1', () => {
    expect(clampPage(0, 10)).toBe(1);
  });
  it('возвращает totalPages, если page больше totalPages', () => {
    expect(clampPage(15, 10)).toBe(10);
  });
  it('возвращает page без изменений внутри диапазона', () => {
    expect(clampPage(5, 10)).toBe(5);
  });
  it('возвращает 1, если totalPages <= 0', () => {
    expect(clampPage(5, 0)).toBe(1);
  });
});
```

### Основные сферы применения ИИ в продуктах (текстовые ассистенты, автоответчики и пр.)

Во фронтенд-продуктах ИИ чаще всего встречается в виде: текстовых ассистентов и чат-виджетов поддержки (виджет на сайте, отвечающий на вопросы пользователя через LLM с доступом к базе знаний), автодополнения и умного поиска (поисковая строка, которая понимает смысл запроса, а не только точное совпадение подстроки), персонализации контента (рекомендательные блоки на основе поведения пользователя), генерации контента на лету (автоматические описания товаров, alt-тексты для изображений), а также автоответчиков и авто-суммаризации (сокращение длинных обсуждений, тикетов, писем до краткой выжимки).

### Методы интеграции ИИ в продукты (API, SDK, встраиваемые модули)

Есть три основных способа встроить ИИ в приложение. Прямая интеграция через REST/HTTP API провайдера (OpenAI, Anthropic, Google) — фронтенд или бэкенд отправляет запрос с промптом и получает ответ; самый гибкий, но требует самостоятельно обрабатывать стриминг, ошибки и rate limiting. Через официальный SDK — обёртка над API с типами, retry-логикой и удобными хелперами (например, `@anthropic-ai/sdk` для Node.js/браузера), что снижает объём шаблонного кода. Через встраиваемые готовые модули/виджеты — сторонний чат-виджет или UI-компонент, который подключается скриптом или npm-пакетом и уже содержит логику общения с моделью, но даёт меньше контроля над поведением.

```ts
// Пример прямой интеграции через SDK (серверная часть, ключ не должен попадать на клиент)
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

export async function generateProductDescription(title: string, features: string[]) {
  const message = await client.messages.create({
    model: 'claude-sonnet-4-5',
    max_tokens: 300,
    messages: [{
      role: 'user',
      content: `Напиши краткое маркетинговое описание товара "${title}" с характеристиками: ${features.join(', ')}.`,
    }],
  });
  return message.content[0].type === 'text' ? message.content[0].text : '';
}
```

## Практика (УМЕЕТ)

### Автоматизировать рутинные задачи (форматирование, базовое тестирование, простая генерация кода, документирование, code review) с LLM

На практике автоматизация рутины строится вокруг связки IDE-агента и чётких промптов-шаблонов, которые команда сохраняет и переиспользует. Например, промпт "сгенерируй JSDoc для всех экспортируемых функций в файле, не меняя логику" применяется к любому файлу за секунды, а промпт из раздела про генерацию тестов — к любой чистой функции проекта.

```json
// .github/copilot-instructions.md — переиспользуемые инструкции для Copilot в репозитории
```
```markdown
Проект использует TypeScript strict mode, React 18, Vitest.
При генерации кода:
- всегда добавляй типы, не используй any
- для новых компонентов создавай рядом файл ComponentName.test.tsx
- используй именованные экспорты, а не default
```

### Применять AI Агентов встроенных в среду разработки (IDE) для написания и модификации кода

IDE-агенты (Cursor, GitHub Copilot Workspace, Windsurf, режим агента в Claude Code) отличаются от простого автодополнения тем, что могут самостоятельно читать несколько файлов проекта, вносить правки сразу в нескольких местах и выполнять команды (запуск тестов, линтера). Пример задачи агенту: "переименуй пропс `onSave` в `onSubmit` во всём компоненте FormModal и всех местах его использования в проекте, обнови типы". Агент находит все вхождения через поиск по проекту, правит сигнатуру компонента, все call-сайты и типы, а затем можно попросить его прогнать `npm run typecheck`, чтобы убедиться, что ничего не сломано — это прямое расширение навыка генерации кода из ЗНАЕТ-раздела на уровень многофайловых изменений.

### Работать с ограничениями размера входных данных (контекстное окно) и оптимизировать запросы к модели

Когда файл или набор файлов не помещается в контекстное окно модели, запрос нужно осознанно сократить: передавать не весь файл, а только релевантную функцию с сигнатурами зависимостей, использовать саммари вместо полного текста больших логов, разбивать задачу на последовательные шаги с промежуточными результатами вместо одного гигантского промпта.

```ts
// Вместо передачи всего 2000-строчного файла модели —
// извлекаем только релевантный контекст
function buildPromptContext(fileContent: string, targetFunctionName: string): string {
  const lines = fileContent.split('\n');
  const start = lines.findIndex((l) => l.includes(`function ${targetFunctionName}`));
  const relevantSlice = lines.slice(Math.max(0, start - 5), start + 40).join('\n');
  return `Вот фрагмент кода вокруг функции ${targetFunctionName}:\n${relevantSlice}`;
}
```

Такой подход снижает стоимость запроса, уменьшает задержку ответа и повышает точность, потому что модель не отвлекается на нерелевантный код остального файла.
